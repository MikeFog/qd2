# Разбор XML-языка паспортов и фильтров

**Дата:** 2026-09-10. Замеры сняты на `ArtvisDev` (`iEntity.passport`, `iEntity.filter`,
только `isObsolete = 0`), поведение сверено с читающим кодом
(`FogSoft.WinForm/Passport/Classes/*`, `FieldTypeResolver`, `ColumnInfo`).

## Зачем это перед этапом 2

Этап 2 — это написать веб-рендерер для данного XML-языка. Стоимость рендерера прямо
пропорциональна числу **различных конструкций**, которые он обязан понимать, а не числу
экранов. Каждая избыточная форма записи — лишняя ветка в новом коде навсегда плюс лишний
случай в сверке с десктопом «поле в поле».

Пока рендерер один (десктопный), правка языка стоит одной миграции метаданных. После
появления второго — двух рендереров и двух проверок. Поэтому чистку дешевле делать сейчас.

## Язык как он есть

**Элементы** (диспетчер `PageControl.CreateInstance`) — 9 штук:
`label`, `field`, `separator`, `lookup`, `objectPicker`, `selector`, `button`, `image`,
`treeselector`.

**Виды полей** (диспетчер `PageField.CreateInstance` по `FieldTypeResolver`) — 10:
строка, двойная строка, textarea, целое, дробное/деньги, булево, дата, дата-время,
время, длительность.

**Тип поля берётся из двух источников.** Приоритет — у атрибута `type` в XML; если его
нет, тип выводится из колонки таблицы (`ColumnInfo`). В паспортах `type` указан у 41
вхождения из 349 (остальные — из колонки), в фильтрах — у 230 из 230. То есть в паспорте
и фильтре действуют **разные соглашения** для одного и того же элемента `field`.

## 1. Настоящие дубли: одно и то же двумя способами

**Текст — три написания.** `string`, `varchar` и `password` в `FieldTypeResolver` дают
один и тот же `IsString`. В данных `string` встречается только в паспортах (24), `varchar`
только в фильтрах (6) — разведены по контексту без причины. `password` не встречается
**ни разу**: настоящее поле пароля делается иначе — `type="string" passportchar="*"
hashit="true"` (сущности 107, 109). Ветка `password` в резолвере мертва.

**«Это деньги» — два независимых механизма.** `type="Money"` (1 вхождение) влияет на формат
подписи в `PageFieldLabel` (`ToString("c")`), а гриды и экспорт определяют денежность
совершенно отдельно — `ColumnInfo.IsMoneyData(columnInfo, attribute)`
(`SmartGrid`, `GenericGridView`, `ExportManager`). Одно понятие — две несвязанные ветки,
которые могут разойтись.

## 3. Ловушки (не дубли, но чинить стоит)

**Неизвестный тип — поле молча исчезает.** Если `type` не опознан, все флаги
`FieldTypeResolver` остаются false, `PageField.CreateInstance` возвращает `null`, и контрол
просто не создаётся. Ни исключения, ни записи в лог. Опечатка в типе = поле пропало с формы.

Ловушка не теоретическая — она уже сработала. Проверка «поля, у которых нет ни `type`, ни
колонки в таблице, ни `source`» нашла три таких поля в двух активных сущностях:

| сущность | tableName | поля |
|---|---|---|
| 76 | `aliasSQLparams` | `name`, `alias` |
| 153 (`RollerAdvertType`) | `RollerAdvertType` | `name` |

**Обеих таблиц в базе не существует** (`INFORMATION_SCHEMA.COLUMNS` пуст для них), при этом
`isObsolete = 0`. То есть карточки этих сущностей сейчас открываются пустыми, и никто об
этом не узнаёт. Разбираться, живые ли это сущности или забытые метаданные, — отдельная
задача; диагностика ниже сделает такие случаи заметными сама.

**`mandatory` не работает у полей, привязанных к колонке.** Порядок такой: `required`
задаёт обязательность жёстко и закорачивает остальное; иначе, если колонка есть, решает её
nullability, а `mandatory` игнорируется; `mandatory` срабатывает только при отсутствии
колонки; `isMandatoryOnCreate="false"` ослабляет правило для новых объектов.
Проверено: все 4 нынешних вхождения `mandatory` — это `password`/`confirmPassword`
сущности `User`, у которых колонки нет, то есть написаны они там, где работают.
Ловушка не в текущих данных, а в следующем разе.

## 4. Что кашей НЕ является (проверено, не трогать)

- **Регистр `DF_DATE` / `df_date`** — резолвер приводит к нижнему регистру, разницы нет.
- **`disabled` и `locked`** — разная семантика: `locked` означает «недоступно всем, кроме
  администратора» (см. комментарий в `PageControl.Constants.cs`).
- **Префикс `df_`** — не произвол: это имена пользовательских типов колонок из
  `ColumnInfo.UDTypes` (`DF_DATE`, `DF_TIME`, `DF_DATETIME`), XML переиспользует словарь БД.
- **Разделение `lookup` / `objectPicker` / `selector`** — это три разных контрола, а не
  синонимы (выпадающий список, выбор объекта диалогом, множественный выбор).
- **Атрибут `filter` и вложенный элемент `<filter>` у `lookup`.** В первой редакции этого
  разбора (2026-09-10) они были записаны в дубли — **это была ошибка, проверка перед правкой
  данных её опровергла.** Совпадает только слово, механизмы разные:
  вложенный `<filter name= type= value=/>` собирает словарь **параметров загрузки** списка
  (`PageFieldSelector.GetFilters` — типизирует значение и кладёт в параметры процедуры);
  атрибут `filter="..."` работает в паре с `parentLookupName` и задаёт **каскадные списки** —
  это строка формата, куда подставляется значение из родительского списка
  (`PageFieldDependentLookup`: `string.Format(parentLookupInfo.Filter, sourceLookupSelectedValue)`).
  Сводить их к одной форме нельзя.
