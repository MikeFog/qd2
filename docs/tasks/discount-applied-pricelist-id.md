# Задача: запоминать применённую скидку и предупреждать о затронутых акциях при её правке

Статус: **реализовано 23.09.2026** (схема согласована с Мишей и заказчиком): SQL накачен на ArtvisDev и проверен,
qd2 собран; ждёт проверки в qd2, коммита и прода. Деплой — `ArtvisDB/Scripts/discount-applied-pricelist-id-deploy.sql`.
Отступление от промпта: добавление станции в пакет (190 AddItem) акции не задевает и окна не показывает —
все кампании посчитанной акции уже совпали с прайс-листом, новая станция условия не меняет.
Ниже — промпт, по которому делалось.

## Промпт

Контекст — qd2 (WinForms + MS SQL, логика в хранимых процедурах). Перед началом прочитай
`CLAUDE.md`, `docs/ARCHITECTURE.md`, `docs/AI_AGENT_PLAYBOOK.md`, `docs/business-errors.md`,

### Проблема

Скидки считаются в `dbo.ActionRecalculate` и хранятся только **значением**:
- объёмная скидка станции — `Campaign.discount`, из `hlp_CompanyDiscountCalculate`
  по `Campaign.startDate` = день первого выпуска кампании (набор `DiscountRelease`, сущность 22, +
  пороги `DiscountValue`, сущность 23);
- пакетная — `Action.discount`, из `hlp_ActionDiscountCalculate` по дате начала акции
  (`MIN(Campaign.startDate)`); из всех подходящих `PackageDiscountPriceList` (сущность 191) берётся
  минимальный коэффициент. Условия пакета: `PackageDiscount.count` (сущность 189), станции и флаги
  типов `PackageDiscountMassmedia` (сущность 190).

Какая скидка применилась, нигде не записано. Человек меняет скидку, которой уже воспользовались
акции, и не знает об этом; при следующем пересчёте акции (любая правка выпусков) скидка у неё молча
меняется.

### Решения (не пересматривать)

1. **Запоминаем применённую скидку**: `Campaign.discountReleaseID`, `Action.packageDiscountPriceListID`,
   пишутся при каждом `ActionRecalculate`. **Старые данные не заполняем** — NULL, прошлое не волнует.
2. **При сохранении правки скидки** — если правка задевает акции (по этим ссылкам), показать список
   затронутых акций с выгрузкой в Excel и спросить «применить?». «Применить» — правка сохраняется,
   **с акциями ничего не делаем** (не пересчитываем), решение на человеке. «Отмена» — назад в паспорт.
   Никакого пробного пересчёта в транзакции — только ссылки.
3. **В списке все акции** — и подтверждённые, и макеты (с колонкой, какая это).
4. **Удалять использованную скидку нельзя** — жёсткий отказ сообщением, без списка.
5. **Жёсткие проверки остаются** (начало ≤ окончание, пересечение периодов).
6. **Только qd2.** Веб в проде не используется; окно и проверку перенесут, когда заказчик
   переделает механизм. Флаг «подтверждено» в процедурах записи **не делаем**.
7. **Журнал решений не ведём** (кто подтвердил, сколько акций) — только обычный `qd2.log`.

### Что сделать — SQL

1. **Схема.** `Action.packageDiscountPriceListID INT NULL` → FK на `PackageDiscountPriceList`,
   `Campaign.discountReleaseID SMALLINT NULL` → FK на `DiscountRelease`, **без каскада**; по
   неуникальному индексу. Без заполнения существующих строк. Файлы таблиц в `ArtvisDB/dbo/Tables`
   тоже. Учти: `PackageDiscount → PackageDiscountPriceList` и `MassMedia → DiscountRelease` —
   `ON DELETE CASCADE`; новые FK сделают такие каскадные удаления невозможными при ссылках —
   так и надо, но отказ должен приходить дружелюбной проверкой раньше FK (п. 5).
2. **`hlp_ActionDiscountCalculate`** — `@packageDiscountPriceListID INT = NULL OUTPUT`.
   Минимальный `discount`, при равенстве — меньший ID (образец — `pc_PackageDiscountCalculateModel`,
   `TOP 1 ... ORDER BY pl.discount`). Значение скидки обязано остаться прежним
   (`COALESCE(MIN(discount), 1)`); нет подходящего — NULL.
3. **`hlp_CompanyDiscountCalculate`** — `@discountReleaseID SMALLINT = NULL OUTPUT`. Выбор строки
   порога сделать явным: `TOP 1 ... ORDER BY dv.summa DESC` (сейчас присваивание без ORDER BY).
   ID — только когда порог найден, иначе NULL.
4. **`ActionRecalculate`** (горячая процедура, история дедлоков) — минимально:
   колонка `discountReleaseID` в `#CampaignPhase1` из OUTPUT в курсоре фазы 1E → в существующий
   `UPDATE c ... FROM #CampaignPhase1`; в фазе 2 ID из `hlp_ActionDiscountCalculate`
   (ветка `@campaignCount <= 1` — NULL) → в существующий `UPDATE dbo.[Action]`. Никаких новых
   запросов/блокировок. Других писателей `Action.discount`/`Campaign.discount` нет (проверено:
   `SpecialActionIUD`, `job_DeleteHistory` вставляют `discount = 1`) — перепроверь grep'ом.
5. **Жёсткий запрет удаления использованного** (новые ключи `iMessage`, «… Операция прервана.»,
   в тексте — что делать: создать новую скидку копированием):
   `DiscountReleaseIUD` DeleteItem, `PackageDiscountPriceListIUD` DeleteItem,
   `PackageDiscountIUD` DeleteItem (если использован хоть один прайс-лист пакета). Заодно убрать
   хвост старой схемы в `PackageDiscountPriceListIUD` DeleteItem (`UPDATE ... SET finishDate = @date
   WHERE ... finishDate = @startDate`). Удаление порога `DiscountValue` и станции пакета — это
   изменение содержимого (п. 6), не удаление скидки.
6. **Процедура(ы) «кого заденет»** — только чтение, принимают те же параметры, что и `*IUD` для
   этой правки, возвращают список акций: `actionID`, фирма, менеджер, период акции, подтверждена/макет,
   сохранённая скидка (для объёмной — ещё станция и кампания). Правила:
   - **даты** набора / прайс-листа: ссылающиеся кампании/акции, чья дата начала (`Campaign.startDate`
     / `Action.startDate`) **выпадает** из нового периода; продление и сокращение без выпадения —
     пусто;
   - **содержимое** — все ссылающиеся: процент, порог суммы, процент заполнения прайс-листа пакета;
     флаги типов набора (для объёмной — только кампании снятого типа); любые правки порогов
     `DiscountValue` (добавить/изменить/удалить) — все кампании, ссылающиеся на набор; станции и их
     флаги `PackageDiscountMassmedia` — все акции, ссылающиеся на прайс-лист; смена `count` пакета —
     все акции, ссылающиеся на любой его прайс-лист. Имя пакета — не задевает.
   Одна процедура с `@entityID`/`@actionName` или по одной на сущность — на твоё усмотрение, главное
   без дублирования правил. Пишущие процедуры (найдено 23.09.2026, перепроверь): `DiscountReleaseIUD`,
   `DiscountValueIUD`, `PackageDiscountPriceListIUD`, `PackageDiscountMassmediaID`, `PackageDiscountIUD`.

### Проверка готовности

1. На ArtvisDev: `ActionRecalculate` в транзакции с откатом **до** и **после** правок по выборке
   (ничьи пакетов, спонсорские/модульные, одна кампания, пустые кампании) — `discount`/`totalPrice`
   совпадают один в один, ID заполнены там, где скидка найдена.
2. Процедура п. 6 на каждый вид правки: использованная скидка — список правильный; неиспользованная —
   пусто; продление периода использованной — пусто.
3. Удаление использованного — отказ нужным ключом; неиспользованного — проходит.
4. Время `ActionRecalculate` на типичной акции до/после — без заметной разницы.
5. `qd2.sln` собирается; в qd2 (вход делает Миша) — окно появляется, Excel выгружается,
   «Отмена» оставляет паспорт, «Применить» сохраняет.
6. Скрипт деплоя идемпотентен.
