# Пакетная скидка: максимальный процент прайма

Постановка согласована с Мишей 18.11.2026 (вопросы 1–11 в чате). Зачем: пакетная скидка действует с порога
«Минимальная сумма (с учётом объёмных скидок)», и менеджеры добирают её праймом — он дороже. Новая настройка
ограничивает долю прайма на каждой кампании пакета.

## 1. Итоговая постановка

**Настройка.** В прайс-листе пакетной скидки (`PackageDiscountPriceList`, сущность 191) поле
«Максимальный процент прайма (%):» — целое 0–100, обязательное. Всем существующим прайс-листам при накате — 100
(прайм без ограничения), так что старые акции считаются как раньше. Новым прайс-листам по умолчанию тоже 100;
порог ниже ставят руками. У поля те же даты действия, что у строки прайс-листа.

**Что такое прайм.** Окно — прайм, если его цена равна максимальной цене окон этой станции в этот день (то же
правило, что в генераторе шаблонов и подсветке ₽). Максимум — по всем окнам станции за день, модульные окна
максимум не меняют (ArtvisDev, 2026 год: ни одного дня, где окно «только для модулей» дороже обычных). День, в
котором у станции все окна по одной цене, — прайм целиком. Окно и день — фактические (`Issue.actualWindowID`,
`TariffWindow.dayActual`, правило 07.10.2026). Цены окон — текущие на момент пересчёта акции; смена цен окон
акции сама не пересчитывает.

**Доля прайма кампании** = секунды роликов в прайм-окнах / все секунды роликов кампании × 100, округление до
0,1. Хранится в кампании (`Campaign.primePercent`), пересчитывается `ActionRecalculate`; скидка проверяется по
этому же числу, что видно в статистике (сравнивается округлённое значение: 30,04% показывается и считается как 30,0).

**Правило.** Проверяется каждая линейная (1) и модульная (3) кампания акции отдельно. Если доля прайма хоть одной
больше порога прайс-листа, этот прайс-лист пакета акции не подходит (другой подходящий прайс-лист может дать
скидку). Граница включительно: 30,0 при пороге 30 проходит, 30,1 — нет. Спонсорские кампании (2) не проверяются —
**вопрос у заказчика**, включение — одно условие в `hlp_ActionDiscountCalculate` и расчёт доли для типа 2.

**Где видно.**
- Статистика кампании (qd2 `CampaignForm`, веб — вкладки «Рекламные окна» и «Модули»), линейной и модульной:
  строка «Прайм: 27,4%». Без выпусков — пусто.
- Статистика веера (qd2 `EditIssuesForm`; веб — «Рекламные окна», когда отмечено несколько кампаний):
  «Прайм, макс.: 42,0% (станция)» — максимум по всем линейным и модульным кампаниям акции, а не только по
  отмеченным в веере.
- Порог в статистике не показываем. Список кампаний акции не меняем.

**Окно «Изменение затронет акции».** При понижении порога в прайс-листе показывает акции этого прайс-листа, где
доля прайма хоть одной линейной или модульной кампании выше нового порога. Видит только акции со ссылкой
`Action.packageDiscountPriceListID` (решение 29.10.2026 не заполнять её задним числом).

**Не делаем сейчас.** Калькулятор цены и оценка в Шаблоне №3 (`pc_PackageDiscountCalculateModel`) порог не
проверяют: им передаются только секунды по станциям, а прайм у калькулятора — по рангу цен тарифа. Расхождение —
К-35 в `docs/tasks/web-price-calculator.md`. Пока во всех прайс-листах 100, его нет.

**Однотарифные станции.** ArtvisDev, окна 2026 года: Дорожное радио (174), Радио Дача (229), Радио Любовь (230),
Маруся ФМ (240), Искатель (241), RFM (243) — весь год одна цена, все шесть во всех пакетах «Переславль» (2–10 шт.,
плюс «4 шт.» на 2027–2029). Размещение на них — всегда 100% прайма, поэтому в пакетах Переславля порог остаётся 100
(решение Миши).

## 2. Изменения

### SQL (Deploy/97)
| Объект | Что |
|---|---|
| `PackageDiscountPriceList.maxPrimePercent` | `tinyint NOT NULL DEFAULT 100` |
| `Campaign.primePercent` | `decimal(4,1) NULL`; NULL у спонсорских, пакетных и пустых кампаний |
| `hlp_ActionCampaignPrimePercent` | новая процедура: доля прайма по `#ActionIssue` вызывающего → `#ActionPrime` — единственное место правила |
| `ActionRecalculate` | фаза 1.0 собирает выпуски линейных и модульных кампаний с окном выхода в `#ActionIssue` одним проходом (`OPTION (LOOP JOIN)`); из него фазы 1A, 1C и доля прайма; фаза 1F пишет `primePercent` |
| `hlp_ActionDiscountCalculate` | кампания типа 1/3 с `primePercent > maxPrimePercent` не совпадает с прайс-листом |
| `PackageDiscountPriceListIUD` | `@maxPrimePercent`: добавление — пусто → 100, копия — из исходного, правка — пусто → прежнее (старый клиент порог не сбросит) |
| `DiscountChangeAffectedActions` | ветка 191 UpdateItem: понижение порога и кампания выше нового порога |
| `Actions1` (одна акция) | `primePercentMax`, `primePercentMaxMassmedia` для статистики веера qd2 |
| `iEntity` 191 | поле паспорта после «Процент заполнения (%):», `min="0" max="100"` |
| `iEntityAttribute` 191 | колонка «Максимальный процент прайма» |
| `iTranslation` | испанский для новых подписей |
| `Campaign` | заполнение `primePercent` у существующих линейных и модульных кампаний порциями по 500 акций через ту же процедуру (только показ и окно предупреждения; скидки не меняет — порог везде 100); ArtvisDev — 37 655 кампаний за 63 с |

`Campaigns` отдаёт `cm.*`, `PackageDiscountPriceLists` — `pdpl.*`: новые колонки приходят без правки процедур.

**Скорость пересчёта (ArtvisDev, 18.11.2026, старые и новые процедуры в откатываемой транзакции, по 2 прохода).**
Акции 2026 года: до 500 выпусков — 3232, 500–2000 — 511, 2000–5000 — 22, больше 5000 — 6.

| Выпусков в акции | Было, мс | Стало, мс |
|---|---|---|
| до 500 (60 акций) | 31,0 | 31,3 |
| 500–2000 (30) | 53,7 | 67,9 |
| 2000+ (5) | 204,8 | 297,7 |

Что не годится (замерено): отдельная функция по выпускам рядом с фазой 1A — второй проход по `Issue × TariffWindow`,
+250 мс на акции в 18 тыс. выпусков; запрос функции внутри `UPDATE` с `#CampaignPhase1` — перекомпиляция, +150 мс;
сбор `#ActionIssue` без `LOOP JOIN` — хеш-соединение с просмотром индекса окон, +500 мс на любой акции.
Замер «функция → `COUNT(*)`» занижен: оптимизатор выбрасывает поиск максимума дня, если результат не нужен.
