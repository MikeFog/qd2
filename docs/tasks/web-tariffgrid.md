## 1. Что на самом деле делает десктоп

Если снять наследование, все семь сеток размещения — это **одна вещь**:

> матрица **«строки × дни»**; ячейка — **место** (окно, получасовой слот, модуль-день,
> программа-день) с остатком времени/штук и набором признаков; действие — **поставить** или
> **снять** ролик в выбранных местах; после действия — пересчёт акции и обновление
> затронутых ячеек.

Разница между типами — только в трёх вещах:

1. **Откуда строки и ячейки** (какие процедуры, что такое «место»).
2. **Как пишется размещение** (какая IUD-процедура, что ставится одним действием).
3. **Какие фильтры и признаки имеют смысл** (позиция, предмет рекламы, прайм, номера роликов).

Всё остальное — шапка с неделей, фиксированные строки дат и счётчиков, цвета, клик,
выделение, панель деталей — общее. В десктопе оно размазано по пяти уровням наследования и
по двадцати проверкам `is`/`as` в `CampaignForm`, а признаки ячейки хранятся в её цвете.

По «местам» типы сводятся к четырём:

| Источник | Место (ячейка) | Строка | Десктоп |
|---|---|---|---|
| **Окна станции** | `TariffWindow` одного дня | тарифное время | `RollerIssuesGrid3` (линейная, ролики спонсорской), модульная — клик ставит модуль на весь день |
| **Слоты акции** | получас × все выбранные станции | получасовой интервал | `TariffWithRangeGrid` (веер) |
| **Модуль-день** | модуль в конкретный день | модуль | `ComboModuleGrid`, `PackModuleGrid` (1 строка), по смыслу — и модульная кампания |
| **Программа-день** | тариф спонсорской программы в день | тариф | `ProgramIssuesGrid2` (чекбоксы) |

## 2. Принципы веб-версии

1. **Композиция вместо наследования.** Один компонент отрисовки матрицы, который ничего не
   знает о типах кампаний. Тип задаётся **источником** — небольшим классом ядра, который
   отдаёт модель сетки и выполняет запись. Ни одной проверки «какого типа сетка» в экране.
2. **Состояние ячейки — в модели, не в оформлении.** Признаки (моя / частично / фирма здесь /
   фирма не на всех станциях / прайм / недоступно / помечено / позиция свободна / подходит
   предмет рекламы) — флаги в модели; CSS-классы выводятся из флагов.
3. **Период одним запросом.** Как у `ComboModuleGrid`, самого удачного члена семейства: модель
   на период строится одним–двумя вызовами, без чтения по окну и по колонке.
4. **Точечное обновление после записи.** Операция возвращает новое состояние только
   затронутых мест; полная перезагрузка — только при смене периода или фильтров.
5. **Один пересчёт акции на действие пользователя.** Клик, «поставить в выделенные», шаблон,
   отмена — это одно действие, в конце один `ActionRecalculate`. В десктопе это нарушено
   в трёх местах (`docs/tariffgrid.md` П-1).
6. **Запись — только через существующие IUD-процедуры** (`IssueIUD`, `ModuleIssueIUD`,
   `AddRangeIssues`, `ProgramIssueIUD`, `PackModuleIssueID`, `MasterIssueDelete`): они же ведут
   занятость окна (`timeInUse*` и др.), других механизмов нет. Новых процедур записи не
   заводим, пока цикл по IUD в одной транзакции укладывается во время (IUD ~4 мс).
7. **Детали — по требованию.** Список выпусков окна, панель пакетного модуля, «Добавленные
   выпуски» веера не перечитываются на каждый клик расстановки (в десктопе это 165 мс из
   231 мс клика — `docs/tariffgrid.md` П-7).
8. **Никакого обходного UI.** Горячие клавиши не переносим (решение 2026-09-18); наведение —
   только CSS; меню действий — общий движок (`ObjectActions`, `ActionMenuService`); итоги
   массовых операций — `TableDialog`; кнопки решают метаданные и права, недоступное — серое.

### 3.1. Ядро: модель

```csharp
public sealed class PlacementGridModel
{
    public DateTime Start, Finish;                 // период (неделя по умолчанию, у комбо — и месяц)
    public IReadOnlyList<PlacementColumn> Columns; // дни: дата, признак выходного
    public IReadOnlyList<PlacementRow> Rows;       // заголовок: время, цена / станция + модуль / тариф
    public PlacementCell?[,] Cells;                // null — места нет (окно не сгенерировано и т.п.)
    public int[] DayTotals;                        // выпусков кампании/акции за день
}

public sealed class PlacementCell
{
    public PlaceKey Key;          // windowId | (slotDateTime) | (moduleId, date) | (tariffId, date)
    public int? FreeSeconds;      // остаток времени
    public int? FreeCount, MaxCount;   // штучные окна
    public CellFlags Flags;       // Mine, MinePartial, FirmHere, FirmPartial, Prime, Disabled,
                                  // Marked, PositionFree, AdvertTypeMatch, …
    public string? Caption;       // особый текст: номера роликов, фирма-владелец программы
}
```

### 3.2. Ядро: источник

```csharp
public interface IPlacementSource
{
    PlacementGridModel Load(DateTime anyDateInPeriod, PlacementFilter filter);
    PlacementResult Place(IReadOnlyList<PlaceKey> places, PlacementBrush brush);  // ролик(и), позиция
    PlacementResult Remove(IReadOnlyList<PlaceKey> places, RemoveFilter filter);  // что снимать
    DataTable LoadPlaceDetails(PlaceKey place);                                   // панель деталей
}

public sealed class PlacementResult
{
    public IReadOnlyList<PlacementCell> ChangedCells;   // перечитанное состояние затронутых мест
    public int[] DayTotals;
    public DataTable Errors;                            // для TableDialog: место + текст ошибки
    public IReadOnlyList<int> CreatedIssueIds;          // для отмены — захват в момент создания
    public decimal ActionTotal;                         // из OUTPUT ActionRecalculate
}
```

Внутри `Place`/`Remove`: одна транзакция на всё действие, IUD-процедура на каждое место,
`ActionRecalculate` один раз, затем перечитывание только затронутых мест. Ошибка по одному
месту не рвёт пачку (как сейчас Insert/Del в десктопе): она попадает в `Errors`.

Классы ядра `Campaign`, `Issue`, `TariffWindowWithRollerIssues`, `MassmediaPricelist` —
`internal`. Источники живут **внутри** ядра и наружу выставляют только публичный фасад —
образец `RollerSubstitution` (`CampaignRoller.cs:109`). Код веера, который сейчас лежит в
`Client/Controls/TariffWithRangeGrid.cs` (вызовы `TariffWindowWithRange`, `AddRangeIssues`,
`MasterIssueDelete`, `RangeSlotIssues`), и транзакции добавления из `RollerIssuesGrid3`
переезжают в ядро. Десктоп можно перевести на них же — тогда логика размещения будет одна
на оба клиента (решение — §7, вопрос 6).

### 3.3. Веб: компонент матрицы

`PlacementGrid.razor` — обычная `<table>`, **без виртуализации**: максимум по данным —
~550 ячеек (линейная неделя) и ~1100 (комбо за месяц), против 40 тыс. строк журнала, где
виртуализация понадобилась. Липкие шапка (даты + счётчик) и левые колонки — теми же
средствами, что `thead th` в `app.css`. Ячейка — один `<td>` с классами из флагов и текстом;
`@key` по месту, чтобы точечное обновление перерисовывало только изменённые ячейки.

Легенда цветов — на экране, а не в памяти пользователя. Цвета берутся из токенов `app.css`
(акцент, `-soft`-варианты статусов), десктопную палитру один в один не копируем.

### 3.4. Веб: экран

- **Страница, не модальное окно.** `DialogHost` всегда `modal-lg` с кнопками «ОК/Отмена» —
  для экрана размещения не подходит. Вход — из журнала акций (действие «Редактировать»
  у кампании и «Массовое редактирование» у акции, сейчас серые).
- **Кисть вместо режимов.** Вместо четырёх `EditMode`: панель «что ставим» (ролик, позиция,
  предмет рекламы). Включённая кисть = клик по месту ставит; выключенная = клик выбирает
  место и открывает детали. Шаблон — отдельный диалог, время из выбранного места
  подставляется, но его можно поменять (в десктопе для этого есть специальный режим
  «кликни по окну»).
- **Панель деталей** справа: выпуски в выбранном месте (все и текущей кампании), действия
  над ними через общее меню «⋯». Грузится при выборе места, а не после каждой постановки.
- **Навигация по периоду** — стрелки и выбор даты; у комбо — переключатель неделя/месяц.
- **Итоги кампании/акции** — из `ActionTotal` результата, без отдельной загрузки акции.
- Всё, что ходит в базу, — под `BusyService.RunAsync`; клики во время запроса Blazor ставит
  в очередь.

## 6. Что понадобится в SQL

Минимально и без смены контрактов, которыми пользуется десктоп:

1. `TariffWindowWithRange`: убрать двойной тяжёлый джойн (разделы 7 и 9, `docs/tariffgrid.md`
   П-2а) — полезно и десктопу, ~−0,5 с на каждый клик веера.
2. `TariffWindowWithRange`: необязательный параметр «один слот» для точечного обновления
   (десктоп его не передаёт — поведение не меняется).
3. Выпуски акции по `@campaignIDs` одним запросом — вместо `BuildAddedIssuesTable`
   (`GetCampaignById` + все выпуски кампании за весь период на каждую кампанию).
4. Имя фирмы-владельца в `ProgramIssues` — вместо N+1 в спонсорской сетке.

Процедур массовой записи (TVP) не заводим, пока цикл по IUD в одной транзакции быстрый.

## 7. Открытые вопросы (сводно)

Всё, что ждёт решения владельца, — в одном месте. Решённое переносится в «Ход работ» (§9)
с датой. Нумерация сквозная, чтобы на вопрос можно было сослаться.

### Размещение рекламы (сетки кампаний) — решаются перед последним этапом

1. **Одна страница размещения для линейной кампании и веера?** Веер — это «линейная для
   нескольких станций сразу». Предложение: один экран размещения акции; выбрана одна
   станция → сетка окон (`WindowsSource`), несколько → получасовые слоты (`RangeSource`).
   Уходит отдельный мастер «Массовое редактирование» с его копией тулбара.
2. **Модульную кампанию показывать сеткой «модуль × день»** (как комбо), а не сеткой окон?
   Модуль всё равно ставится на весь день целиком (в десктопе клик по неполной колонке ничего
   не делает, `IsFullColumn`), а в ячейке комбо уже есть остаток в самом заполненном окне
   модуля. Тогда модульная, пакетная и комбо — один источник `ModuleDaySource`.
3. **Выделение нескольких мест.** Правило веба «групповой выбор только чекбоксами» (2026-09-22)
   придумано для списков. В матрице чекбокс в каждой ячейке съест место под текст.
   Предложение: для матрицы — выделение прямоугольником (нажал–протянул) и Shift-клик,
   с явной панелью «выделено N мест: поставить / снять / перенести».
4. **Original или actual.** Сейчас отметка «мои выпуски» и счётчики идут по окну, куда выпуск
   ставили (`originalWindowID`), а список выпусков окна и занятость — по окну, где он реально
   выйдет (`actualWindowID`); у веера — ещё и вперемешку (`docs/tariffgrid.md` §5).
   Предложение: в вебе везде показывать **фактическое** окно (`actualWindowID`), это то,
   что прозвучит в эфире. Затрагивает 1205 выпусков на dev.
5. **Номера роликов и значки Н/Д** в ячейках веера — переносим в первой версии или позже?
6. **Переводить ли десктоп на те же источники из ядра.** Плюс: одна логика размещения на два
   клиента, заодно уходят П-1…П-8. Минус: десктоп придётся перепроверять на всех типах
   кампаний. Альтернатива — чинить в десктопе только П-1, П-2а, П-4, П-5 (малые правки).
7. **Отмена последнего шаблона** — нужна ли в вебе? Если да — через `CreatedIssueIds`,
   захваченные при создании.
8. **Что не переносить** — шесть предложений §5 (раскладка по `broadcastStart`, режим грантора,
   всплывающие «нет окон», режим шаблона «кликни по окну», перетаскивание → «Перенести в…»,
   управление окнами вне сетки размещения). Ни одно не подтверждено; п. 6 де-факто принят —
   генерация окон и трафик идут отдельными экранами.

### Управление окнами (генерация — сделано, трафик — в работе)

9. **Операции с окнами в меню узла прайс-листа.** Сейчас «Сгенерировать окна» и др. работают с
   вкладки «Рекламные окна», а в меню узла прайс-листа дерева «Рекламные тарифы» они серые —
   как и в десктопном дереве тарифов: `MassmediaPricelist.IsActionEnabled` разрешает их

   эти пункты тоже станут доступны в дереве тарифов.

    не перечитывается после одиночного клика). Проверить руками.

## 8. Этапы

Каждый этап проверяется сверкой вызовов процедур с эталоном, снятым в десктопе на тех же
данных (`web-migration.md` §7 п.7 — автотестов нет).

| # | Что | Готово, когда |
|---|---|---|

## 9. Ход работ

**Генерация рекламных окон — перенесена (23.09.2026).** Первым взят этап 6: без денег и
пересчёта, но строит то, что нужно размещению, — матрицу недели, чтение окон той же
`TariffWindowRetrieve`, меню действий над окном, долгие операции с прогрессом.

Решения владельца:

- отдельного экрана нет: у прайс-листа в дереве «Рекламные тарифы» вкладки «Тарифы |
  Рекламные окна»; пункт меню `miTariffWindow` открывает то же дерево сразу на окнах
  (`BrowserRoute.OpenWindowsTab`);
- метка «не как в тарифе» у окон с точечными правками (`docs/business-logic.md`, «Тариф и
  рекламное окно»).

Что сделано:

| Где | Что |
|---|---|
| ядро `TariffWindowWeek` | неделя окон одним `TariffWindowRetrieve` + список тарифов для метки; объект окна из строки; «Изменить цену» (паспорт `ChangeTariffWindowsPrice`, `TariffWindowChangePrice`) |
| ядро `PricelistWindows` | генерация и удаление сгенерированных окон неделями, запрет внесения и пометка «по шаблону» (паспорт `TariffWindowsStatusChange`), отчёт о заблокированных окнах |
| веб `TariffWindowsView` | сетка недели, навигация, недоступные/помеченные окна, метка, карточка окна (двойной клик, правая кнопка), «⋯» у строки времени, кнопка «Операции с окнами» по метаданным прайс-листа |
| веб, общее | `ProgressDialog` (прогресс + «Остановить» между порциями), `PeriodDialog` (интервал дат), диалог без кнопки «Сохранить»; `Passport` учитывает `disabled`/`locked` из XML |

Отличия от десктопа и почему:

- генерация и удаление — неделями без перекрытий: десктоп удалял по дню, с перекрытием
  границ, и интервал из одного дня не обрабатывал вовсе. Удаление года — 53 вызова вместо
  365 (на проверке ~1 с);
- нет кнопки «Удалить окно»: сгенерированное окно `TariffWindowIUD` удалить не даёт
  (`TariffWindowDeleteAttempt`), других окон сетка не показывает — в десктопе кнопка всегда
  кончается ошибкой;
- открывается на текущей неделе; показаны недоступные/помеченные окна и число окон за день;
- интервалы проверяются: внутри срока прайс-листа, хотя бы один день недели;
- операции с окнами — на вкладке, а в меню узла прайс-листа они серые, как в десктопном дереве
  тарифов: `MassmediaPricelist.IsActionEnabled` разрешает их только при дочерней сущности
  «Рекламное окно». Открыть их и в меню узла — правка ядра, задевает десктоп (решение владельца).

Найдено по дороге: веб-карточка не читала `disabled="true"` из XML (7 карточек, 5 именованных
форм, 4 фильтра) — поля, которые десктоп блокирует, в вебе редактировались; у окна так можно
было поменять цену. Исправлено; следующий шаг — показывать такие поля текстом, а не серым вводом.

## 10. Параллельно в десктопе (по решению владельца)

Малые правки производительности из `docs/tariffgrid.md` §8, которые не мешают вебу и дают
выигрыш сразу:
