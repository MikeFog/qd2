## Решения

- Языки: **только `ru` (исходный) и `es`**. Больше не закладываем.
- Многоязычность — **только в вебе**. Десктоп остаётся русским и не должен
  заметить изменений.
- Установка локальная: одно агентство — один язык. Язык всё равно хранится
  на пользователя (настройка → умолчание установки → `ru`), это ничего не стоит.
- **Справочники-данные не переводим**: тип ролика, тип кампании, типы оплаты,
  типы блоков, месяцы, `ReportType` и т. п. в испанской установке просто
  заполняются по-испански. Переводится только то, что поставляется вместе с
  системой: метаданные (`i*`) и код.
- Носителя для вычитки нет: черновой перевод делает Claude, вычитка — потом.
- Наработка `iMenu.name_es` (колонка на язык) как схема **отвергнута**: не
  масштабируется на ~15 таблиц и не покрывает XML паспортов/фильтров.
  75 готовых переводов переносятся в новое хранилище. Качество требует
  правки: нет диакритики («campanas» = «колокола», нужно «campañas»).

## Архитектура

### 1. Язык и культура

- Язык пользователя: `UserSetting` `Language` → `App.config` `Language`
  (умолчание установки) → `ru`.
- Язык живёт в сеансе (`UserSession.Language`), а не в `CurrentUICulture`:
  смена языка без перезагрузки (перезагрузка разлогинивает).
- Формат чисел/дат и **валюта** — настройка установки (`App.config`), а не
  языка пользователя. Сейчас в вебе культура не задана вовсе: `ToString("C")`,
  `TryParse` без культуры и «₽» в `GridExcelExport.cs:421` зависят от ОС
  сервера — это чинится первым.

### 2. Метаданные БД — перевод по исходному тексту

Таблица `iTranslation(lang, context, source NVARCHAR(4000), text NVARCHAR(4000))`,
PK по SHA-256 исходника.
Ключ — русский оригинал (gettext-подход): «Обновить» ×84 и «Радиостанция» ×34
переводятся один раз, XML паспортов не копируется. Для `iMessage` ключ — тоже
текст сообщения. Правка русского текста в метаданных
не ломает UI: показывается оригинал.

**Переводить при выводе, а не при загрузке.** Кэши `EntityManager` и
`MessageAccessor` статические и общие для всех пользователей веба —
закэшированные объекты не трогаем. Точки вывода в вебе: `ObjectList`,
`ObjectSelector`, `ActionMenuHost`/`ObjectActions`, `PassportSchema`
(caption), `FilterPanel`, `MenuService`, `ErrorPresenter`, заголовки
`Journal`/`Browser`/`PassportDialog`.

`MessageAccessor.GetMessage` сам подставляет параметры в шаблон, поэтому ему
шаблон проходит через `Tr.T` до `String.Format` (в десктопе переводчика нет —
текст прежний).

Меню: `MenuService` переводит `name` по `iTranslation`; процедуры
`UserMenuItems`/`UserAdditionalMenus` не трогаем (десктоп и Protector
передают `ru`). `name_es` удаляется после переноса данных.

### 3. Код

Пересмотрено 24.09.2026 (вместо resx с символьными ключами): тот же подход
«ключ = русский текст», что и для метаданных. Литерал оборачивается в
`Tr.T("Сохранить")` / `Tr.Format("… {0} …", x)` — `FogSoft.WinForm/Classes/Tr.cs`,
собирается и в десктопе, и в `FogSoft.Core`. Десктоп переводчик не задаёт —
`Tr.T` возвращает исходный текст; веб подставляет `WebTranslator`. Плюсы: код
остаётся читаемым, ключи придумывать не нужно, в ядре литерал не переезжает в
resx, переводы всех видов — в одном хранилище (`iTranslation`).
- Дни недели (`WindowWeekGrid.razor:186`, `ChangeWindowsForm.razor:118`,
  `DateTimeUtils.cs:9-25`) → `DateTimeFormatInfo` культуры.

### 4. Тексты, собираемые SQL

По мере переноса экранов, не разом: необязательный `@languageCode = 'ru'`
(старые вызовы не меняются) + функция перевода по той же `iTranslation`.

### 5. Инструменты

- Псевдоязык (`[·Сохранить·]`) в Development — непереведённое видно глазами.
- Лог непереведённых строк (один раз на строку).
- Выгрузка всех исходных строк (БД + resx) → перевод → скрипт загрузки.
- Правило в `AI_AGENT_PLAYBOOK`: в `FogSoft.Web` без кириллических литералов.

## Unicode-данные: VARCHAR → NVARCHAR

Не про перевод интерфейса, а про то, чтобы испанская установка вообще могла
хранить свои данные. Сопоставление базы `Cyrillic_General_CI_AS`: в `VARCHAR`
кодовая страница 1251, á/é/ñ/¿ молча превращаются в `?`.

Оставляем одно сопоставление для всех установок (метаданные — русский
исходник, он же ключ перевода); человеческий текст переводим в `NVARCHAR`.

- Область: ~35 колонок с человеческим текстом — `Firm`, `HeadCompany`,
  `AdvertType`, `Agency`, `MassMedia`, `MassmediaGroup`, `Announcement.subject`,
  `BlockType`, `ReportType`, `iMonthName`, `ReportPartText` (`text` →
  `NVARCHAR(MAX)`), `iMessageToSubtitute.message`, `Tariff.suffix`.
  Технические коды (`codeName`, `inn`, `bik`, `phone`, `email`, имена
  процедур/таблиц) не трогаем.
- **UDT `doubleString`** (`VARCHAR(256)`, 23 колонки, в т. ч. `Firm.name`):
  по имени типа `FieldTypeResolver` рисует многострочное поле паспорта
  (`PageFieldTextDoubleString`, веб — `Passport.razor:1062`). Нельзя просто
  сменить колонки на `NVARCHAR(256)` — поля станут однострочными. Путь:
  `CREATE TYPE doubleStringN FROM NVARCHAR(256)` → перевести колонки →
  `DROP TYPE doubleString` → `sp_rename 'doubleStringN', 'doubleString',
  'USERDATATYPE'`. Код не меняется.
- Главная работа — не таблицы, а **путь данных**: 204 `VARCHAR`-параметра в
  126 процедурах плюс локальные переменные и `#temp`. Пропущенное место не
  падает, а тихо портит символы. C# не страдает: типы параметров выводятся из
  процедур (`GetSpParameterSet`).
- Проверка: прогнать `'Ñandú Café ¿?'` через каждую IUD-процедуру затронутых
  сущностей и прочитать обратно через процедуры чтения.
- Таблицы маленькие (максимум `Firm`, 8,5 тыс. строк), переписывание строк —
  секунды. Индексы/умолчания на затронутых колонках — единицы
  (`MassmediaGroup.name`), пересоздаются в скрипте.
- Экспорт DJin/VideoDJ пишет в `windows-1251` (`DJinParam.cs:24`,
  `VideoDJParam.cs:13`) — для испанской установки отдельный вопрос.
- Crystal Reports (5 живых) — проверить после перехода.
