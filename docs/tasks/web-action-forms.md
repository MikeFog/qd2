## 1. Что показало обследование

- Создают и правят акцию **пять форм** (вместе с сетками и шаблонами — около 10,6 тыс. строк): карточка `ActionForm`,
  «суперформа» `CampaignForm` в пяти режимах, веер `EditIssuesForm` (наследник
  `CampaignForm`), комбо `ComboModulePlacementForm` (≈40% — копии из двух предыдущих) и
  `CampaignNewForm`. Плюс **три разных способа создать акцию**, каждый со своими проверками
  и своим «мусором» (`action-forms.md` §2.2).
- Работают с акцией, а не с кампанией: у **79%** акций с линейными кампаниями станций две и
  больше (в среднем 3,4 кампании на акцию). Веер — один из главных инструментов: за две недели
  14,4 тыс. добавлений через него (клики, выделенные окна, шаблоны) у 10 человек; кликов в
  сетке одной кампании — 15,2 тыс. у 17 человек.
- Типы распределены неравномерно: только линейные — 79% акций, только модульные — 15%,
  линейные + модульные — 2,5%, спонсорские — 2%, пакетные — 1%.
- В вебе сегодня: журнал акций с почти всеми операциями над акцией и кампанией; «Редактировать»
  у акции и кампаний — серое «скоро»; **создать акцию или кампанию нельзя**; есть матрица окон
  `WindowWeekGrid` (генерация окон, трафик), но для размещения она не годится: признаков
  «моя / фирма / частично» в ней нет; кода размещения в ядре нет — транзакции живут в
  `Client/Controls` и `Client/Forms`.

## 2. Была ли суперформа ошибкой

**Да — но ошибка не в том, что экран один, а в трёх вещах.**

1. **Единица работы — одна кампания, то есть одна станция.** Пользователь думает акцией:
   цена, пакетная скидка, активация, оплата — всё на уровне акции. Веер и комбо появились
   как обходы именно этого ограничения: «та же форма, но сразу по нескольким станциям».
2. **Тип решается внутри формы.** Около 145 мест в одном файле зависят от типа; признаки
   смешивают тип кампании и тип сетки; около половины кода работает только для линейной;
   у модульной до выбора модуля кнопки грузят сетку, которую следующий шаг очищает; у
   программ спонсорской посреди размещения — действия справочника. Новый тип сетки — обход
   всех мест вручную, компилятор не поможет.
3. **Повторное использование — наследованием и копированием.** Веер держится на заглушках
   (`NotImplementedException`, фиктивный прайс-лист) и 12 virtual-методах базовой формы;
   комбо скопировал то, что не смог унаследовать.

**Что было верным и что сохраняем:** единое рабочее место — ролики слева, сетка в центре,
выпуски выбранного места рядом, итоги перед глазами; одинаковый смысл позиции, предмета
рекламы, «учитывать макеты» во всех сетках. Пользователь переходит от линейной к модульной,
не переучиваясь. В вебе это сохраняется **набором общих компонентов**, а не одной формой с
проверками типа.

Ошибка того же рода — **три способа создать акцию** (ленивое сохранение в карточке, SQL-процедура
мимо `CampaignIUD` в веере, ленивое создание в комбо) с разными проверками и разным
поведением при ошибке (Д-2…Д-5).

## 3. Предложение

### 3.1 Единица работы — акция: страница акции

Одна страница на акцию, `/action/{id}`: шапка, вкладка «Кампании», вкладки размещения.
Десктопный «пинг-понг» модальных окон (карточка → форма кампании → закрыть → перечитать
карточку) исчезает: всё на одной странице, итоги в шапке обновляются после каждой операции.

```
┌───────────────────────────────────────────────────────────────────────────────────────┐
│ Акция 186593 · «Фирма» · макет · 01.10–31.10.2026     по тарифам 120 000 · ×0,85 ·    │
│ создатель: …                                            итого 102 000          [ ⋯ ]  │
├───────────────────────────────────────────────────────────────────────────────────────┤
│  Кампании (4)  │  Окна  │  Модули  │  Спонсорство                                     │
├────────────────────┬─────────────────────────────────────────────┬────────────────────┤
│ Станции            │ ‹ 06.10–12.10 ›    Ставить: ролик 2, первым │ Пн 06.10, 08:15    │
│ ☑ Станция А, безнал│        Пн     Вт     Ср    …                │ выпуски в месте    │
│ ☑ Станция Б, безнал│ 08:00  02:30  01:10  …                      │ [⋯] по строке      │
│ Ролики фирмы       │ 08:15  00:45  …                             │                    │
│  1 «Осень» 30″     │                                             │                    │
│  2 «Скидки» 15″    │ Выделено 3: Поставить · Снять · Заменить…   │                    │
└────────────────────┴─────────────────────────────────────────────┴────────────────────┘
```

- **Шапка:** фирма, создатель, состояние (макет / подтверждена), период, цены.
  Меню «⋯» — существующее меню акции из журнала (`ObjectActions`): активация, пересчёт,
  документы, медиаплан, смена фирмы и т.д. — **без нового кода**.
- **«Кампании»:** список кампаний (сущность 78) с чекбоксами; меню строки — уже
  перенесённые действия кампании (тип оплаты, агентство, медиаплан, эфирная справка) плюс
  недостающие: «Удалить», «Установить менеджерскую скидку». На тулбаре вкладки — «Добавить
  рекламные кампании» и «Установить цену акции».
- **Вкладки размещения** показываются только для тех видов, что есть в акции; добавили
  кампании нового вида — появилась вкладка.
- **Входы:** «Редактировать» у акции в журнале → страница на «Кампаниях»; «Редактировать» у
  кампании (и у частей спонсорской) → нужная вкладка с отмеченной кампанией; мастер создания
  (§3.7) → вкладка размещения.

### 3.2 Вкладки — по виду места, а не по типу кампании

Сетку определяет не тип кампании, а то, **что лежит в ячейке**: окно, модуль-день,
программа-день, пакет-день (`web-tariffgrid.md` §1).

| Вкладка | Кампании | Ячейка | Источник (ядро) | Заменяет в десктопе |
|---|---|---|---|---|
| **Окна** | линейные | окно (одна станция) или получас (несколько) | `WindowsSource` / `RangeSource` | `CampaignForm` (Л) + веер |
| **Модули** | модульные | модуль × день | `ModuleDaySource` | `CampaignForm` (М) + комбо, все три режима |
| **Спонсорство** | спонсорские | программа × день; бонусные ролики — окно | `ProgramSource` + `WindowsSource` | `CampaignForm` (С-п и С-р) |
| **Пакеты** | пакетная | пакет × день | `PackDaySource` | `CampaignForm` (П) |

Все вкладки собраны из одних компонентов (§3.8). Ни одной проверки «какой это тип» в
разметке страницы: вкладка знает свой источник, источник — свои процедуры.

### 3.3 «Окна»: одна станция — сетка окон, несколько — веер

Слева — линейные кампании акции галочками (станция, тип оплаты, агентство — как чек-лист веера).

- **Отмечена одна** → точная сетка окон станции (`WindowsSource`): время × дни, остаток окна,
  прайм, недоступные и помеченные окна, бирюзовые «фирма здесь».
- **Отмечено несколько** → получасовые слоты по всем отмеченным (`RangeSource`, логика
  веера): синие / красные / бирюзовые / оранжевые, номера роликов и Н/Д, «Удалить дубли»,
  «Добавить до полного пересечения». Это свежие доработки по заказу (18.09.2026) — переносим.

Отдельной формы «Массовое редактирование» и мастера с отдельным тулбаром нет. Отличие от
десктопного веера: при одной отмеченной станции видна настоящая сетка окон, а не получасовой
агрегат.

### 3.4 «Модули»: сетка «модуль × день», комбо-модуль — набор строк

Строки — модули, колонки — дни недели или месяца, ячейка — минимальный остаток по окнам
модуля за день (как в комбо). Окна модуля и остаток каждого — в панели выбранного места.
Клик ставит модуль на весь день; в десктопе модуль и так ставится только целиком.

Какие строки видны:
- модули, уже размещённые в модульных кампаниях акции (десктопный комбо-режим 2);
- плюс добавленные пользователем кнопкой «Показать модули…»: модули станции **или весь
  состав комбо-модуля** (режимы 1 и 3).

Комбо-модуль и сейчас по сути «сохранённый набор строк»: связи «акция ← комбо-модуль» в базе
нет. Отдельная форма для него не нужна. Постановка в модуль станции, где модульной кампании
ещё нет, создаёт кампанию в той же транзакции — как сейчас в комбо (тип оплаты и агентство
спрашиваются один раз при «Показать модули…»).

### 3.5 «Спонсорство»

Программы (тариф программы × день, ячейка-галочка, чужая фирма — текстом) и бонусные ролики
этой же кампании (та же сетка окон, что на вкладке «Окна», для одной станции) с остатком
бонусных секунд в шапке вкладки. В десктопе это две разные формы с двумя кнопками в карточке.
Все 164 спонсорские кампании года имеют программы, 148 — ещё и ролики: части используются
вместе.

### 3.6 «Пакеты»

Пакет × день, как модули; панель места — состав пакета (`GetPackModuleIssueDetails`).
38 акций в год — делается последним.

### 3.7 Создание акции: один мастер

Маршрут `/action/new`. Как сделано (этап 3, решения 07.10.2026 — §8):

1. **Фирма** — при входе сразу окно «Фирма-заказчик» (`ObjectSelector`, тот же набор и выбор, что
   у десктопного `Firm.SelectFirm` и «Сменить фирму-заказчика»).
2. **Кампании** — на странице, той же формой, что «Добавить рекламные кампании» на странице акции
   (`CampaignAddForm`): тип рекламной кампании, тип оплаты один на всё, группа, радиостанции
   галочками; агентство единственное — подставлено, несколько — выбор под таблицей, нет —
   радиостанция пропускается. Отдельного шага «Оплата и агентства» с таблицей «станция → агентство»
   нет: эту таблицу владелец отверг 05.10.2026 (§10, этап 1).

Запись — `ActionIUD` + `CampaignIUD` на каждую станцию **в одной транзакции** (исправляет
Д-2…Д-4), затем страница акции на нужной вкладке. Модули по комбо-модулю — кампании лениво,
при первой постановке (§3.4) — вместе с вкладкой «Модули» (этап 6).

Пункты меню остаются со своими правами и ведут в этот мастер: «Внести макет рекламной акции»
(`miCreateUnconfirmedAction`) и «Веерное размещение» (`miMasterCreateActions`) — с этапа 3,
«Размещение комбо-модулями» (`miComboModulePlacement`) — с этапа 6. Метаданные меню не меняются.
Подставленной фирмы «из журнала или карточки фирмы» нет: в десктопе такого входа нет, у фирмы нет
подходящего пункта.

### 3.9 Правила

- **Одно действие пользователя — одна транзакция и один `ActionRecalculate`**: клик, «поставить
  в выделенные», шаблон, перенос, удаление. В десктопе это нарушено в нескольких местах (П-1, Д-16).
- **Точечное обновление:** операция возвращает затронутые места и итоги акции; полная
  перезагрузка — только при смене периода, станций или фильтров.
- **Детали — по требованию:** панель места и список выпусков не перечитываются на каждый клик
  расстановки (П-7).
- **Запись — только существующими IUD-процедурами**: `IssueIUD`, `ModuleIssueIUD`,
  `ProgramIssueIUD`, `PackModuleIssueID`, `AddRangeIssues`, `MasterIssueDelete`, `CampaignIUD`,
  `ActionIUD`. Путь `CreateActionWithRange` в веб не берём.
- **Права проверяет фасад, а не кнопка.** Прямые вызовы процедур мимо `DataAccessor.DoAction`
  метаданные-права обходят (`IssueIUD` у «Выпуска» правами не ограничен, `AddRangeIssues` и
  `MasterIssueDelete` идут по имени). Поэтому фасад перед записью проверяет «Редактировать» у
  сущности кампании (91/92/171), `EditIssues` у частей спонсорской (86/87) и
  `CheckLoggedUserRight` у акции. Страница, открытая по прямой ссылке, проверяет то же:
  `MenuAccess` знает только пункты меню.
- **Отмена** — одна «Отменить последнее» для любой постановки: созданные выпуски
  запоминаются в момент создания, а не ищутся потом.

## 4. Десктоп → веб: что куда

| Десктоп | Веб |
|---|---|
| **ActionForm** — шапка с ценами | шапка страницы, обновляется после каждой операции |
| грид кампаний | вкладка «Кампании» |
| Добавить рекламную кампанию | «Добавить рекламные кампании» (шаги 2–3 мастера) |
| Удалить рекламную кампанию (одну, три пути с разным поведением, Д-8) | чекбоксы → «Удалить (N)», один вопрос, один пересчёт |
| Редактировать размещение роликов / Выходы спонсорских программ | переход на вкладку с отмеченной кампанией |
| Веерное редактирование | «Окна», отметить несколько станций |
| Размещение модулями (вопрос Да/Нет/Отмена) | «Модули» → «Показать модули…» |
| Менеджерская скидка | «Установить менеджерскую скидку» у кампании; без «разрешающего» (решение 21.08.2026) |
| Цена рекламной акции (только при выделенной кампании) | «Установить цену акции» уровня акции |
| Галочки печати + «Ok» | не нужны: документы и медиаплан — в меню акции |
| **CampaignForm** — ролики, пустышка, прослушать | `RollerBrush` |
| Старт / режим шаблона | кисть вкл/выкл; шаблон — диалог, время в нём полем |
| Позиция, предмет рекламы | кисть: фильтр + жирное «подходит» |
| Учитывать макеты, подсветка, прайм, недоступные, номера роликов | переключатели вида, легенда на экране |
| Шаблоны 1, 2, 3 | один диалог «Шаблон» с тремя режимами |
| Отмена шаблона | «Отменить последнее» для любой постановки |
| Insert / Del / Ctrl+R по выделенным окнам | выделение + кнопки «Разместить ролик», «Удалить выпуски», «Заменить ролики» (слова десктопа) |
| Перетаскивание | «Перенести в окно»: выбор приёмника как в трафике, запись — как у перетаскивания (удалить + добавить) |
| Выходы в окне / этой кампании | `PlaceDetails` |

## 6. Ядро и SQL

**Что переезжает в ядро** — §3.8. Классы `Campaign`, `Issue`, окна остаются `internal`; веб видит
только фасады. Транзакция ядра в вебе работает (`AsyncLocal` в `DataAccessor`), образец —
`TrafficManagement.Apply`.

**SQL** — минимально, без смены контрактов, которыми пользуется десктоп:

1. `TariffWindowWithRange`: убрать двойной тяжёлый джойн (П-2а) и добавить необязательный
   параметр «один слот» для точечного обновления (`web-tariffgrid.md` §6, п. 1–2).
2. Выпуски акции по `@campaignIDs` одним запросом — вместо `BuildAddedIssuesTable` (N+1).
3. `ProgramIssues`: имя фирмы-владельца (вместо N+1) и параметр тарифа, который сейчас
   теряется (Д-13).
4. Строки «Модулей» по произвольному набору станций или модулей: сейчас
   `ComboModuleFreeTimeRetrieve` умеет только «комбо-модуль» или «акция».
5. По желанию — `tariffPrice` OUTPUT-параметром `ActionRecalculate`, чтобы шапка не перечитывала
   акцию после каждой операции (П-10).

Новых процедур записи (TVP) не заводим, пока цикл IUD в одной транзакции укладывается во время.

## 9. Параллельно в десктопе

Архитектуру десктопных форм не трогаем — их заменит веб. Чинить стоит то, что портит данные
или пугает пользователя, пока десктоп живёт (номера — `action-forms.md` §10):

| Приоритет | Дефекты | Почему |
|---|---|---|
| высокий | Д-4 (дубли кампаний в «Добавить кампанию»), Д-5 («фантомная» акция комбо), Д-7 (комбо ставит не в ту кампанию) — исправлены в десктопе 03–04.10.2026; Д-9 («Разделить кампании» сбрасывает скидку) — не исправляем, см. `docs/action-forms.md` §10 | неверные данные или цена |
| средний | Д-1 (режим шаблона 1 не выключается), Д-3 (NRE мастера веера), Д-6 (ошибка после удаления в комбо), Д-8 (суммы карточки после Del), Д-10 (мёртвый тулбар веера) | ошибки на экране, данные верны |
| по ходу | Д-11…Д-16, мёртвый код (`action-forms.md` §11) | при следующей работе с формой |

Всё найдено чтением кода (Д-1 и Д-2 перепроверены, остальное — из отчётов обследования):
перед правкой воспроизвести.

Упрощения десктопа, которые облегчают веб (правило «Требование №1 изменено»): удалить мёртвое
(импорт Grammofon/MediaPlus, режим грантора — [GRANT-01]), чтобы не разбирать его при переносе;

### Этап 4б, часть 5 — веер: панель окна и перенос выпусков (14.10.2026)

Сделано: справа от сетки — панель окна (как у сетки одной кампании) и действие «Перенести в окно» вместо десктопного перетаскивания (решение
плана, `web-tariffgrid.md` §5 п. 5). Щелчок по окну (без «Режима добавления») выделяет его, как раньше, и показывает панель последнего
выбранного окна: группы «ролик + позиция» с числом выпусков и «N из M» — у скольких отмеченных кампаний группа стоит (подсказка — какие).
Выпуски читаются из уже загруженного вместе с неделей `RangeSlotIssues` (у цветных окон они есть всегда, у остальных — при «Номерах
роликов», иначе одним вызовом по этому окну).

- **Перенос**: отметить группы в панели → «Перенести в окно» → полоса над сеткой («Перенос выпусков (N) из окна …», «Отмена», Esc; недели
  листать можно, окно-источник обведено, остальные окна — приёмники) → щелчок по окну-приёмнику → вопрос десктопа «Перенести выпуск в окно
  '…' в тех кампаниях, где он есть?» / «Перенести выпуски (N шт.) в окно '…' …?»; если в окне-приёмнике на станциях переносимых кампаний уже
  есть выпуск этой фирмы (из любой акции) — первой строкой предупреждение «В этом окне уже есть выпуск фирмы «…» (акция подтверждена / ещё
  не подтверждена)» (`RangeSlotFirmConflict`, только сигнал).
- **Запись** — как десктопное `MoveRangeIssuesToSlot`, всё или ничего одной транзакцией: удаляются все группы окна-источника
  (`MasterIssueDelete` по кампаниям группы), затем те же ролики с теми же позициями в тех же кампаниях ставятся в окно-приёмник
  (`AddRangeIssues`), один пересчёт. Группа переезжает в том составе кампаний, в котором стояла (иначе перенос размножил бы выпуск на
  остальные). Отказ любой станции (позиция занята, нет места, прошлое…) откатывает весь перенос и показывается над сеткой; режим переноса
  остаётся — можно выбрать другое окно.
- **Отличия от десктопа в лучшую сторону**: десктопный путь по группам теряет дубли (за вызов снимается и ставится по одному выпуску на
  кампанию) — здесь копии переносятся все (проходы по числу копий); состав окна-источника перечитывается в транзакции, изменившаяся группа
  отменяет перенос (удалённый между выбором и щелчком выпуск не воскреснет, как в переносе сетки одной кампании).
