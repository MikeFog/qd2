# Задача: реклама в период политической агитации

## Статус

Этапы 1–2 реализованы в ветке `feature/political-agitation` и проверены на dev-базе
(см. раздел 8). Этапы 3+ — не начаты. Документ фиксирует требования из устной встречи
(Телемост, 24.07.2026, две записи ~18 и ~21 мин, локально расшифровано
faster-whisper/medium/ru) и их сверку с текущим кодом. Возможны неточности
распознавания речи (особенно цифры/термины) — сверено с таймкодами на случай
пересмотра записи.

Источники (не в репозитории, локальные файлы на момент написания):
`Политика/Встреча в Телемосте 24.07.26 07-19-39 — запись.webm` (часть 1),
`Политика/Встреча в Телемосте 24.07.26 07-42-00 — запись.webm` (часть 2).

**Срок:** период агитации начинается «в начале августа» (точная дата не
названа на встрече, идут переговоры со станциями) — часть 2, ~1090–1116с.

## 1. Проблема

Закон о выборах требует, чтобы ролик политической агитации на радио был
обязательно обрамлён идентификацией СМИ: локальный ролик перед агитацией,
федеральный — после (независимо от уже существующей практики обрамления для
соблюдения лицензионной квоты местного вещания). Сейчас это делается только
вручную, точечно, силами администратора. Нужно, чтобы система сама следила за
этим правилом при появлении ролика политической агитации в размещении.

## 2. Что уже есть в коде (переиспользуем)

- Классификация ролика — **не `AdvertType`** (это «предмет рекламы» фирмы,
  другая сущность: `ArtvisDB/dbo/Tables/AdvertType.sql`), а
  `Roller.rolActionTypeID` → `ArtvisDB/dbo/Tables/iRollerActionType.sql`.
  Значения **4** и **5** уже означают именно то, о чём речь на встрече: тип 4 —
  рамочный, первым в окне; тип 5 — рамочный, последним. Проверка «не более
  одного 4 и одного 5 на `TariffWindow`» уже реализована в
  `ArtvisDB/dbo/Stored Procedures/hlp_IssueVerify.sql` (вызывается из
  `IssueIUD.sql`, `ModuleIssueIUD.sql`, `PackModuleIssueID.sql`).
- Право «уходить в минус» по вместимости окна уже существует как обычное право
  по действиям: `ArtvisDB/dbo/Functions/fn_IsRightForMinus.sql` +
  `ArtvisDB/dbo/Stored Procedures/hlp_GetMainUserCredentials.sql`
  (`iEntityAction`, name = `RightForMinus`). Это ровно то, что предложено на
  встрече включать для акций с агитацией — не нужен новый флаг.
- Спецпозиционирование централизовано: `ArtvisDB/dbo/Functions/fn_IsPositionOk.sql`,
  проверки в `hlp_IssueVerify.sql`, enum `Client/Classes/InternalConstants.cs`
  (`RollerPositions`), кнопка `tbbPosition` в `Client/Forms/CampaignForm.cs`
  (уже отключается для тарифов с малой `maxCapacity` — готовый пример, куда
  добавить ещё одно условие).
- `ActionActivate` (`ArtvisDB/dbo/Stored Procedures/ActionActivate.sql`) — точка
  строгой проверки бизнес-правил (см. `docs/business-logic.md`, «Черновик и
  активация») — совпадает с тем, что на встрече называют правильным моментом
  для авто-вставки («по идее это нужно делать в момент активации», часть 2,
  ~171–184с): в макете строгие правила не действуют, значит и авто-вставку
  раньше активации делать нельзя (может не влезть).
- Автоматической подстановки роликов 4/5 в коде сейчас **нет** — есть только
  закомментированный, никогда не включённый набросок в
  `Client/Classes/GridExport/DJinSerializer/DJinExportDocument.cs` (10.01.2026,
  поле `_issuesWithRolType4And5`). Писать эту часть придётся с нуля.

## 3. Что такое «блок» — решено

Блок = `TariffWindow` в ~99% случаев (подтверждено пользователем, 2026-07-24) —
разговорное «блок» и рекламное окно тождественны для подавляющего большинства
размещений. Значит вся новая логика (авто-вставка, проверка «уже обрамлено»,
запрет позиционирования, запрет смешения) в первую очередь работает на уровне
одного `TariffWindow`, как и существующая проверка типов 4/5 в
`hlp_IssueVerify.sql` — гипотеза предыдущей версии документа подтвердилась.

Оставшийся ~1% — несколько `TariffWindow` подряд, физически один непрерывный
кусок эфира, связанные через `windowNextId`/`windowPrevId` (self-FK,
`ArtvisDB/dbo/Tables/TariffWindow.sql:23-24`). Для этого случая **существующий
`hlp_IssueVerify.sql` не подходит как есть** — он проверяет «не более одного 4
и одного 5» строго на `@windowID`, не проходя по цепочке
`windowPrevId`/`windowNextId`. Если новую логику применить наивно (по одному
окну), для цепочки возможны два дефекта:
- дубли — в каждое окно цепочки вставится свой локальный/федеральный ролик
  вместо одной пары на всю цепочку;
- ложное «не обрамлено» — если в одном окне цепочки уже стоит тип 4, а в
  другом тип 5, per-window проверка в третьем окне цепочки их не увидит и
  вставит ещё одну пару поверх.

**Для этапов 3/5 нужна отдельная (пока не существующая в коде) функция обхода
цепочки**: по `@windowID` найти начало (идти по `windowPrevId`, пока не NULL)
и конец (идти по `windowNextId`, пока не NULL), и проверять/вставлять тип 4 в
первое окно цепочки, тип 5 — в последнее. Для 99% случаев (нет
`windowPrevId`/`windowNextId`) цепочка = само окно, поведение не отличается от
описанного в разделе 4.

## 4. Извлечённые требования (с таймкодами для проверки по записи)

1. Нужны 4 новых значения `rolActionTypeID`: кандидатский ролик «политическая
   агитация» (ставит менеджер), анонс «а теперь политическая агитация»
   (часть 2, ~125–136с: «добавится тип шестой и тип седьмой… какой-то ролик,
   а теперь политическая агитация») + два варианта рамочных роликов «для
   политики» (локальный / федеральный), отдельные от обычных 4/5 — специально,
   чтобы отличать авто-вставленное для политики от вручную поставленного для
   действующей практики соблюдения квоты вещания (часть 2, ~1006–1045с, идея
   «типа 44»). Авто-вставляемая обвязка — **три** ролика (часть 2, ~86–100с:
   «ставит три вот этих ролика… тогда получается будет 4 ролика»).
   Порядок в блоке (часть 1, ~43–70с; часть 2, ~244–254с): влёт → обычная
   коммерческая реклама → локальное СМИ → анонс агитации → ролики кандидатов →
   федеральное СМИ → аут.
2. Авто-вставка — только в момент `ActionActivate`, не в макете (часть 2,
   ~171–184с).
3. Логика вставки (часть 1, ~409–501с): если в окне уже есть ролики 4/5,
   поставленные вручную — их не трогать, добавить только анонс (и сам ролик
   агитации); если нет — система сама ставит локальный-для-политики и анонс
   перед агитацией и федеральный-для-политики после, не меняя физическую
   длительность окна (просто как обычные размещённые ролики — свободное время
   уменьшится само, часть 1, ~301–318с).
4. Вставляет «системный» пользователь, не реальный менеджер (часть 1,
   ~223–279с) — практическая причина: отличать при удалении, что можно чистить
   автоматически, и определять зону позиционирования для авто-роликов. Решили
   не заводить отдельный флаг «кто поставил», а использовать сам новый
   `rolActionTypeID` как маркер (см. п.1).
5. Запрет спецпозиционирования для ролика агитации — подтверждено юристом
   («Света») голосом прямо на встрече (часть 2, ~267–319с): «как встал, так и
   встал». Нужна проверка в `fn_IsPositionOk`/`hlp_IssueVerify` + отключение
   `tbbPosition` в UI при типе = агитация.
6. Запрет смешивания в одной акции: если в акции уже есть ролик агитации —
   нельзя добавить обычный, и наоборот (часть 2, ~698–806с). Причина —
   отдельная отчётность перед избиркомом по каждому кандидату, смешивание её
   ломает. Проверка нужна в обе стороны при добавлении ролика в акцию.
7. Переполнение при активации (часть 2, ~500–612с):
   - не влезает сам ролик агитации — обычное поведение (не активируется);
   - ролик влезает, а рамочные — нет — разрешить уход «в минус» именно для
     акций с агитацией (переиспользовать `RightForMinus`, включать контекстно);
   - UI («трафик») должен подсвечивать переполненные окна красным заранее, до
     формирования сетки вещания — конкретная форма/грид на встрече не названы,
     нужно уточнить у пользователя.
8. Удаление/деактивация (часть 2, ~916–1045с): если убираемый ролик агитации —
   последний в окне, авто-вставленные рамочные ролики удаляются вместе с ним;
   если в окне остался ещё один ролик агитации (от другой акции) — рамочные
   ролики не трогать. Различать по типу ролика (новый ID), не по флагу.
9. Гонка при активации нескольких акций в одно окно (часть 2, ~327–421с) —
   например, два разных кандидата размещают агитацию в одно окно и активируют
   в разном порядке. **Открыто** — участники сами сказали «надо подумать»,
   решения на встрече не нашли.
10. Медиапланы/распечатки: авто-вставленные ролики не должны попадать в
    печатные медиапланы клиента (часть 2, ~1117–1216с). Обсуждали вариант
    привязывать авто-ролики к отдельной служебной акции/фирме — **не
    финализировано** («вариант, кстати»).
11. Контекст, не задача на код: риск структурного превышения лицензионной
    квоты вещания в период агитации (часть 1, ~878–928с) — организационный /
    юридический риск.

| `ArtvisDB/dbo/Stored Procedures/ModuleIssueIUD.sql` | Тот же запрет смешения в ветке AddItem (по прецеденту `PositionErrorForTheSameAction`) |

Ключевые проектные решения:

- Запрет смешения — симметричный, по границе множества (6,7,44,55): тип 6 нельзя
  добавить в акцию с выпусками других типов, а типы вне (6,7,44,55) нельзя
  добавить в акцию, где есть тип 6. Типы 7/44/55 могут жить в агитационной акции
  (нужно для авто-вставки этапа 3) и не запрещены в обычных акциях (ручное
  обрамление — тема типов 4/5, поведение не менялось).
- Несколько роликов агитации в одном окне/одной акции допустимы (несколько
  кандидатов — подтверждено на встрече), уникальность в окне только у рамочных.
- Проверка смешения сделана в трёх IUD-процедурах, а не в `hlp_IssueVerify`,
  потому что в `hlp_IssueVerify` нет `@actionID`, а менять её контракт — трогать
  всех вызывающих. Прецедент такого размещения — `PositionErrorForTheSameAction`.
- Все выпуски (включая модульные/пакетные) пишутся в `Issue`, поэтому проверка
  единообразна во всех трёх процедурах: `Issue` → `Campaign.actionID` → `Roller.rolActionTypeID`.
- Импортные процедуры `CampaignImportGrammofon`/`CampaignImportMediaPlus` тоже
  вставляют в `Issue` напрямую — проверки туда не добавлялись (legacy-импорт,
  вне сценария агитации); при необходимости добавить позже.

Деплой: процедуры деплоить через sqlcmd **обязательно с флагом `-I`**
(`QUOTED_IDENTIFIER ON`) — без него UPDATE в `IssueIUD` падает на индексах.

### 7.1. Ролики обвязки в карточке радиостанции (24.07.2026)

Источник роликов обвязки для авто-вставки — карточка радиостанции: три
необязательные **ссылки на `Roller`** (lookup-списки роликов соответствующего
типа). C#-код не менялся вообще: форма паспорта строится динамически по XML из
`iEntity.passport`, сохранение идёт metadata-driven в `MassmediaIUD` (имя поля
XML = имя колонки view = имя параметра процедуры).

История решения (обе итерации 24.07.2026): сначала ссылки с lookup, затем по
отзыву с формы упрощение до текстовых полей («путь или название, как
DJin-пути»), затем возврат к ссылкам — авто-вставке этапа 3 нужны настоящие
`Roller` (для `Issue.rollerID` и длительности `Roller.duration`, занимающей
время окна). Из текстовой итерации сохранено UX-замечание: подзаголовок-label
на странице убран. Deploy-скрипт конвергентный: из любого прежнего состояния
(чистая база / первая lookup-редакция / текстовая редакция) приводит к
финальному — страница паспорта всегда вырезается по позиции и вставляется
заново.

Пустые выпадающие списки на форме означают, что роликов типов 44/7/55 ещё не
создано.

### 7.2. Этап 3: авто-вставка/снятие обвязки (24.07.2026)

Решения (согласованы с пользователем в диалоге):
- обвязка принадлежит окну, а не акции менеджера → гонка активаций исчезает;
- контекстный `RightForMinus` не нужен: вставку делает система, минус по
  времени окна допустим by design (сигнал трафику — красное окно);
- выпуски обвязки живут в **служебной акции** (инвариант `Issue.campaignID
  NOT NULL` не трогаем): служебная фирма `(Служебная) Обвязка политагитации`
  → служебная акция (вечно isConfirmed=1) → по одной служебной кампании на
  радиостанцию; всё get-or-create в рантайме, т.к. `job_DeleteEmptyActions`
  может удалить пустую служебную акцию между агитационными периодами — штатно;
- фильтрация отчётов — по `rolActionTypeID IN (7,44,55)` и нулевой цене, без
  флага «служебная» на акции;
- активация акции с типом 6 блокируется (`AgitationStationRollersNotSet` в
  `iMessageToActivate`), если у станции не заполнены три поля обвязки.

| Файл | Суть |
|---|---|
| `AgitationFraming.sql` (новая SP) | `InsertForAction`: по окнам с подтверждённым типом 6 — get-or-create служебных сущностей, вставка 44 (первое окно цепочки), 7 (окно агитации), 55 (последнее окно цепочки) с учётом ручных 4/5 и обновлением счётчиков окна. `CleanupWindow`: если в цепочке не осталось типа 6 — прямое удаление служебных выпусков с корректировкой счётчиков (мимо `IssueIUD`, чтобы `PastIssue`/`DeadLineViolationDelete` не блокировали системное снятие; лог удалений не ведётся) |

| `ActionActivate.sql` | предпроверка заполненности полей станции (fatal, блокирует активацию целиком) + вызов `InsertForAction` после подтверждения выпусков, перед `ActionRecalculate` |

Проверено на dev (транзакция с откатом): блокировка при пустых полях станции;
активация создаёт 3 выпуска обвязки в служебной акции и увеличивает
`timeInUseConfirmed` на сумму длительностей; повторная активация не дублирует;
удаление последнего типа 6 снимает обвязку и возвращает счётчики. Ошибка FK в
`SayAdminThatIssuesDelete` при тесте — артефакт (userID=1 нет на dev), не код.

**Ловушка `Action.userID`** (найдена при ручном тестировании): колонка
nullable, но на практике обязательна — журналы и гриды джойнят `[User]` через
`INNER JOIN` по `Action.userID`, и акция с NULL-создателем в них просто
исчезает. Симптом был: обвязка есть в `Issue`, но не видна в блоке «Все выходы
в эфир» (`WindowIssuesRetrieve`). Тот же паттерн — в `Actions1`,
`SpecialActions`, `TransferLogRetrieve`, `ProgramIssues`, ряде `stat_*`.
Служебная акция теперь создаётся с `userID` = 0 (`admin`): владелец служебной
акции не должен зависеть от того, кто активировал агитацию первым, иначе
статистика с группировкой по менеджеру получит чужие (нулевые) выпуски.
Сетка вещания (`rpt_Grid_v3`) джойнит `[Action]` без `[User]` — там обвязка не
терялась. Вывод на будущее: не полагаться на NULL-поля как на «естественный
фильтр» служебных сущностей — фильтруем по `rolActionTypeID`, как договорились.

Блок «Выходы в эфир этой кампании» обвязку не показывает и не должен — она
принадлежит служебной кампании, а не кампании клиента (by design).

### 7.3. Размещение в уже активированной акции (24.07.2026)

Найдено при тестировании: активированную акцию можно открыть и доразместить
агитацию — `IssueIUD` берёт `@isConfirmed` из `[Action].isConfirmed`, то есть
выпуск создаётся сразу подтверждённым, минуя `ActionActivate`, и обвязка не
появлялась.

Ядро вынесено в режим `AgitationFraming 'InsertForWindow'` (одно окно), его
используют оба пути: `InsertForAction` (активация) теперь перебирает окна и
вызывает его, а `IssueIUD AddItem` — при добавлении подтверждённого ролика
типа 6. В `hlp_IssueVerify` добавлена парная проверка: подтверждённое
размещение агитации при незаполненных полях станции запрещено
(`AgitationStationRollersNotSet`, добавлено и в `iMessage`). В черновике
проверки/вставки нет — их выполнит активация.

Проверено на dev: блокировка без полей станции; вставка обвязки при прямом
добавлении (+44с к окну); второй ролик агитации не дублирует обвязку; удаление
одного из двух обвязку сохраняет, удаление последнего — снимает; регрессия
черновик→активация работает.

### 7.4. Инвентаризация путей записи выпусков (что покрыто, что нет)

| Путь | Статус |
|---|---|
| `IssueIUD AddItem/DeleteItem` (линейное размещение, Del) | покрыто хуками |
| `ActionActivate` (активация + удаление непрошедших) | покрыто |
| `AddRangeIssues`, `MasterIssueDelete` (веер) | покрыто — зовут `IssueIUD` |
| `IssueTransfer` (перенос выпуска, drag-and-drop) | **не покрыто**: прямой `UPDATE actualWindowID` — обвязка останется в старом окне |
| Режим переноса в `ActionActivate` (`@tryTransferFailedIssues`) | **не покрыто**: тот же прямой `UPDATE` окон |
| `ModuleIssueIUD`, `PackModuleIssueID` (модуль/пакет) | **не покрыто**: прямой `INSERT INTO Issue` |
| `CampaignImportGrammofon`, `CampaignImportMediaPlus` (импорт) | **не покрыто**: прямой `INSERT` |
| Каскадное удаление кампании/акции (`FK_Issue_Campaign ON DELETE CASCADE`: `job_DeleteEmptyActions`, `DeleteActionsInPast`, удаление акции) | **не покрыто**: выпуски исчезают без `IssueIUD`, обвязка остаётся сиротой |
| `RollerSubstitute` (замена ролика) | не требует: класс агитация/не-агитация при замене менять запрещено, окно уже обвязано |

Альтернатива, закрывающая все пути разом — триггер на `Issue`
(AFTER INSERT/DELETE/UPDATE). В базе сейчас **ноль** пользовательских триггеров
(`sys.triggers`), то есть это был бы новый для проекта архитектурный приём;
плюс нужна защита от рекурсии (обвязка сама пишет в `Issue`). Решение о
триггере vs добивание путей по одному — за владельцем продукта.

Остаётся (этап 4): порядок обвязки в DJin-экспорте (`DJinExportDocument`/
`BlockManager` — c-type-44/7/55 между влётом и аутом), проверка «красных» окон
в UI трафика, ручная проверка сценария в клиенте.

| Файл | Суть |
|---|---|
| `ArtvisDB/dbo/Tables/MassMedia.sql` | +3 колонки `agitationLocalRollerID` / `agitationAnnounceRollerID` / `agitationFederalRollerID` (INT NULL, FK на `Roller` — привязанный ролик нельзя удалить) |
| `ArtvisDB/dbo/Views/vMassmedia.sql` | +3 колонки в SELECT (паспорт читает главную запись из view) |

Механика движка паспорта (для будущих правок): result set'ы процедуры паспорта
получают имена по `iTableAlias` (storedProcedureID+position→name); `<lookup
source="...">` ищет таблицу DataSet по этому имени; ValueMember =
`columnWithID`, DisplayMember = колонка `name`; для необязательности lookup
нужна колонка `id` в источнике (по ней вставляется пустая строка), а
nullable-ность поля движок берёт из метаданных колонки view. При сохранении
`ApplyChanges` кладёт значение в словарь параметров по имени поля XML.

Проверено на dev (в транзакции с откатом): миграция из текстовой редакции
прошла, XML валиден (одна страница, lookup без подзаголовка), `MassmediaIUD
UpdateItem` пишет все три ссылки, view их возвращает, FK отклоняет
несуществующий rollerID, повторный прогон deploy-скрипта идемпотентен. Форма
(вкладка «Политическая агитация») проверена пользователем в WinForms-клиенте.

## 9. Риски

- Цепочки `windowNextId`/`windowPrevId` (~1% окон) требуют отдельной, ещё не
  написанной функции обхода — при недосмотре легко получить дубли рамочных
  роликов или ложное «уже обрамлено» (раздел 3).
- Точный дедлайн не назван — уточнить у юриста дату начала агитации.
- Юридические правила могут измениться до реализации.
- Гонка активации (п.9 раздела 4) не имеет решения — риск двойной вставки или
  потери обрамления при параллельной работе двух менеджеров.
