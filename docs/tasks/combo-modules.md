# Комбо-модули

Комбо-модуль — объединение нескольких модулей в одну сущность. Устроен так же,
как пакетный модуль, но **без уровня прайс-листа**.

| | Пакетный модуль | Комбо-модуль |
|---|---|---|
| Уровень 1 | `PackModule` (`name`, `path`) | `ComboModule` (`name`) |
| Уровень 2 | `PackModulePriceList` (период, цена, наценки, ролик) | *отсутствует* |
| Уровень 3 | `PackModuleContent` (`moduleID`, `modulePriceListID`) | `ComboModuleContent` (`moduleID`) |

Решения, зафиксированные с заказчиком (14.08.2026):

- у комбо-модуля **только название**: ни периода действия, ни цены, ни наценок,
  ни ролика-заставки, ни пути для DJin;
- запись состава ссылается **только на модуль**, без прайс-листа модуля;
- из проверок `PackModuleContentIUD` перенесена **только уникальность модуля**
  внутри комбо-модуля. Единый тип рекламы (`roltypeID`), однородность тарифов по
  `maxCapacity` и покрытие дат прайс-листами модулей — **не переносятся**
  (последнее и невозможно: у комбо-модуля нет дат).

## Шаг 2: размещение комбо-модулями (согласовано, не реализовано)

### Зачем

Менеджеру, который продаёт комбо-модуль, нужно видеть по каждому модулю из
комбо-модуля, сколько в нём осталось свободного времени, — и ставить ролик, не
переключаясь между кампаниями станций.

### Мастер

По образцу веерного размещения (`MDIForm.MasterCreateAction`,
`SelectMassmediasStep`, `EditIssuesForm`). Новый пункт меню **«Размещение
комбо-модулями»**:

1. **Выбор фирмы** — `Firm.SelectFirm`, как в веерном.
2. **Выбор комбо-модуля** + **тип оплаты** (один на все кампании) +
   разрешение агентств: агентство берётся у станции модуля, а если у станции
   их несколько — спрашиваем сразу здесь, как это делает
   `SelectMassmediasStep.CreateAgencciesIDSString`.
3. **Форма размещения** — новая, по образцу `EditIssuesForm`: слева ролики
   фирмы, «Добавленные выпуски», статистика акции, тулбар «Позиционирование»;
   справа новый грид.
4. После закрытия формы открывается карточка акции (`ActionForm`).

### Грид

Новый контрол по образцу `RollerIssuesGrid3`:

- **строки — модули** комбо-модуля (в обычном гриде строка = тарифное окно),
  **столбцы — дни недели**;
- **период — переключатель «неделя / месяц»**: неделя, как во всех остальных
  гридах размещения, либо сразу целый месяц. В месячном режиме колонок 28–31 и
  колонка — это дата, а не день недели, поэтому недельную адресацию ячеек
  `TariffGrid` (7 колонок по номеру дня недели) переиспользовать не получится:
  новый грид строит колонки сам. Строк мало (модули, а не окна), так что месяц
  по горизонтали помещается, нужна горизонтальная прокрутка. Навигация в
  месячном режиме — по месяцам. Выбранный режим запоминается в `UserSetting`
  (`FogSoft.WinForm.Classes.UserSettings`), форма открывается в последнем
  использованном;
- в шапке столбца — дата и число выпусков за день, как в веерной форме;
- в ячейке — **минимальный остаток времени по окнам модуля** за этот день,
  то есть `MIN(duration − timeInUseConfirmed [− timeInUseUnconfirmed])`.
  Смысл: показать самое заполненное окно модуля, чтобы менеджер видел, где
  осталось всего 25 секунд;
- у окон со **штучным** ограничением (`maxCapacity > 0`) остаток по количеству
  показывается отдельно, как в обычном гриде: `02:30 [3/5]`. Время и штуки не
  смешиваются в одну величину — минимумы считаются по каждой отдельно;
- **неподтверждённые выпуски** учитываются в остатке по переключателю, как в
  обычном гриде (`ShowUnconfirmed`, он же «учитывать макеты»);
- при выбранном **позиционировании** жирным помечаются модули, у которых эта
  позиция свободна **во всех** окнах: `ComboModuleFreeTimeRetrieve` отдаёт
  `positionFree` (минимум по окнам от `isFirstPositionOccupied` /
  `isSecondPositionOccupied` / `isLastPositionOccupied`, а при учёте макетов ещё
  и от счётчиков `*PositionsUnconfirmed`). Тот же критерий, что в
  `RollerIssuesGrid3.MarkCell`, только применённый ко всем окнам модуля сразу;
- если у модуля в этот день нет ни одного окна (состав модуля задан прайс-листом
  модуля и днями недели тарифа) — **ячейка пустая**.

### Клик по ячейке

Клик создаёт `ModuleIssue` — через существующий `Campaign.AddModuleIssue`.
Повторный клик по той же ячейке добавляет **второй** выпуск, переключателем не
работает.

Кампании и акция создаются **лениво**, в момент первого клика, всё одной
транзакцией:

1. акции ещё нет — создаём новую (акция всегда новая, дописывание в
   существующую не предусмотрено);
2. кампании для станции этого модуля нет — создаём через `CampaignIUD`
   (`campaignTypeID` = 3 «Модульная», тип оплаты и агентство — с шага 2);
3. `ModuleIssue`;
4. пересчёт акции.

Если любой шаг не прошёл — откат целиком, иначе останется пустая кампания.

Проверять переполнение окон отдельно не нужно: `ModuleIssueIUD` вызывает
`hlp_IssueVerify`, который проходит по всем окнам модуля и при нехватке времени
хоть в одном возвращает `WindowOverflow`, отменяя вставку целиком. Там же —
запрет позиционирования для модулей с тарифами `maxCapacity` 1–3
(`MaxCapacityModuleSetPositionError`).

Отдельно учесть: `CampaignIUD` не даёт обычному менеджеру добавлять кампанию в
подтверждённую и уже завершившуюся акцию (`CannotAddCampaignInConfirmedFinishedAction`).
Клик по такой строке должен показать сообщение, а не упасть.

### Удаление

Только через панель «Добавленные выпуски» (в гриде удаления нет). При удалении
последнего выпуска кампании эта кампания удаляется **молча**, без вопроса, —
чтобы в акции не оставались нулевые кампании, которые лезут в счета и статистику.
Если так удалена последняя кампания акции, удаляется и сама акция.

### Этап 1: `ComboModuleFreeTimeRetrieve` (сделано)

`ComboModuleFreeTimeRetrieve(@comboModuleID, @startDate, @finishDate,
@showUnconfirmed)` — одна строка на (модуль, день):

| Колонка | Смысл |
|---|---|
| `moduleID`, `modulePriceListID`, `price` | модуль и действующий на этот день прайс-лист модуля |
| `issueDate` | день (`dayOriginal`) |
| `freeTime` | минимальный остаток времени по окнам модуля, секунды |
| `freeCapacity` / `maxCapacity` | минимальный остаток по количеству среди штучных окон и вместимость того самого окна; `NULL`, если штучных окон нет |

Решения, принятые при реализации:

- **День — `dayOriginal`**, как в `IsModuleExist` и `ModuleIssueIUD`, то есть по
  исходной сетке окон, а не по перенесённой.
- **Модуль либо есть в этот день целиком, либо его нет.** Строка возвращается,
  только если окно есть на *каждый* тариф прайс-листа (та же проверка, что в
  `IsModuleExist`) и ни одно окно не отключено — иначе клик всё равно ничего не
  создаст: `AddModuleIssue` вернёт `null`, либо `hlp_IssueVerify` ответит
  `DisabledInsertRoller`. Промежуточного состояния «модуль есть частично» нет.
- **Дня нет в выдаче** — модуля в этот день нет (прайс-лист не покрывает дату,
  окон нет вовсе или они неполные). Грид рисует пустую ячейку.
- **Время считается по всем окнам, включая штучные.** `hlp_IssueVerify` проверяет
  переполнение по времени независимо от `maxCapacity`, так что это ограничение
  реально для любого окна. Штучный остаток идёт отдельной парой колонок, ячейка
  показывает обе величины: `02:30 [1/1]`.
- Строки грида (перечень модулей комбо-модуля) берутся отдельно, существующей
  `ComboModuleContentRetrieve` — дублировать её в этой процедуре не стал.

Проверено на dev: минимум сходится с поокошным расчётом (модуль 589 на
10.08.2026 → 80 сек, с неподтверждёнными → 79); у модуля с неполными выходными
эти дни в выдачу не попадают; модуль из штучных окон отдаёт `00:30 [1/1]`. Месяц
по пяти модулям — 24 мс.

### Этап 2: `ComboModuleGrid` (сделано)

`Client/Controls/ComboModuleGrid.cs` — отдельный `UserControl`, а не наследник
`TariffGrid`: там и сетка колонок, и адресация ячеек жёстко недельные
(семь колонок по номеру дня недели), а нам нужен ещё месяц. `NavigationCaption`
переиспользована, а вот `GridWithColumnsAutoResizing` — нет: он растягивает
последнюю колонку на всю свободную ширину, а колонки дней должны быть
одинаковыми. Внутри обычный `DataGridView` с теми же стилями.

Устройство: две фиксированные колонки (радиостанция, модуль), две фиксированные
строки (даты, число выпусков), дальше строка на модуль и колонка на день. Данные
берутся из `ComboModule.LoadContent` (строки) и `ComboModule.LoadFreeTime`
(ячейки), `Client/Classes/ComboModule.cs`.

- `ComboModuleID`, `PeriodMode` (`Week` / `Month`), `ShowUnconfirmed`,
  `CurrentDate` — свойства; `RefreshGrid()` перестраивает всё.
- Колонки пересоздаются на каждый период: в месяце их 28–31, заголовок — день
  недели соответствующей даты.
- `CellClicked` отдаёт `ComboModuleDay` (модуль, станция, прайс-лист модуля,
  цена, дата, остаток). По пустой ячейке события нет: модуля в этот день нет.
  Событие не поднимается и пока выключен `EditMode` — режим добавления, который
  включается кнопкой «Режим добавления» в тулбаре формы (аналог `tbbStart`
  обычной кампании).
- `MarkIssues(issues)` красит синим ячейки, где у текущей акции уже есть
  выпуски, — тем же цветом, что и тарифная сетка обычной кампании. Вызывается по
  событию `GridRefreshed`, поэтому подсветка и счётчик выпусков переживают
  листание стрелками и смену режима недели/месяца.
- `SetIssuesCount(date, count)` — строка счётчика выпусков под датами, заполнять
  будет форма размещения на этапе 5.

- Колонки дней одинаковой ширины, по самой широкой из них; в месяце грид
  прокручивается по горизонтали.

### Этап 3: `SelectComboModuleStep` (сделано)

`Client/Forms/CreateActionMaster/SelectComboModuleStep.cs` — второй шаг мастера,
рядом с `SelectMassmediasStep` веерного размещения: список комбо-модулей,
тип оплаты и разрешение агентств. Раскладка на `TableLayoutPanel` +
`FlowLayoutPanel`, как в остальных переделанных диалогах.

Результаты шага: `ComboModuleID`, `ComboModuleName`, `PaymentTypeID`,
`AgencyByMassmedia` (агентство на каждую радиостанцию комбо-модуля).

- Кампании и акция здесь **не создаются** — в отличие от веерного мастера, где
  `CreateActionWithRange` сразу заводит акцию и кампании на все станции. У нас
  они появятся лениво, по первому клику в форме размещения.
- Агентства всё же разрешаются здесь: если у станции агентство одно — берётся
  молча, если несколько — открывается выбор, как в `CreateAgencciesIDSString`.
  Спрашивать об этом посреди расстановки роликов неудобно. Если у станции нет
  ни одного агентства — сообщение и отказ, потому что `CampaignIUD` без
  агентства не работает (`CannotAddCampaignWithoutAgency`).
- Тип оплаты грузится `PaymentTypesLoad @ShowActive = 1` (проверено: колонки
  `paymentTypeID`, `name`, активных типов 7).

Форму целиком отрисовать вне приложения не удалось: список комбо-модулей идёт
через метаданные, а `EntityManager.LoadEntity` требует залогиненного
пользователя (`SecurityManager.LoggedUser`). Проверяется в работающем клиенте
после этапа 6, когда появится пункт меню.

### Этап 4: `ComboModulePlacementForm` (сделано)

`Client/Forms/CreateActionMaster/ComboModulePlacementForm.cs` — третий шаг
мастера. Слева ролики фирмы, статистика акции и «Добавленные выпуски», справа
`ComboModuleGrid`; сверху тулбар: позиционирование, неделя/месяц, учёт
неподтверждённых.

Форма самостоятельная, а не наследник `CampaignForm` (как `EditIssuesForm`):
`CampaignForm` завязана на одну кампанию с её прайс-листом и тарифной сеткой, а
здесь строки — модули разных радиостанций и кампаний столько же, сколько
модулей. Набор панелей повторён вручную теми же контролами.

- Режим периода запоминается в `UserSetting` под именем
  `ComboModulePlacementPeriodMode`.
- `OnLoad` строит грид синхронно (ролики, выпуски акции, остатки по модулям) — на
  большой акции заметно, поэтому обёрнут в `Cursor.Current = Cursors.WaitCursor`
  (именно `Cursor.Current`, а не `this.Cursor`: форма ещё не показана).
- Ролики берутся `Firm.GetRollers()` с сущностью `ActionRollers` — как в
  `CampaignForm.InitRollersList`.
- Статистика акции и список добавленных выпусков пока пустые: акции до первого
  клика нет. Заполняются на этапе 5.
- Клик по ячейке грид отдаёт, но форма его пока не обрабатывает — это этап 5.

Проверена раскладка (отрисовка формы в обход конструктора, без данных).
Заодно выяснилось, что `NavigationCaption` показывает текст про прайс-лист, пока
грид не обновился, — в конструкторе `ComboModuleGrid` шапка теперь очищается.

### Этап 5: запись (сделано)

**Добавление.** Клик по ячейке → `ComboModulePlacementForm.AddModuleIssue`, всё
одной транзакцией:

1. `EnsureAction` — акции ещё нет, создаём (`ActionIUD` через `Update()`,
   `isConfirmed = 0`);
2. `EnsureCampaign` — кампании на радиостанции этого модуля нет, создаём
   (`CampaignIUD`, тип 3 «Модульная», тип оплаты и агентство с шага 2);
3. `Campaign.AddModuleIssue` → `ModuleIssueIUD`;
4. `_action.Recalculate()`.

При откате объекты, созданные внутри этой же транзакции, забываются и в памяти
(`_action`, `_campaignByMassmedia`) — иначе форма считала бы существующим то,
чего в базе нет.

Модуль и прайс-лист для `AddModuleIssue` собираются из данных ячейки: `ModuleIssue`
берёт у них только идентификаторы и цену, поэтому лишний поход в базу не нужен.

**Удаление.** Выпуски удаляет сам `SmartGrid` панели (`ModuleIssue.Delete` →
`ModuleIssueIUD`, пересчёт акции внутри). Форма по событию `ObjectsDeleted`
убирает то, что осталось пустым: кампанию без выпусков, следом акцию без
кампаний — тоже одной транзакцией.

**Панель «Добавленные выпуски»** — новая процедура `ComboModuleIssuesRetrieve`
(существующие `ModuleIssueRetrieve` и `CampaignModuleIssuesRetrieve` работают в
разрезе одной кампании), а сущность у панели — **штатная 130 «Выпуск модуля»**
со своим набором колонок: `iEntityAttribute` с `selector = 3` (дата,
радиостанция, модуль, ролик, порядок), клон сущности с
`AttributeSelector = ModuleIssue.AttributeSelectorComboPlacement`. Так же
`ActionForm` показывает кампании коротким набором колонок.

Сначала для панели была заведена отдельная сущность 1272, и это оказалось
ошибкой: `ModuleIssue` во всех конструкторах берёт сущность жёстко
(`base(GetEntity())` → `Entities.ModuleIssue`), поэтому объекты всё равно жили
под 130. `SmartGrid.DeleteRow` начинается с `IsAllowedEntity(объект.Entity)` и
при несовпадении с сущностью грида молча выходит — строка не пропадала из
списка, а событие удаления не поднималось, значит не работали ни пересчёт, ни
обновление панелей. Своя сущность тут в принципе не годится, пока класс сам
задаёт свою; набор колонок через `selector` решает ту же задачу без обмана.

Строка счётчика выпусков под датами заполняется из этой же выборки.

**Меню выпуска в панели — стандартное, от сущности 130:** обновить,
позиционирование, замена ролика, удаление. Это правильно — в панели
действительно `ModuleIssue`. Практическое следствие: `ComboModuleIssuesRetrieve`
обязана отдавать всё, что читают эти действия (`positionId`,
`modulePriceListID`, `rollerID`, `deleteDate`), иначе меню падает.


**Проверка.** Весь путь записи прогнан на dev теми же процедурами, что вызывает
форма (`ArtvisDB/Scripts` не хранит этот прогон — он разовый, в транзакции с
откатом): один `ModuleIssue` породил 6 строк `Issue` по числу окон модуля;
остаток в самом заполненном окне упал со 113 до 101 секунды — ровно на
длительность ролика; удаление выпуска убрало и `ModuleIssue`, и все шесть
`Issue`; кампания и акция удалились следом, не осталось ничего.

### Этап 6: пункт меню и мастер целиком (сделано)

`MDIForm.MasterPlaceComboModules` — по образцу `MasterCreateAction`:
`Firm.SelectFirm` → `SelectComboModuleStep` → `ComboModulePlacementForm` →

### Редактирование готовой акции

Кнопка «Размещение модулями» на тулбаре карточки акции (`ActionForm`) сначала
спрашивает (`UserMessage.ShowYesNoCancel`), в каком режиме открыть форму:

- **«Нет» — только размещённые модули.** Строки грида берутся не из комбо-модуля,
  а из самой акции — модули её модульных кампаний. Комбо-модуль не нужен, так
  правятся и акции, заведённые обычным путём. Кампании не создаются и не
  удаляются. Описано в этом разделе.
- **«Да» — выбрать комбо-модуль.** Открывается `SelectComboModuleStep`
  (комбо-модуль + тип оплаты + агентства), затем форма показывает **весь состав
  выбранного комбо-модуля**, достраивая модули, которых в акции ещё нет. См.
  «Достройка по комбо-модулю» ниже.

- Набор модулей даёт `ComboModuleActionModulesRetrieve`, остатки —
  `ComboModuleFreeTimeRetrieve` с параметром `@actionID` вместо
  `@comboModuleID` (список модулей внутри процедуры собирается в табличную
  переменную, дальше расчёт общий).
- **Модульная кампания без выпусков в грид не попадает.** Связи кампании с
  модулем в схеме нет, она выводится через `ModuleIssue` — так же устроена
  `CampaignModulesRetrieve`. Пока в кампании ничего не размещено, неизвестно,
  какой в ней модуль. Решено оставить как есть.
- Клик добавляет выпуск в **существующую** кампанию радиостанции; кампании
  запоминаются из выпусков (`ComboModuleIssuesRetrieve` отдаёт и `massmediaID`,
  и `campaignID`).
- **Панель статистики показывает акцию целиком**, а не только модульную её часть,
  хотя грид и список выпусков ограничены модулями. Так же ведёт себя веерная
  форма, и это осознанно: пакетная скидка считается по всей акции, поэтому сумма
  по части кампаний не совпала бы с тем, что попадёт в счёт, а сама по себе
  никому не нужна.
- **Каскадное удаление в этом режиме отключено:** удаляются только выпуски,
  кампании и акция остаются. Молча сносить кампанию в чужой готовой акции
  опасно — человек может просто чистить выпуски.

### Достройка по комбо-модулю (ветка `feature/combo-modules-toolbar`)

Проблема: акцию завели из комбо-модуля на 10 модулей, ролики поставили в 3 →
акция из 3 модульных кампаний. При повторном входе в «Размещение модулями» видно
только эти 3: связи «акция ← из какого комбо-модуля» в базе нет, остальные 7
модулей система не знает. Теперь через выбор «Да» менеджер указывает комбо-модуль
руками, и форма дорисовывает недостающие модули.

Третий режим `ComboModulePlacementForm` — конструктор
`ComboModulePlacementForm(ActionOnMassmedia action, SelectComboModuleStep step)`,
признак `_reconstructFromComboModule` (это `_isExistingAction && _comboModuleID > 0`).

- **Строки грида — состав комбо-модуля целиком** (`ComboModuleContentRetrieve`,
  как в мастере), остатки — `ComboModuleFreeTimeRetrieve` по `@comboModuleID`.
  SQL не менялся: и выборки строк, и расчёт остатка уже умеют работать от
  комбо-модуля.
- **Существующие модульные кампании видны, только если их модуль входит в
  выбранный комбо-модуль.** Модули не из комбо-модуля просто не получают строк;
  заодно `LoadActionModuleIssues` фильтрует выпуски для панели, счётчика по дням
  и стартовой даты по `ComboModuleContent` — иначе в панель полезли бы выпуски
  скрытых модулей.
- **Клик в модуль без кампании создаёт новую модульную кампанию прямо в этой
  акции** — `EnsureCampaign` больше не отказывает при `_isExistingAction`, если
  это режим комбо-модуля. Тип оплаты и агентство — с шага выбора
  (`SelectComboModuleStep` разрешает агентства по всем станциям комбо-модуля).
- **Каскадное удаление — только для кампаний, созданных в этой сессии**
  (`_campaignsCreatedThisSession`, ключ — `massmediaID`). Оставшуюся без выпусков
  такую кампанию сносим молча; ранее существовавшие кампании и саму акцию не
  трогаем никогда (в мастере — трогаем, там акция наша).
- **Подтверждённая и завершившаяся акция:** `CampaignIUD` не даёт обычному
  менеджеру дописать кампанию (`CannotAddCampaignInConfirmedFinishedAction`) —
  ошибка всплывает в `ErrorManager.PublishError`, форма продолжает работать.
- Порог кнопки не менялся: «Размещение модулями» активна при ≥2 модульных
  кампаниях в акции (`ActionForm.EnableComboModulesButton`).

Новый хелпер `UserMessage.ShowYesNoCancel` (`MessageBoxButtons.YesNoCancel`).

### Кэширование списка комбо-модулей — выключили кэш глобально

Причина, почему список и названия комбо-модулей в мастере размещения не
обновлялись без перезапуска приложения: `ObjectsIterator.GetContent()`
кэширует результат в `lastContentFilter`, а `EntityManager.GetEntity(entityId)`
возвращает один и тот же объект `Entity` на весь процесс — фильтр в
`SelectComboModuleStep` всегда пустой и не меняется, поэтому кэш не сбрасывается,
пока жив процесс.

Штатный переключатель этого кэша — `ConfigurationUtil.IsUseSimpleCache`
(appSetting, по умолчанию `true`, нигде в `.config` раньше не задавался явно).
Перед тем как его трогать, прогнали перепись всех вызовов `.GetContent()` по
проекту (35 мест), чтобы понять реальный масштаб последствий:

- **Свежий объект-контейнер на каждый вызов** (`campaign.GetContent()`,
  `_action.GetContent()` и т.п. в `Action.cs`, `ActionOnMassmedia.cs`,
  `ActionRoller.WinForms.cs`, `ActionForm.cs`) — кэш живёт не дольше самого
  объекта, флаг тут не влияет вообще.
- **Тот же singleton `Entity`, но кэш явно сбрасывается перед чтением**:
  `JournalForm.LoadData` (`grid.Entity.ClearCache()`), `TreeView2.RefreshDependantGrid`
  (`CurrentObjectContainer.ClearCache()`), `SmartGrid.RefreshDependantGrid` (там
  вообще не singleton, а `PresentationObject` конкретной строки). То есть все
  журналы и админ-дерево — самый частый способ показать список в системе — уже
  и так каждый раз ходят в базу, флаг им не нужен.
- **Реально кэшируется навсегда** — вот где флаг что-то менял: наш
  `SelectComboModuleStep`, `Firm.GetFirmCandidates()`, `HeadCompany.GetFirmsForReassign()`,
  `PackModule.LoadModules()` (фильтр — дата, поэтому обычно и так меняется),
  и два переиспользуемых лукап-контрола без явного `ClearCache` —
  `PageFieldLookUp` (выпадающий список ссылки на справочник в любом паспорте
  по метаданным) и `ObjectPicker2`. Все — небольшие справочные списки, не
  тяжёлые по объёму данных.

Раз проблемы с производительностью в системе всегда были от неоптимального SQL,
а не от объёма данных, решили не городить точечный обход конкретно для
комбо-модулей (загрузка напрямую через `DataAccessor.LoadDataSet`, в обход
`Entity.GetContent()`), а выключить кэш глобально:
`IsUseSimpleCache=false` в [Client/app.config](../../Client/app.config). Заодно
закрывает и наш случай, без изменений в `SelectComboModuleStep.cs`.

### Запрет минимизации

При сворачивании формы окно пропадало: `ShowInTaskbar` по умолчанию `true`, но
Windows группирует окна одного процесса под одной иконкой панели задач,

грида, разворачивать/восстанавливать её имеет смысл.

### Массовый набор состава галочками

Раньше модули в комбо-модуль добавлялись по одному через паспорт («Добавить

  метаданной, `SelectionForm` получает `EntityManager.GetEntity(Entities.Module)`
  как есть.
- **Удаление по естественному ключу.** `ComboModuleContentIUD.DeleteItem` теперь
  принимает либо `@comboModuleContentID`, либо пару `(@comboModuleID, @moduleID)`,
  когда первый `NULL`. Без этого для каждой снятой галочки пришлось бы отдельным
  запросом искать `comboModuleContentID` по модулю — лишний круг. Решение по
  образцу `ModuleTariff`: там для той же задачи вообще нет суррогатного ключа,
  первичный ключ таблицы составной `(modulePriceListID, tariffID)`; у
  `ComboModuleContent` суррогатный `comboModuleContentID` уже был (и остался, он
  нужен как надёжный PK для одиночного «Удалить» из дерева), поэтому решили
  проблему на уровне процедуры, а не трогая схему.
- Добавленные/удалённые строки проводятся так же, как `EditTariffList`:
  `contentEntity.CreateObject(dict).Update()` / `.Delete(true)` — без сырых
  вызовов процедуры, через штатный метаданный путь сущности 1271.

Проверено на dev: `ComboModuleAllModulesSelection` для тестового комбо-модуля
корректно помечает `isObjectSelected=1` у всех пяти уже добавленных модулей;
удаление по `(comboModuleID, moduleID)` без `comboModuleContentID` отрабатывает
(проверено в транзакции с откатом); класс `ComboModuleContainer` и переопределение
`AssignNew` подтверждены рефлексией на собранной сборке.

**Фикс: добавление тихо не срабатывало.** `Entity.CreateObject(Dictionary)`
внутри присваивает `PresentationObject.Parameters`, а у этого свойства побочный
эффект — `isNew = false`. Из-за этого `.Update()` для добавленных модулей
отправлял не `AddItem`, а `UpdateItem` с пустым `@comboModuleContentID`, и
`UPDATE ... WHERE comboModuleContentID = NULL` тихо не находил ни одной строки —
без ошибки, без эффекта. Снятие галочек при этом работало (`Delete(true)` всегда
шлёт `DeleteItem`, который уже умел падать на естественный ключ).

`ModulePricelist.EditTariffList` с той же схемой (`CreateObject(dict).Update()`)
эту ловушку обходит по-другому: передаёт `["isEditTarrifs"] = true`, и
`ModuleTariffID.sql` явно проверяет этот флаг, чтобы завернуть `UpdateItem` в
`INSERT`. Для `ComboModuleContent` пошли проще — `content.IsNew = true;` перед
`.Update()`, без флага и без правки процедуры.

### Массовое добавление по Insert

Симметрично массовому удалению по Del: выделили ячейки прямоугольником (в
режиме просмотра — только там `RawDataGridView.MultiSelect` включён), нажали
Insert — выбранный ролик расставляется в каждую выделенную ячейку.

Максимально просто, как и просили: `AddIssuesInSelectedCells` в цикле вызывает
уже существующий `AddModuleIssue` на каждую ячейку — тот же метод, что и у
одиночного клика, без новых хранимых процедур. Каждый вызов — своя транзакция
(как и раньше), поэтому частичный успех возможен: часть ячеек встанет, часть
может не пройти `hlp_IssueVerify` (переполнение окна и т. п.) — успешные не
откатываются. `RefreshAfterChange()` вызывается один раз в конце, а не на
каждую ячейку.

`ComboModuleGrid_KeyDown` теперь диспетчерит оба ключа: `Insert` →
`AddIssuesInSelectedCells`, `Delete` → `DeleteIssuesInSelectedCells`.

**Ошибки не в msgbox, а в том же журнале, что у Del.** Первая версия собирала
ошибки в список и показывала одним `UserMessage` — при семи выделенных ячейках,
из которых три не встали, это неудобно читать. `DeleteIssuesInSelectedCells` в
этой же форме уже решает ровно такую задачу через
`SmartGrid.CreateDeleteErrorsTable`/`AddDeleteError`/`ShowDeleteErrors` — простой
журнал со строкой на ошибку (название и текст), а не одна портянка текста.

Проблема была в том, что `ShowDeleteErrors` называла журнал и его окно жёстко
«Ошибки удаления»/«Ошибки массового удаления» — неправильно для операции
добавления. Добавлен необязательный параметр `caption` (по умолчанию — старый
текст, поведение всех прежних вызовов не меняется), `AddIssuesInSelectedCells`
передаёт «Ошибки массового добавления». Название методов (`*DeleteError*`)
осталось прежним — переименовывать по всему проекту не стали, это уже не про
конкретно удаление, а про массовые операции вообще, о чём теперь сказано в
комментарии к `ShowDeleteErrors`.

### PgUp/PgDown — пролистать неделю/месяц

Стрелки в подписи над сеткой (`NavigationCaption`, `Caption_GoNext`/
`Caption_GoPrevious` в `ComboModuleGrid`) продублированы клавиатурой: PageUp —
на период назад, PageDown — вперёд.

Разбирали варианты клавиш, прежде чем остановиться на этих:
- стрелки влево/вправо заняты перемещением между ячейками грида;
- Ctrl+PageUp/PageDown (как переключение листов в Excel) не пересекается ни с
  чем, но признано неудобным — требует двух клавиш;
- голый PageUp/PageDown у `DataGridView` по умолчанию сам листает строки на
  страницу, но строк тут немного (список модулей комбо-модуля, не окна
  тарифной сетки), так что потерять эту прокрутку клавиатурой не жалко —
  колесо мыши и скроллбар остаются.

`ComboModuleGrid` получил два публичных метода-обёртки, `GoToNextPeriod`/
`GoToPreviousPeriod` — тонкие обёртки над уже существующими приватными
`Caption_GoNext`/`Caption_GoPrevious`, чтобы форма могла их дёрнуть, не расширяя
паблик-API самой подписи. `ComboModuleGrid_KeyDown` (тот же обработчик, что и у
Insert/Delete) стал свитчем по `e.KeyCode`; для PageUp/PageDown выставляется
`e.Handled = true` — иначе `DataGridView` после смены периода попробует ещё и
прокрутить строки по уже неактуальным, пересобранным под другой период
координатам.

### Кнопка «Отменить» — отмена последнего добавления

По образцу `CampaignForm.tbbTemplateUndo`, но для любого добавления, не только по
шаблону. `tbbUndo` на тулбаре формы (текстовая, рядом с «Переход к дате»),
задизейблена, пока ничего не добавлено.

- `AddModuleIssue` теперь возвращает созданный `ModuleIssue`. `OnCellClicked`
  запоминает один выпуск, `AddIssuesInSelectedCells` — весь пакет, в
  `_lastAddedIssues` (`SetLastAdded` заменяет предыдущий список целиком).
- `tbbUndo_Click` удаляет ровно эти выпуски (`issue.Delete(true)` по одному с
  журналом ошибок — тот же паттерн, что `DeleteIssuesInSelectedCells`), затем
  общий хвост `AfterIssuesDeleted` (пересчёт акции, чистка пустых кампаний). В
  мастере отмена самого первого выпуска сносит и кампанию, и акцию — как ручное
  удаление того же выпуска.
- Любое удаление выпусков (`AfterIssuesDeleted`) сбрасывает `_lastAddedIssues`:
  запомненное «последнее добавление» после этого неактуально. Листание,
  refresh, смена недели/месяца и фильтров кнопку не трогают — выпуски на месте.
