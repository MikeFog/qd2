# Веб: новый объект отправлял в процедуру только те поля, которых коснулись

## Как проявлялось

«Добавить тариф» в вебе не работал **никогда**: сохранение падало с

```
Не удалось вставить значение NULL в столбец "duration_total", таблицы "ArtvisDev.dbo.Tariff";
в столбце запрещены значения NULL. Ошибка в INSERT.
```

Первая формулировка была «форма не передаёт `@duration_total`», и это увело бы в
сторону: поле объявлено в паспорте сущности 81 как обычный `<field>` на вкладке
«DJin» и рисуется правильным контролом (минуты:секунды). Отсутствовало не поле, а
**параметр**.

## Причина

Разная механика сбора значений.

**Десктоп.** Каждый контрол паспорта реализует `ApplyChanges(parameters)`
(`FogSoft.WinForm/Passport/Classes/PageControl.cs` и наследники), и форма при
сохранении обходит **все** контролы. Условие `ValueShouldBeSet`
(`PageField.cs:162`) в карточке истинно всегда — в левой колонке там подпись, а не
галочка «использовать», как в фильтре. То есть в процедуру уезжает значение каждого
объявленного поля, трогали его или нет: `PageFieldNumeric` кладёт
`NumericControl.Value`, `PageFieldText` — `TextBox.Text`, `PageFieldBoolean` —
`Checked`.

**Веб (до правки).** Значение попадало в параметры объекта только из обработчика
`@onchange`, то есть **лишь у полей, которых коснулся пользователь**.

У существующего объекта разницы не видно: словарь параметров уже заполнен
процедурой загрузки карточки. А у нового в нём оказывались только поля со
значением по умолчанию в самом паспорте (атрибут `value`) и то, что заполнил
пользователь. Остальные до процедуры не доезжали вовсе.

**Это не дефект тарифа, а дефект движка карточки.** Ломался любой новый объект, у
которого есть поле, не заполняемое руками, и процедура без умолчания у этого
параметра.

## Что обнаружилось по дороге (живые прогоны, по одному слою за раз)

| Прогон | Отказ | Чему научил |
|---|---|---|
| до правки | `NULL в столбце duration_total` | параметр не доезжает |
| дописали галочки и продолжительности | `TariffIUD ожидает параметр @maxCapacity` | у процедуры нет умолчаний и у обычных числовых полей |
| дописали обычные поля пустой строкой | `Failed to convert parameter value from a String to a Int16` | пустая строка не годится числовому параметру: ADO.NET отвергает её ещё до SQL |

Третий шаг — поучительный: «делать как десктоп» нельзя понимать буквально. Десктоп
отправляет **число**, потому что у него числовой контрол (`NumericUpDown`), а веб
рисует те же поля текстовым `input` и отправил бы текст.

## Что сделано

`FogSoft.Web/Components/Passport.razor`, метод `ApplyUntouchedFields()` — веб-аналог
десктопного цикла `ApplyChanges`. Вызывается из `Passport.ApplyChanges()`, то есть
перед `Update()` (`PassportDialog`). Для каждого объявленного поля, значение
которого отсутствует или `NULL`, записывается то, что показывает контрол, **в виде,
соответствующем типу поля** (`FieldTypeResolver`, он уже посчитан по метаданным и
типу колонки):

| Тип поля | Что записывается |
|---|---|
| boolean | `false` |
| integer, decimal, money, timeDuration | `0` |
| строка и прочее | пустая строка |
| date, dateTime, time | **ничего** |
| тип не распознан (`Type == null`) | **ничего** |

`lookup`, `objectPicker`, `selector`, картинка и `label` пропускаются: у них своя
запись значения либо её нет вовсе.

## Почему дату не подставляем

Пустой календарь — это «не выбрано», а не 01.01.1900, и SQL привёл бы `''` к дате
молча. Лучше честный отказ процедуры, чем тихо записанная неверная дата. То же с
полем без распознанного типа: подставлять вслепую нечего.

**Остаток:** если у какой-то сущности окажется обязательный параметр типа «дата» без
умолчания в процедуре, добавление нового объекта в вебе упрётся в него так же, как
упиралось в `duration_total`. Отказ будет виден сразу и с внятным текстом.

## Закрытый вопрос: `maxCapacity = 0`

Новый тариф уходит с `maxCapacity = 0`, потому что умолчания у поля в паспорте нет
и контрол показывает ноль (десктопный `NumericUpDown` показал бы то же). Сначала это
выглядело как недосмотр, но **ноль здесь и есть правильное значение: он означает
«без ограничения по ёмкости»** (владелец продукта, 2026-09-22). Менять метаданные
не нужно, поведение верное.

## Что стоит решить отдельно

1. **Обязательность обычных полей в вебе не проверяется** (`Passport.Validate()`
   намеренно проверяет только `lookup` и `objectPicker`). Поэтому пустое
   обязательное поле сейчас уходит в процедуру и отказ приходит уже от неё. Ввести
   проверку — отдельная работа: она начнёт отклонять сохранения, проходящие сегодня.
