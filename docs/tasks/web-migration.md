исходных пунктов: три сделаны, один сделан за 22 партии (вынос диалогов,
отдельный отчёт — `docs/tasks/web-migration-dialogs.md`), один перенесён в

**Технология выбрана: ASP.NET Core 10 + Blazor Server** (решение принято
2026-08-23, обоснование — раздел 5.1 и 5.5). Открытый вопрос №1 закрыт.

**Вертикальный срез сделан** (2026-08-24, ветка `feature/web-slice`). Замер и
находки — в разделе 10. Короткий итог: экран стоит **ноль строк кода** —
журнал работает для любой сущности по метаданным; 34 из 56 активных сущностей
с паспортом покрыты уже сейчас. Дальше — этап 1.

Остальная часть документа — аналитическая, написана до начала работ: замеры
кодовой базы (август 2026), классификация кода по стоимости переноса, выбор
технологии интерфейса, оценка объёма.

Исходные требования (сформулированы устно):

1. Минимальный объём изменений. Не улучшать то, что работает, только потому что
   «делаем новое».
2. Бизнес-логика остаётся в хранимых процедурах. Процедуро-центричная
   архитектура сохраняется как есть.
3. Существующие классы, выполняющие свою функцию, переиспользуются.
4. Изменения касаются только слоя пользовательского интерфейса: вместо
   Windows Forms — браузер.
5. Технология визуализации выбирается по критерию простоты: простота написания
   кода, простота поддержки, простота понимания.

**Требование №1 изменено владельцем продукта (2026-09-18).** Было:
«минимальный объём изменений, не улучшать то, что работает». Стало: при
разборе десктопного кода, который переносим (и вообще по дороге), **нужно**
искать и **предлагать** исправление косяков и упрощение существующей
архитектуры десктопа, если это облегчает переход на веб. Не «можно», а
«нужно».

Порядок:

- **предлагать, а не делать молча.** Идея — с обоснованием: что упрощается,
  что теряется, чего стоит, что затронет в десктопе. Решение принимает
  владелец продукта;
- **уже перенесённое не трогаем** — правило про код, который ещё предстоит
  разбирать;
- до решения владельца переносим как есть; после — делаем по решению и
  записываем его здесь.

Первый кандидат — **идея владельца: вместо движка `MasterDetail` —
древовидный экран** (слева мастер, справа его «детали»): 4 пункта меню, см.
`docs/tasks/web-menu-inventory.md` §3 и §4 (`MasterDetailForm`). До решения
нужен разбор: мастер в `MasterDetail` — это журнал с отбором и тысячами строк
(журнал оплат), а дерево держит узлы без виртуализации и без колонок; что
теряется при переходе и не проще ли «журнал + подчинённый список под ним».

## 2. Ключевой вывод: большая часть UI — это движок и метаданные

Значительная доля экранов не написана руками:

- **Меню и права** грузятся из БД:
  `ArtvisDB/dbo/Stored Procedures/UserMenuItems.sql` (`iMenu` + `GroupMenu` +
  `UserAdditionMenu`), рендерится в `Client/Forms/MDIForm.cs`.
- **Журналы** строятся универсально: `Globals.ShowSimpleJournal(Entity, ...)`
  → `JournalForm`. В `MDIForm.cs` — 36 таких вызовов.
- **Карточки сущностей (паспорта)** собираются в рантайме из XML в колонке
  `iEntity.passport` движком `FogSoft.WinForm/Passport/Classes/*`
  (словарь контролов — `PageControl.Attributes`: `field`, `lookup`,
  `objectPicker`, `selector`, `treeselector`, `image`, `button`, `label`,
  `separator`). Подробности — `docs/ARCHITECTURE.md`, раздел
  «Metadata-driven passport forms».
- **Фильтры** — XML в `iEntity.filter` (57 сущностей).

Следствие для плана: один веб-рендерер журнала, фильтра и паспорта закрывает
большинство из 89 активных пунктов меню **без кода на каждый экран**. И после
миграции добавление сущности останется, как сейчас, чисто метаданными (колонка
в таблице и view, параметр в IUD-процедуре, строка в `iTableAlias`, XML в
`iEntity.passport`). Это точка максимального рычага, вокруг которой строится
весь план.

## 3. Где реально проходит граница «UI / не-UI»

Требование «менять только UI» в буквальном виде невыполнимо: граница в коде не
проведена. Факты по `Client/Classes` (85 файлов):

- 54 файла ссылаются на `System.Windows.Forms` / `System.Drawing`;
- **56 вызовов `ShowDialog` и 55 обращений к `DialogResult` находятся внутри
  доменных классов**: `Action.cs`, `ActionOnMassmedia.cs`, `Campaign.cs`,
  `Agency.cs`, `ActionRoller.cs`, `ActionRollerInStatJournal.cs` и др.
  Пример: `Client/Classes/Action.cs:383` — доменный метод сам открывает
  `FrmDateSelector`, блокируется и читает `DialogResult`;
- 52 обращения к `Cursor.` и 51 `Application.DoEvents()` — шум, удаляется
  механически;
- базовый класс всех сущностей `FogSoft.WinForm/Classes/PresentationObject.cs`
  импортирует `System.Windows.Forms` и содержит `ShowPassport(IWin32Window)`;
- `FogSoft.WinForm/Globals.cs` — статический класс, наполовину UI
  (`MdiParent`, `ShowSimpleJournal`, `SetWaitCursor`, `CopyToClipboard`,
  `ShowMessageError`), наполовину полезные утилиты
  (`ResolveFilterInitialValues`, `SetParameterValue`, `CreateIDs`).

Это **не** повод переписывать бизнес-логику: расчёты и последовательность
вызовов процедур сохраняются один в один. Но каждый из ~56 сайтов с диалогом
придётся разрезать на «подготовить варианты» и «выполнить с выбором
пользователя». Работа делается **в существующем десктопе**, не ломая его
(этап 0).

### 3.1. Глобальное состояние

В десктопе на процесс приходится один пользователь, поэтому статика безопасна.
В вебе она становится общей на всех:

| Место | Сейчас | Что делать |
|---|---|---|
| `FogSoft.WinForm/Classes/SecurityManager.cs:97` | `private static User loggedUser` | хранилище → `AsyncLocal`, публичный API без изменений |
| `FogSoft.WinForm/DataAccess/DataAccessor.cs:88` | `[ThreadStatic] private static SqlTransaction _transaction` | `AsyncLocal` (`[ThreadStatic]` ломается на первом `await`) |
| `FogSoft.WinForm/DataAccess/DataAccessor.cs:89` | `[ThreadStatic] SqlParameter[] _commandParameters` | то же |
| `procedureConfigs`, `IMemoryCache`, `MessageAccessor`, `PassportLoader` | статические кэши | оставить как есть — read-only, общие для всех, это корректно |
| `EntityManager` (кэш сущностей) | статический кэш | **нельзя оставлять — исправлено 2026-09-10.** Строка ниже объясняет, почему первоначальное «оставить как есть, это корректно» было ошибкой |

**Поправка от 2026-09-10 (этап 1, права).** Кэш `EntityManager` в этой таблице
изначально стоял рядом с `procedureConfigs` как «read-only, общий для всех». Для
`procedureConfigs` это верно, для `EntityManager` — нет, и это дефект
безопасности, а не производительности: `EntityInfoRetrieve` принимает `@userID`
и в третьем результате отдаёт `dbo.IsActionEnabled(@userID, entityActionID)`,
то есть **в метаданные сущности вшиты права конкретного пользователя**
(`Entity.Action.IsEnabled`). При этом `FullLoadDictionaries` (включён по
умолчанию, в конфигах не переопределён) снимает метаданные всех сущностей разом
под тем, кто вошёл первым. Итог в вебе: **права первого вошедшего в процесс
достаются всем остальным до перезапуска.** Десктоп это не задевает — у него в
`Client/app.config` стоит `TestMode=true`, и `GetEntity` перечитывает сущность
при каждом обращении; в `FogSoft.Web/App.config` такой настройки нет.
Исправлено тем же приёмом, что и хранилище пользователя в этапе 0.2:
`EntityManager.SetEntityCache` — десктоп остаётся на прежнем статическом кэше,
веб подставляет свой, живущий на circuit (`WebEntityCache`).

Замена хранилища при сохранении сигнатур означает: **ни одно из 100+ мест
вызова не меняется**. Это главный пример «минимального изменения с
максимальным эффектом».

### 3.2. Транзакции — хорошая новость

Все явные `BeginTransaction` — 10 сайтов, все в UI-слое:
`Client/Forms/ActionForm.cs`, `CampaignForm.cs`,
`CreateActionMaster/ComboModulePlacementForm.cs`, `EditIssuesForm.cs`,
`Client/Controls/PackModuleGrid.cs`, `ProgramIssuesGrid2.cs`,
`RollerIssuesGrid3.cs`.

Проверено: begin/commit находятся внутри одного обработчика, **ни одна
транзакция не оборачивает пользовательский диалог**. Значит, каждая транзакция
целиком укладывается в один HTTP-запрос, переделывать границы не нужно.

### 3.3. Подключение к БД

Строка подключения — один SQL-логин `AdvertAgUser` на всё приложение, а
идентификация пользователя передаётся в процедуры параметром `loggedUserId`
(`DataAccessor`). Для веба это идеальная схема: не нужны ни персональные логины
в СУБД, ни impersonation, пул соединений работает штатно. Менять нечего.

## 5. Выбор технологии интерфейса

### 5.1. Рекомендация: ASP.NET Core + Blazor Server

Обоснование опирается на свойства именно этого кода, а не на общие соображения:

1. **Весь транспорт данных — `DataSet` / `DataTable` / `DataView`.** Решающий
   аргумент. SPA или подход «Razor плюс JSON-эндпоинты» потребуют
   конвертировать результат каждой из 271 процедуры в DTO — сотни новых классов
   и ровно та работа, которой требование №1 велит избегать. Blazor Server держит
   данные в процессе: `DataTable` биндится напрямую, без сериализации.
2. **`ShowDialog` → `await ShowDialogAsync()`.** Паттерн «открыл модальное окно,
   получил `DialogResult`, продолжил» воспроизводится почти дословно (модалка
   через `TaskCompletionSource`). 56 болезненных мест из раздела 3
   переписываются по одной строке каждое, а не разворачиваются в цепочку
   колбэков и маршрутов.
3. **Состояние экрана.** WinForms держит в памяти граф объектов (`Campaign`,
   `Action`, `DataTable` сетки). Blazor Server держит его так же — компонент
   живёт, пока открыта вкладка. Не нужна ни ре-гидратация состояния из БД на
   каждый запрос, ни дублирование состояния на клиенте.
4. **Метаданные → компоненты.** `PageControl.CreateInstance`, который сейчас по
   XML собирает дерево WinForms-контролов, переносится на `RenderTreeBuilder` —
   та же диспетчеризация по имени элемента.
5. **Один язык, один слой моделей.** Нет webpack, нет npm-бандла, нет
   REST-контрактов между слоями. Для команды с 60 000 строк C# и нулём строк
   фронтенда в этом продукте это и есть простота по критерию №5.

Условия применимости выполняются полностью: внутренняя система, десятки
пользователей, LAN/VPN, одна БД, нет требований мобильности и офлайна. Сейчас
пользователи работают через RDP к серверу — веб убирает этот слой вместе с
RDP-лицензиями и сессиями.

**Минусы, которые надо принять сознательно:**

- каждое действие — round-trip по WebSocket; на плохом канале заметно при вводе
  в сетке (лечится точечно локальным состоянием компонента);
- circuit удерживает память на пользователя (та же память, что сейчас держит
  форма, но на сервере и умноженная на число пользователей);
- нужен корректный сценарий переподключения после обрыва;
- у команды нет опыта Blazor.

### 5.2. Альтернатива: ASP.NET Core MVC + Razor + htmx

Минимум JS, без сборщика. Сложные сетки — по одному изолированному
JS-компоненту с JSON-эндпоинтом. Проще в эксплуатации и ближе к стеку соседнего
продукта компании (iTender: `net8.0`, Razor, jQuery, DataTables, Bootstrap,
webpack). Цена — необходимость DTO-слоя поверх `DataTable` и ручная разборка
диалоговых сценариев.

Выбирать этот вариант, если решено не рисковать с circuit-ами Blazor или если
приоритет — переиспользование опыта команды по iTender.

### 5.3. Отвергнутые варианты

- **SPA на React/Vue плюс REST API.** Максимальный объём работы, два языка,
  полный слой DTO поверх `DataTable`. Прямо противоречит требованию №1.
- **ASP.NET MVC 5 на .NET Framework 4.8.** Соблазнительно — можно сослаться на
  существующие сборки буквально как есть, включая Crystal Reports. Но это
  тупик: платформа в режиме поддержки, только Windows/IIS, второй продукт
  компании уже на .NET 8. Не рекомендуется.

### 5.5. Решение принято: Blazor Server (2026-08-23)

Раздел 5.1 был написан как предварительная рекомендация, до того как стали
известны обстоятельства самой разработки. Когда они выяснились, два пункта
исходного анализа пришлось пересмотреть — оба в пользу Blazor.

**Обстоятельства, которых не было в исходном анализе:**

- миграцию делает **один человек — автор исходной системы**, а не команда;
- его опыт веба: ASP.NET примерно десятилетней давности, **и WebForms, и MVC**;
  современный JS-стек (React и подобное) — нет;
- **сроков нет**, задача делается неспешно и качественно.

**Что это меняет:**

1. **Аргумент за Razor + htmx исчез наполовину.** Раздел 5.2 обосновывал этот
   вариант двумя условиями: «не рисковать с circuit-ами **или** приоритет —
   переиспользование опыта команды по iTender». Второго условия больше нет:
   команда iTender к этой работе отношения не имеет.

2. **«Риск circuit-ов» при честном сравнении разворачивается в плюс.** В
   разделе 5.1 минусами записаны «circuit удерживает память на пользователя» и
   «нужен сценарий переподключения». Сравнивать их надо не с абстрактным
   stateless-веб-приложением, а с тем, что работает **сейчас**: пользователи
   заходят на сервер **по RDP**. То есть постоянное stateful-соединение с
   сервером уже есть; сервер уже держит всё состояние UI, причём целой
   Windows-сессией с процессом `Merlin.exe` на пользователя; надёжность канала
   уже является предусловием работы; обрыв уже переживается переподключением.
   Circuit Blazor — тот же принцип, но на порядок дешевле: граф компонентов
   вместо сессии с процессом. **Память на пользователя не вырастет, а упадёт.**
   По той же причине снимается и минус про плохой канал: по каналу, на котором
   плохо работает Blazor, RDP сегодня работает хуже.

3. **Сетки решают, и решают в пользу C#.** Замер на 2026-08-23: из 19 контролов
   в `Client/Controls` — **14 сетки**, ~7000 строк без Designer, 46 обработчиков
   взаимодействия (клики по ячейкам, drag-drop, редактирование по месту, своя
   отрисовка); `DataGridView` фигурирует в 30 файлах, `SmartGrid` (1911 строк) и
   семейство `TariffGrid` — обёртки вокруг него. Перенос сеток — самый большой
   кусок работы, и он одинаково велик при обоих вариантах. Разница в языке: в
   Blazor это компонент на C# с прямым биндингом `DataTable`; в htmx, по самому
   же разделу 5.2, — «изолированный JS-компонент с JSON-эндпоинтом», то есть
   14 сеток, помноженных на свой JS и свой DTO-слой. Для команды с фронтендером
   это паритет; для одного разработчика без опыта современного JS — нет.

4. **Отсутствие сроков снимает главный минус Blazor.** «У команды нет опыта
   Blazor» из раздела 5.1 — это стоимость обучения, а не технический риск.
   Без дедлайна она приемлема. Важнее оказывается другое: когда помочь некому,
   ценно оставаться в одном языке, который знаешь давно.

**Опыт WebForms работает на нас напрямую.** Blazor Server — это, по существу,
stateful-компоненты с серверными обработчиками событий, то есть WebForms без
ViewState и постбэков; мысленная модель переносится и из WebForms, и из
WinForms. Опыт MVC даст синтаксис Razor, но привычку «request → controller →
view» придётся сознательно отложить: в Blazor состояние живёт между
действиями, и первое время это ломает интуицию.

**Что осталось честной ценой решения** (не отменяется выбором, просто принято):

- готового аналога `DataGridView` в вебе нет — сетки переписываются руками либо
  берётся сторонняя библиотека компонентов (MudBlazor, Radzen); это главный
  объём работы этапа 3;
- отладка обрывов circuit — новый навык (но заменяет собой возню с
  переподключением RDP, а не добавляется к ней);
- Crystal Reports на современном .NET не работает, нужен внешний сервис на .NET
  Framework — но это одинаково при любом выборе фронтенда, см. открытый
  вопрос №4.

### 5.4. Технические решения по инфраструктуре

- **Версия платформы — .NET 10** (выбрано 2026-08-23). На момент выбора это
  текущий LTS: выпущен 11.11.2025, фаза Active, поддержка до 14.11.2028.
  `.NET 8`, на котором изначально писался этот план и был поднят
  `FogSoft.Core`, к августу 2026 уже в фазе Maintenance (только исправления
  безопасности) и выходит из поддержки **10.11.2026** — стартовать на нём
  многолетнюю миграцию значило бы менять рантайм посреди работы. `FogSoft.Core`
  переведён на `net10.0`: сборка прошла без единого нового предупреждения,
  набор замечаний тот же, что был на `net8.0`.
- **SqlClient**: на .NET 10 пакет `System.Data.SqlClient` работает — на первом
  шаге не меняется ни один `using`. Переход на `Microsoft.Data.SqlClient` —
  отдельным шагом позже; учесть, что там `Encrypt=true` по умолчанию, что
  ломает текущие строки подключения.
- **log4net** работает на .NET 10 — формат и файл лога сохраняются
  (`docs/LOGGING.md`).
- **Разделяемые исходники**: чтобы не переносить файлы физически и не ломать
  сборку десктопа, ядро подключается в новый проект через
  `<Compile Include="..\FogSoft.WinForm\DataAccess\*.cs" Link="..." />`.
  Обе UI-платформы живут параллельно всю миграцию.

   неуспешном `ApplyChanges`.

**Находка по метаданным.** Все 17 объявлений `lookup` **в паспортах** на
`ArtvisDev` идут через `source`. Запасной путь `PageFieldLookUp` через атрибут
`entity` (`GetEntity(...).GetContent(...)`) в паспортах не встречается и не
перенесён; такой lookup не промолчит, а покажет «lookup с источником по
entity». Уточнение от 2026-09-17: в **фильтрах** эта форма как раз
используется (сущности 146, 1266, 1269), так что путь понадобится — см. типы
полей фильтра ниже.

**Находка, видимая только на живом прогоне.** У обязательного lookup-а пустого
пункта нет, и первая отрисовка нового объекта давала пустой список, а
сохранение отклонялось как незаполненное. Десктоп ведёт себя иначе: присвоение
`LookUp.DataSource` встаёт на первую строку и поднимает `SelectedItemChanged`,
то есть в процедуру уходит первая строка списка. Лечится явным
`PreselectRequired()`. Это ровно тот класс расхождения, ради которого критерий
этапа 2 требует сверки поле в поле, а не просто «экран открылся».

**Проверено вживую** (`sveta`, `ArtvisDev`, сущность 207 «Остаток», единственная

**Зависимые lookup-ы — проверено вживую (2026-09-18).** Написанное выше «маршрута
на них в вебе пока нет» устарело: движок древовидных экранов (см. «Древовидные

#### `objectPicker` — сделано (2026-09-17)

Второй контрол по покрытию: 11 сущностей. Выбор объекта другой сущности —
текстовое поле с именем выбранного и кнопки «Выбрать» / «Создать» / «Очистить».

Что понадобилось сверх самого контрола:

1. **Стек диалогов** (`DialogService`). Было ограничение «диалог уже открыт»,
   а objectPicker по своей природе открывает второй: выбор объекта — из уже
   открытой карточки, создание нового — ещё уровнем глубже. В десктопе это те
   же вложенные `ShowDialog` (`ObjectPicker2.btnSelect_Click` вызывается из
   открытой `PassportForm`), так что запрет был ограничением веба, которого в
   переносимой системе нет. Нижние диалоги остаются видимы, но кнопки у них
   погашены — закрыть можно только верхний.
2. **`ObjectSelector`** — веб-аналог `SelectionForm`: строки сущности и выбор
   одной, без фильтра, карточки и действий. Права на экран здесь не
   проверяются намеренно: в десктопе у выбора объекта нет своего пункта меню,
   доступ даёт уже открытая карточка. Это тот случай «доступно из родительского
   экрана», который предусмотрен в комментарии к `MenuAccess`.
3. **`PassportDialog`** — цикл «показать → проверить → сохранить» вынесен из
   `Journal.razor` в общий сервис, когда появился второй вызывающий: кнопка
   «Создать». Заодно заголовок карточки стал десктопным
   (`Новый: <сущность>` / `Свойства: <объект>` из `PassportForm.SetFormCaption`)
   вместо прежних «Новая запись» / «Редактирование».
4. **`PickerData`** — данные контрола: кандидаты (готовый набор по `source`
   либо `entity.GetContent(фильтры)`), значения вложенных `<filter>` и
   разрешение имени по сохранённому идентификатору.

**Находка в десктопе, перенесённая как есть.** `ObjectPicker2.LoadData`
собирает словарь `parameters` с начальными значениями фильтра сущности, а затем
передаёт в `GetContent` не его, а `filterValues` — собранное игнорируется.
Повторено фактическое поведение, а не намерение: иначе веб показывал бы другой
состав строк, чем десктоп. Кандидат на отдельный разбор, но не под этой задачей.

**Проверено вживую** (`sveta`, `ArtvisDev`):

- сущность 207 «Остаток», три `objectPicker` подряд (фирма, менеджер,
  агентство) — выбор в каждом, показ имени, сохранение. Создана тестовая

- повторное открытие той же записи — имена всех трёх выбранных объектов

- «Очистить» снимает выбор; после этого «Сохранить» отклоняется сообщением

  обязательным для заполнения»), и процедура **не вызывается** — в логе только
  `MessageLoad`. Так закрыт пункт, оставшийся непроверенным после `lookup`;
- «Создать» открывает карточку другой сущности третьим уровнем диалога
  (`Новый: Фирмы` поверх `Свойства: Остаток`), отмена возвращает на карточку
  без записи;
- сущность 16 «Фирмы», два других `objectPicker` (банк, группа компаний):
  имя группы разрешилось из базы, список банков открылся своим составом

**Не проверено вживую и почему:**

- **Кандидаты из готового набора** (`source`) и **вложенные `<filter>`**. Обе
  возможности есть только у сущностей 145 «Платеж», 20 и 1244 «Ролик», а из
  веб-меню достижимы лишь 16 и 207, где `source` не задан и фильтров нет.
  Проверено только то, что путь по `source` не мешает работать лениво
  загружаемому.
- **`relationScenario`** (выбор из дерева, `TreeViewSelector`) не переносился:
  в метаданных `ArtvisDev` нет ни одного такого `objectPicker`. Если появится —
  контрол покажет причину, а не промолчит.

**Мелкое расхождение, оставлено сознательно.** После отказа в сохранении веб
закрывает и заново открывает диалог, поэтому имена в `objectPicker` заново
разрешаются из базы (два лишних вызова процедуры на неуспешное сохранение).
Десктоп форму не закрывает и не перезапрашивает. Чтобы убрать, диалог должен
уметь оставаться открытым и показывать ошибку сам, — это изменение
`DialogService`, а не контрола.

#### Типы полей фильтра — сделано (2026-09-17)

До этого фильтр понимал только `boolean`, всё остальное показывал как «пока не
поддержан». Теперь поддержаны `string`, `int`, `decimal`/`money` и `df_date`,
то есть все типы `<field>`, встречающиеся в фильтрах достижимых журналов.

Тип разрешается ядровым `FieldTypeResolver` по тому же правилу, что в
`PageField.CreateInstance`: сначала атрибут `type`, затем тип колонки сущности.

**Галочка «использовать».** В десктопе левая колонка фильтра — не подпись, а
`CheckBox` (`PageField.CreateControlInLeftColumn` при `PageTypes.Filter`), и
параметр уходит в процедуру только когда он отмечен (`ValueShouldBeSet`), а
неотмеченный из словаря удаляется. Отмечен он изначально тогда, когда значение
есть (`PageField.SetValue`), то есть когда его дали метаданные через атрибут
`value`. Всё это повторено: в вебе признак «используется» — наличие ключа в
словаре фильтра.

**Почему это стоило сделать раньше остальных контролов.** Без типов полей
журнал фирм отдавал все 6993 строки, журнал удалённых выпусков — 40521:
отфильтровать их было нечем. Движок один на все 15 достижимых журналов.

**Проверено вживую** (`sveta`, `ArtvisDev`): `string` — «Банк», часть названия
«сбер», 373 → 37; `df_date` — «Фирмы», последний выпуск после 01.09.2026,
6993 → 122; `int` — «Удалённые выпуски», № акции 185937, 40521 → 40;
`decimal` — «Менеджерский коэффициент», коэффициент ниже 0.5, 5224 → 251.
Неотмеченное поле в вызове процедуры отсутствует целиком. Значения из
метаданных (`LAST_WEEK`, `TODAY`, `StartOfTheMonth`) проставляются и сами
включают галочку.

**Две находки живого прогона, обе про раздел 7 п.5.** Пункт про культуру и
форматы оказался шире, чем звучал: тихие расхождения даёт не только дата, а
любой HTML-инпут со своим форматом.

1. **Дробные числа.** `<input type="number">` по стандарту всегда отдаёт точку,
   а разбор параметра идёт в культуре системы, где разделитель — запятая. Ввод
   «0.5» валил экран сообщением «The input string '0.5' was not in a correct
   format». Даты переводились с самого начала, числа — нет, потому что в первых
   трёх проверенных журналах дробных полей не было. Теперь переводятся оба
   типа, целые не трогаются: разделителя у них нет.
2. **Неподдержанный контрол притворялся полем ввода.** `lookup`, у которого
   источник задан атрибутом `entity`, а не `source`, разбор не строит — и поле
   проваливалось в общую ветку `<field>`, превращаясь в поле для ввода текста.
   В `massmediaGroupId` можно было вписать что угодно и отправить в процедуру.
   Лечится проверкой `Unsupported` до всех остальных веток.

**Попутно исправлено утверждение из раздела про `lookup`.** «Путь через атрибут
`entity` в реальных данных недостижим» верно только для паспортов. В фильтрах
эта форма используется — сущности 146, 184, 1266, 1269, — так что источник
списка по сущности всё-таки понадобится, вместе с остальной работой по
`lookup`/`objectPicker` в фильтре.

**`lookup` и `objectPicker` не сделаны на момент этого коммита** — см. отдельный
подраздел ниже, тем же днём.

#### `lookup` и `objectPicker` в фильтре — сделано (2026-09-17)

Достраивает движок фильтра: до этого оба контрола показывали «пока не
поддержан» в фильтре, хотя в паспорте `objectPicker` уже работал, а `lookup` —
только через `source`.

**1. Источник данных фильтра — перенесён в ядро.** `Globals.PrepareForFilter`
(UI-половина, звала `EntityId_Load_FilterPage`) зависела только от
`DataAccessor` — ровно тот же случай, что `PresentationObject.LoadPassportData()`
на шаге про `lookup` в паспорте. Перенесена в `Globals.Core.cs` без изменений
(`FogSoft.WinForm/Globals.cs` → `Globals.Core.cs`), UI-половина зовёт её же.
Веб грузит набор один раз на открытие журнала, и только если в фильтре
реально есть `lookup`/`objectPicker`, которым есть куда его девать — иначе
лишний поход в базу.

**2. Запасной путь `lookup` по `entity`.** В паспортах эта форма недостижима
(см. запись про `lookup` выше), но в фильтрах используется на сущностях 146,
1266, 1269. `PageFieldLookUp` не различает контекст (`GetEntity(...).GetContent(...)`
работает и в паспорте, и в фильтре одинаково), но веб — различает: `lookup`
без `source` помечен `Unsupported` в паспорте и разрешён в фильтре
(`PassportSchema.Parse` получил параметр `PageTypes pageType`). Это сознательное
отступление от буквального повторения десктопа, а не недосмотр: в паспортах
такой `lookup` не встречается ни разу, сверить реализацию не с чем, а правило
всей этой работы — «непроверенное остаётся непроверенным», а не «работает,
раз код одинаковый». `PassportLookup.Source`/`EntityName` стали нолабельными,
плюс `Filters` для вложенных `<filter>` — тем же разбором, что у `objectPicker`.

**3. `PageTypes` не было в `FogSoft.Core`.** Перечисление лежит в
`PageContext.cs` (`FogSoft.WinForm/Passport/Classes/`), который до этой правки
не подключался мостом — только соседний `PageControl.Constants.cs`. Файл
оказался без UI-зависимостей (`System.Data`, `PresentationObject`, `Entity`),
подключён тем же приёмом `<Compile Include>` в `FogSoft.Core.csproj`.

**4. Поведение в режиме фильтра, оба контрола.** Галочка «использовать» —
как у обычных полей (ключ в словаре фильтра). `lookup` без пустого пункта
(десктопное `Lookup.IsNullable = isNullable && PageType == Passport`, то есть
всегда `false` в фильтре): при отметке галочки в фильтр сразу подставляется
типизированное значение первой строки списка (`InitialFilterValue`), а не
пустая строка, — иначе `<select>` визуально показывал бы первую строку (так
ведёт себя HTML `<select>` без пустого пункта), а в процедуру уходило бы
пустое значение. `objectPicker` пустого выбора не боится (десктопный
`ApplyChanges` при `SelectedObject == null` просто не пишет параметр) —
значение остаётся `DBNull.Value`, пока не нажали «Выбрать»; `DBNull.Value`
выбран, а не пустая строка (как у обычных полей), потому что `objectPicker`
— это всегда типизированный идентификатор, а не текст, и пустая строка
рисковала бы упасть на конвертации типа параметра. Кнопки «Создать» у
`objectPicker` в фильтре нет вовсе, независимо от `isCreateNewAllowed`
(`PageFieldObjectPicker` гасит её при `PageTypes.Filter`) — в разметке
фильтра эта кнопка просто не рисуется.

**5. Переиспользование.** `PickerData.Candidates`/`Filters` — параметр
`owner` стал нолабельным (в фильтре нет редактируемого объекта, значит нет и
значений `parameter`/`parameter_isnew`); добавлен `PickerData.LookupRows` —
источник по `source`, иначе `entity.GetContent(Filters(...))`, тот же порядок,
что у `PageFieldLookUp`. `ObjectSelector.Owner` тоже стал нолабельным: диалог
выбора один и тот же что у паспорта, что у фильтра.

**Кэш на время жизни компонента.** И запасной путь `lookup` по `entity`, и
разрешение имени `objectPicker` бьют в базу — `Journal.razor` кэширует оба
по имени поля (`_filterLookupCache`, `_filterPickerNames`), иначе каждый
перерендер страницы (например, ввод в соседнем поле) читал бы их заново;
кэш сбрасывается в `OnParametersSet` при смене сущности.

**Проверено вживую** (`sveta`, `ArtvisDev`, все четыре экрана из плана):

- **«Менеджерские скидки»** (сущность 1266, Администрация; без процедуры

  `objectPicker`: «Фирма» (`entity=firm`, без `source`) — выбор «100 АПТЕКА»

колонки не было, упал бы весь фильтр с `DataException`, и ловить это можно
было только живым прогоном, не чтением метаданных.

**Не проверено вживую и почему:**

- **Вложенный `<filter>` типа `parameter`/`parameter_isnew`** для `lookup`
  или `objectPicker` в фильтре. В реальных метаданных фильтров такой тип

- **Зависимый `lookup`** (`parentLookupName`) в фильтре. В реальных
  метаданных фильтров ни один `lookup` зависимость не объявляет — только в

  непроверено). Код `PassportLookup.ParentLookupName`/`ParentFilter`
  разбирается общим для паспорта и фильтра путём, но в фильтре ветка
  `ResetDependent`-подобной пересборки не написана вовсе — если понадобится,
  делать вместе с проверкой на реальном экране.

Этим движок фильтра закрыт: все контролы паспорта и все контролы фильтра,

#### `selector` — сделано (2026-09-17)

Набор дочерних объектов с галочками: 4 сущности (8, 9, 107, 109). Веб-аналог
`ObjectsSelector` — грид `SmartGrid` с `CheckBoxes`.

Строки берутся готовым набором из процедуры паспорта (у `selector`, в отличие
от `objectPicker`, запасного пути по `entity` нет вовсе), состояние галочки — в
колонке `isObjectSelected`, которую заполняет сама процедура
(`massmediaPassport`: `CASE WHEN am.massmediaID IS NULL THEN 0 ELSE 1 END`).
Отмеченное и снятое копятся двумя списками ровно так же, как в
`SmartGrid.CheckedStatusChanged`: повторная отметка снятого не добавляет
объект, а убирает его из снятых. По сохранению списки уходят в
`IParentObject.SetChildrenChanges` — дословно `ObjectsSelector.ApplyChanges`.

**Мина, которую пришлось обезвредить.** Записывает накопленное `Update()`
доменного класса, а у `Massmedia` весь этот override лежит в
`Massmedia.WinForms.cs` — в сборку без UI не попадает. В вебе вызвался бы
базовый `PresentationObject.Update()`, галочки сохранились бы «успешно» и
пропали. Переносить `Update()` в ядро целиком нельзя: он начинается с проверки
лицензии, а та показывает диалог.

Решение без изменения лицензирования: в `ObjectContainer` добавлен виртуальный
`SubmitChildrenChanges()`, по умолчанию пустой. Тело записи связей переехало из
`Massmedia.WinForms.cs` в `Massmedia.cs` как его переопределение; десктопный
`Update()` теперь зовёт его вместо своего цикла — поведение то же. Веб зовёт
сам, сразу после `Update()`. Порядок одинаковый: отдать накопленное объекту до
сохранения, записать в базу после — связь пишется по идентификатору родителя,
которого у нового объекта до `Update()` ещё нет.

**Проверка лицензии осталась в десктопе.** Веб её не делает — ни при входе, ни
по таймеру, ни при добавлении радиостанции; так было и до этой работы. Это
открытый вопрос №3, и решать его должен владелец продукта. Отдельно стоит
учесть: при параллельной работе десктопа и веба лимит числа станций перестанет
быть надёжным — станцию можно будет добавить из браузера в обход проверки.

**Проверено вживую** (`sveta`, `ArtvisDev`, «Авторадио (Переславль)»,
`massmediaID = 199`): список агентств открылся, связанное агентство 242 стояло
отмеченным; снял его, отметил 259, сохранил — в логе ровно два вызова
`AgencyMassmediaID` (`AddItem` для 259, `DeleteItem` для 242), в базе осталась
одна связь 199 → 259. Повторное открытие показало новое состояние с
отмеченной строкой первой (процедура сортирует по `isObjectSelected desc`).
Затем вернул как было — 199 → 242, состояние базы совпадает с исходным.

**Не проверено:** `multiselect="false"` (в метаданных нет ни одного такого
selector-а, список рисуется без галочек и только для чтения) и селекторы
сущностей 107/109 — на них в вебе нет маршрута.

#### `image` — сделано, `button` — переносить нечего (2026-09-17)

**`image`** (сущности 8 и 9). Картинка показывается data-URL-ом, заменяется
обычным файловым вводом, очищается кнопкой — как `PageFieldImage` с его
`OpenFileDialog` и `BtnDelete_Click`. Высота показа берётся из атрибута
`height`, умолчание 60 точек — то же, что в десктопе.

Два решения, которые стоит знать:

- **Байты кладутся как есть, без перекодирования.** Десктоп сохраняет через
  `Image.Save(stream, ImageFormat.Bmp)`, но читает через `Image.FromStream`,
  который разбирает и PNG, и JPEG. Значит перекодирование потребовало бы
  `System.Drawing` на сервере и ничего бы не дало.
- **Тип для показа определяется по сигнатуре файла**, а не по расширению: в
  базе лежит то, что когда-то записал десктоп (BMP), а загрузить могут что
  угодно.

**Главный риск был не в показе, а в сохранении.** Байты картинки приезжают в
`Parameters` из строки журнала и уходят обратно нетронутыми — так было и до
этой работы, пока контрол был помечен неподдержанным. Правка не должна была
этот транзит сломать, поэтому значение не трогается, пока пользователь ничего
не сделал.

**Проверено вживую** (`sveta`, `ArtvisDev`, «Авторадио (Переславль)»,
`massmediaID = 199`, подпись 127926 байт BMP):

1. подпись видна на странице «Подписи», браузер разобрал её как `image/bmp`,
   216×148;
2. **сохранение карточки без трогания картинки оставило `painting` байт в
   байт** — контрольная сумма совпала с резервной копией;
3. «Очистить» + сохранение — в процедуру ушло `@painting = NULL`, колонка
   стала NULL;
4. загрузка PNG 40×20 + сохранение — в базе 138 байт с сигнатурой `89504E47`,
   то есть файл лёг без изменений, и показался он уже как `image/png`;
5. исходная подпись восстановлена из резервной копии, контрольная сумма
   совпадает, временная таблица удалена.

**`button` не переносится.** Сам `PageButton` пустой: `SetValue` и
`ApplyChanges` ничего не делают, обработчика клика в нём нет. Поведение живёт в
форме паспорта ролика: `RollerPassportForm.FormBuildCompleted()` находит
контрол по имени и вешает обработчик, который открывает диалог выбора звукового
файла, меряет длительность через `AudioFileReader` (NAudio) и кладёт в параметр
`path` **локальный путь к файлу на диске пользователя**. Ни одна часть этого не
принадлежит движку паспорта: локальный путь в вебе смысла не имеет, NAudio на
сервере — это раздел 4.4 и этап 4, а сама форма ролика с блокировками полей по
`IsUsed` — этап 3. Обе сущности с `button` (20 и 1244) в веб-меню всё равно
недостижимы. Кнопка, которая ничего не делает, хуже сегодняшней честной
пометки, поэтому контрол остаётся неподдержанным до порта экрана ролика.

#### Внешний вид: дизайн-система (2026-09-17)

Перерыв в переносе движков: весь визуальный слой до этого был **нетронутым
шаблоном Blazor** — 262 строки шаблонного CSS, фиолетовый градиент в меню,
бренд «FogSoft.Web» и ссылка «About» на `learn.microsoft.com` в шапке, а

**Решение по основе принято владельцем продукта:** своя дизайн-система поверх
уже подключённого Bootstrap, **без библиотеки компонентов**. Альтернатива
(MudBlazor / Radzen / Fluent UI Blazor) закрыла бы разом и вид, и три
оставшихся движка — грид с постраничностью и сортировкой, дерево,
master-detail, — но это новая зависимость на весь UI против требований №1 и №7.
Развилку прошли сознательно и в последний дешёвый момент: если решать позже,
написанные вручную движки придётся выбрасывать.

Правила системы записаны в самом `wwwroot/app.css`: шаг сетки 4px, плотность
выше дефолтной (Bootstrap рассчитан на сайты, а не на таблицы в тысячи строк),
нейтральная база и один приглушённый акцент, табличные цифры, липкая шапка
таблиц, видимый фокус, единый вид состояний «загрузка / пусто / ошибка / нет

#### Хвосты журнала: виртуализация, сортировка, удаление (2026-09-17)

**Процедуры не тронуты.** Все три доработки — в слое отрисовки; в ядре одна
правка видимости (`PresentationObject.DeleteConfirmationText` стал публичным).

**Замер до работы** — журнал удалённых выпусков, 40 521 строка:

| | До | После |
|---|---|---|
| Первая отрисовка | ≈ 30 с | ≈ 1 с |
| Узлов в DOM | 405 409 | 1 328 |
| Память браузера | 111 МБ | 4 МБ |
| Отклик на клик (свернуть панель отбора) | 1 837 мс | **39 мс** |

Последняя строка была решающей: полторы-две секунды на каждое нажатие, потому
что Blazor Server считает разницу по всему дереву. Процедура при этом отдаёт те
же строки за десятки миллисекунд — узкое место чисто в отрисовке.

**Это уточняет записанное правило «тормоза в qd2 всегда от SQL, не от объёма».**
Для десктопа оно верно: WinForms-грид держит 40 тысяч строк спокойно. Веб
вносит новое узкое место, которого в десктопе нет. Раздел 7 п.4 плана это
предсказывал; теперь измерено, а не предположено.

**Решение владельца продукта: виртуализация, не постраничность.** Постраничности
в десктопе нет вовсе, прокрутка идёт по всему списку — страницы были бы не
переносом поведения, а выдумыванием нового. Серверную постраничность
(`OFFSET/FETCH` плюс `@pageNumber`/`@pageSize`) отвергли отдельно: она меняет
контракты процедур, общие с десктопом, против требований №2 и №4.

Цена виртуализации: строки обязаны быть одной высоты, поэтому ячейки больше не
переносятся — длинные значения обрезаются, полный текст во всплывающей
подсказке. Десктопный грид ведёт себя так же.

**Сортировка** — на клиенте через `DataView.Sort`, как `SmartGrid` отдаёт её
`DataGridView` (`SortMode.Automatic`); в процедуру ничего не передаётся.
Сортируем через `DataView`, а не по строковому виду значений, иначе числа и
даты выстроились бы лексикографически.

**Удаление** потребовало разреза «спросить / сделать» — конвенция этапа 0.
Десктоп спрашивает изнутри `Delete()` через `UserInteraction.Confirm`
синхронно: модальная форма блокирует поток. В вебе circuit блокировать нельзя,
поэтому веб спрашивает своим диалогом и зовёт `Delete(silenceFlag: true)`.
Текст вопроса тот же — `DeleteConfirmationText` доменного класса, включая
переопределение у `ActionOnMassmedia`; ради этого он и стал публичным.

Попутно выяснилось: `UserInteraction.SetConfirmHandler` в вебе не назначен
вовсе. Шов спроектирован падать громко, а не удалять молча, так что до этой
работы удаление упало бы с внятным сообщением. `SetNotifyHandler` тоже не
назначен — любой путь ядра, зовущий `Notify`, в вебе упадёт. Отдельная мина,
искать при переносе специализированных экранов.

**Проверено вживую** (`sveta`, `ArtvisDev`): замеры выше сняты на одном и том
же экране до и после; сортировка по «Времени» работает в обе стороны с
пометкой направления; удаление тестовой записи «Остаток» `actionID = 185963`
(созданной при проверке `objectPicker`) — диалог показал десктопный текст
«Эта операция приведет к удалению объекта 'Остаток № 185963' из системы.

#### Панель отбора: общий компонент для журнала и дерева — сделано (2026-09-17)

Закрывает хвост предыдущего пункта: та же операция, что раньше была проделана
со списком (коммит `c15fd53`, `Journal.razor` → `ObjectList.razor`), теперь
проделана с отбором — `FilterPanel.razor` (+`FilterPanel.razor.css`).

Из `Journal.razor` уехали разметка между комментариями `Фильтр`/`Список`,
поле `_filterOpen`, кэши `_filterLookupCache`/`_filterPickerNames`/
`_filterPickerNamesFor` и 15 методов отбора (`GetFilterBool` … `SelectFilterPicker`,
плюс безымянный в списке задачи `IsFractional` — приватный помощник только
этих методов, без него они не собрались бы). `NeedsFilterData` остался у
каждого владельца экрана, как и было решено: он выбирает источник набора
строк, а источник у журнала и у дерева разный.

**Кэш переехал вместе с методами, но точка сброса — другая.** В `Journal.razor`
кэши чистились явно в `OnParametersSet` при смене сущности. Компонент такого
сигнала не получает — только новое значение параметра `Pages`. Решение: та же
идея, что уже есть в `ObjectList` для `Data` (`_sorted` vs `Data` по
`ReferenceEquals`) — `FilterPanel` сравнивает пришедший `Pages` с тем, для
которого кэш собирался, и чистит кэш только при смене ссылки. Ссылка меняется
ровно тогда, когда владелец заново вызывает `PassportSchema.Parse` (смена
сущности в журнале, смена сценария/навигация в дереве), а не на каждом
перерендере экрана — иначе кэш EntityName/objectPicker-имён бесполезен.

**Значения фильтра — тот же словарь, без копирования**, как и было
сформулировано: `Values` меняется на месте. У журнала это тот же
`_filterValues`, что и раньше. У дерева — `container.Filter`
(`FakeContainer`/`ObjectsIterator._filter`), который контейнер сам заполнил
начальными значениями в конструкторе (`Globals.ResolveFilterInitialValues`);
второй раз не заполняется.

**Подключение к дереву** (`Browser.razor`): страницы отбора —
`PassportSchema.Parse(scenario.XmlFilter, scenario.StartingEntity, pageType: PageTypes.Filter)`,
но только если `container.IsFilterable` (иначе `Array.Empty<PassportPage>()` —
`FilterPanel` сама не покажется на пустом списке страниц, ровно как раньше
скрывалась внутри `Journal.razor`). Набор строк для lookup/objectPicker —
`Globals.PrepareForFilter(scenario.StartingEntity)`, вызывается только если
`NeedsFilterData` (та же логика, что у журнала, продублирована — не общий
метод, по тем же причинам, по которым `NeedsFilterData` не переехал в
компонент).

**Ловушка, ради которой в задаче был отдельный абзац, подтвердилась на
практике.** Первая версия проверки применяла отбор через `RefreshSelected()`
(перечитать выбранный узел) — список менялся, а раскрытые ветви дерева

перечитывать.

**Стили.** Секция `/* ---------- Отбор ---------- */` переехала в

#### Хвост: `ObjectList` рисовал пустые колонки — исправлено (2026-09-17)

Найдено не этой задачей, а по вопросу пользователя «почему в журнале
„Радиостанции“ на дереве и на десктопе разный набор колонок» — сущность
(`entityID = 9`) и процедура загрузки (`massmediaList`, единственная запись в
`iModuleProcedure` для `Load`) у обоих экранов одни и те же, значит дело не в
данных, а в отрисовке.

**Причина.** `massmediaList` в обычной ветке селектит `mm.*` из `vMassmedia`,
а в этом view нет `executorName`/`extraChargeFirstRoller`/
`extraChargeSecondRoller`/`extraChargeLastRoller` — при этом
`iEntityAttribute` для `selector = 0` их объявляет. Десктопный `SmartGrid`
такие атрибуты пропускает (`SmartGrid.SetColumnHeaders`:
`if (columns.Contains(entityAttribute.Name)) AddColumn(...)`), а
`ObjectList.razor` рисовал заголовок для каждого атрибута метаданных
безусловно — отсюда 4 лишних, всегда пустых столбца в вебе там, где десктоп
их не показывает вовсе. Дефект не из этой задачи — жил с коммита `929bc18`
(«Журнал: виртуализация, сортировка, удаление»), задевал все журналы и
деревья, где метаданные и процедура расходятся хотя бы по одной колонке.

**Фикс.** `Columns` в `ObjectList.razor` фильтрует `Entity.SortedAttributes`
по `Data.Columns.Contains(a.Name)` — тот же критерий, что у `SmartGrid`,
одной строкой на оба места использования (`<thead>` и `<tbody>` используют
один и тот же список, поэтому синхронизировать нечего).

**Проверено вживую** (`sveta`, ArtvisDev, дерево «Рекламные тарифы» → узел
«Радиостанция»): подтверждено пользователем — лишние пустые колонки
(«Медиа-планер», три «Наценки») пропали, состав совпал с десктопным.

#### Хвост: `ObjectList` писал «True»/«False» текстом — исправлено (2026-09-17)

Тем же разбором задет соседний вопрос: колонка «Активный объект» в списке
показывала литеральные `True`/`False`. Десктоп для boolean-колонок текст не
рисует вовсе — `SmartGrid.CreateDataGridColumn` ставит
`DataGridViewImageColumn` с `DataGridViewExBooleanCell`: галочка при `true`,
пустая ячейка при `false`. Признак boolean-колонки берётся из
`ColumnInfo.IsBooleanData(columnInfo, attribute)` — чистая проверка по
метаданным (`attribute.DataType`/`columnInfo.DataType == "bit"`), без
UI-зависимостей, уже в `FogSoft.Core`.

**Фикс.** `ObjectList.razor` переиспользует тот же `ColumnInfo.IsBooleanData`:
для boolean-колонки рисуется `<span class="bool-check">✓</span>` только при
`true`, при `false` — пусто, как у десктопа. Текстовое представление
(`Display`) для boolean тоже поправлено — «Да»/пусто вместо `ToString()`,
остаётся источником для `title` и для не-boolean колонок.

**Проверено вживую** (`sveta`, ArtvisDev): подтверждено пользователем на
журнале «Радиостанции» — колонка «Активный объект» показывает галочку вместо
`True`.

**Тот же хвост нашёлся во втором месте — selector-грид карточки.** Список
дочерних объектов на вкладке паспорта (`selector`, например «Агентства» у
радиостанции) — не `ObjectList`, а отдельная копия разметки таблицы в
`Passport.razor`, со своей функцией вывода ячейки (`CellText`/`AsText`,
голый `ToString()`). Десктопный `ObjectsSelector` тоже построен на
`SmartGrid`, значит там уже была галочка — а веб показывал `True`/`False`
текстом ровно по той же причине, что и в `ObjectList` до фикса выше.
Исправлено тем же приёмом: `IsBooleanColumn(field, attribute)` — та же
`ColumnInfo.IsBooleanData`, только сущность берётся из
`field.Selector.EntityName`, а не из параметра компонента (это отдельная,
не связанная с `PassportField.Unsupported`-веткой проверка
`IsBoolean(PassportField)`, которая решает тип обычного поля паспорта по
`XmlType`, а не тип колонки строк selector-грида). Проверено вживую
(`sveta`, ArtvisDev, карточка радиостанции → «Агентства») — подтверждено
пользователем.

**Все найденные расхождения — один и тот же класс дефекта, что и в трёх
более ранних хвостах этой задачи** (`True`/`False` текстом в `ObjectList` и
в selector-гриде карточки): движок паспорта и списка узнаёт тип поля из
`FieldTypeResolver`/`ColumnInfo`, но при отрисовке использовал этот тип не
везде. Три новых места:

**1. Boolean-поле паспорта.** `Passport.razor.IsBoolean(field)` проверял
только явный атрибут `type="boolean"` в XML. Десктопный
`PageField.CreateInstance` решает через `FieldTypeResolver`: атрибут
`type`, а если его нет — тип колонки (`bit` → `PageFieldBoolean` →
`CheckBox`). У `isActive` (сущности 9, 16) и у дней недели спонсорского
тарифа (`monday`...`sunday`, сущность 14) `type` в XML не задан вовсе —
поле проваливалось в обычный `<input>` и показывало литеральное `True`.
Фикс — `IsBoolean(f) => f.Type?.IsBoolean == true`: `field.Type` уже считает
это правило (`PassportSchema.ResolveType`), просто не был использован.

**2. Дата/время в паспорте показывали ToString() целиком.** Ни один из
специальных контролов десктопа (`PageFieldDate` — `DateTimePickerFormat.Short`,
только дата; `PageFieldTime` — `Custom "HH:mm"`, дата-заглушка 01.01.1900)
не имел пары в вебе: любое поле, не lookup/objectPicker/boolean/selector/
image, рисовалось обычным текстовым `<input>` со значением
`AsText(Object[name])`, то есть голым `DateTime.ToString()`. Для дат
(сущности 134, 22 — `startDate`/`finishDate`) это давало «01.01.2026
0:00:00» вместо «01.01.2026»; для времени (сущность 14, поле `time`) —
дату-заглушку вместо чистого «13:00». Фикс — два новых контрола,
`<input type="date">` и `<input type="time">`, тем же приёмом перевода
ISO ↔ культура, что уже есть в `FilterPanel.GetFilterText`/`SetFilterText`
для `df_date`; признак — тот же `field.Type.IsDate`/`IsTime`.

**3. Деньги и decimal в списках — без формата.** Десктопный
`SmartGrid.CreateDataGridColumn` ставит `Style.Format = "c"` (валюта, ₽,
разделитель тысяч) для money-колонок (`ColumnInfo.IsMoneyData`:
`money`-тип, либо `decimal(18,2)`) и `"f"` (два знака, без разделителя
тысяч) для остальных decimal/float. `ObjectList.razor.Display` этого не
делал — голый `ToString()` давал «8000,00» вместо «8 000,00 ₽». Задета
любая денежная колонка в любом журнале/дереве, не только эти три сущности
— просто на них она попалась под сверку (цена тарифа/прайс-листа, сумма
скидки, сумма платежа). Фикс переиспользует те же `ColumnInfo.IsMoneyData`/
`IsFloatData`, что уже в `FogSoft.Core`, и форматирует `Convert.ToDecimal(v)`
через `"C"`/`"F"` — те же стандартные строки формата .NET, что стоят за
десктопными `"c"`/`"f"`.

**Что не тронуто и почему.** Числовые поля паспорта (decimal/int, например
«Цена:», «Скидка:») уже показывали правильный текст без правки: десктопный
`PageFieldNumeric` — это `NumericUpDown` без `ThousandsSeparator`, то есть
без разделителя тысяч и без символа валюты, только знаки после запятой —
ровно то, что уже даёт голый `decimal.ToString()`. Формат `"c"`/`"f"` нужен
только спискам (`DataGridView`), не карточке. Значит value-текст «450,00»,
«8000,00», «0,8000» в карточках — это не расхождение, а совпадение,
которое сверка обязана была проверить, а не предположить.

**Четвёртый и пятый фикс — по итогам обсуждения с пользователем, тем же
днём.** Изначально в этом разделе стояли как открытые вопросы владельцу
продукта; при уточнении оказалось, что оба — не развилки, а обычные

**4. `label` — оказался в объёме этапа 2, а не вне его.** Черновая версия

##### Правило ManagerFilter

**Десктоп.** `JournalForm` при заданном делегате `OnFilterClick`
использует **только** его вместо `Globals.ShowFilter` (комментарий в
`tsbFilter_Click`); `ManagerFilter` создаётся с теми же
`Globals.PrepareForFilter(entity)` и `entity.XmlFilter`, что и обычная форма,
и после `base.OnLoad` делает одно: если найден контрол `managerID` (иначе
`userID`) типа `ObjectPicker2` и его галочка `*_checkbox`, то
`Enabled = IsRightToViewForeignActions() || IsRightToViewGroupActions()`.
Начальных значений он не задаёт и не сбрасывает: `managerID=LoggedUser` у
сущностей 146 и 184 приходит из метаданных, поэтому заблокированное поле
остаётся отмеченным и стоит на самом пользователе.

**Веб.**

- признак — `JournalRoute.ManagerFilter` в `MenuRoutes.SimpleJournal`, рядом
  с маршрутом, а не отдельным списком сущностей: правило привязано к пункту
  меню (у 146 оно есть через `miPaymentByManagerFromRSection`, а тот же 146
  через `miPaymentByManager` открывается другим экраном). Пункт меню
  передаётся в `Journal.razor` параметром `?menu=`; если он не сходится с
  сущностью или не задан (адрес набран руками), берётся первый маршрут на эту
  сущность;
- само правило — в `FilterPanel` (общая для журнала и дерева):
  параметр `RestrictManager`, метод `IsManagerLocked`; поле ищется по имени
  как `FindControl` (`managerID`, иначе `userID`), правило действует только
  если это `objectPicker`; блокируются галочка, поле и кнопка «Выбрать», значение
  остаётся;
- расширения прав — `Merlin.Classes.AdvertAgUser` (уже в `FogSoft.Core`) пришлось
  сделать `public` (было `internal`) — одно слово в общем файле десктопа;
- правило включено у `miBalance`, `miBalanceFromRSection` (184),
  `miPaymentByManagerFromRSection` (146), `miSpecialActions` (207) и у 13
  журналов статистики, кроме `FillPercentage`.

Это расхождение интерфейса, а не защита: процедуры `stat_Balance`,
`PaymentCommonActions`, `SpecialActions` сами проверяют права по
`@loggedUserID`.

#### Действия над объектами: замена контекстного меню — сделано (2026-09-18)

**Решение владельца продукта (2026-09-18).** Правая кнопка — основной способ
работы в десктопе, но для веба «не родная». Взят паттерн веб-Outlook: клик по
строке открывает карточку; при наведении в строке проявляются быстрые иконки и
«⋯» с полным меню; правая кнопка — второй путь к тому же меню (мышечная память
пользователей десктопа). Неперенесённые пункты видны **серыми** с подсказкой
«в вебе пока нет», а не прячутся. Макет утверждён до кода.

**Масштаб на `ArtvisDev`:** 421 видимое действие у 98 сущностей, 97 разных
имён. Четыре общих (`Properties`, `DeleteItem`, `AddItem`, `RefreshItem`) —
около 55%; остальное — около 110 веток в ~40 переопределениях `DoAction`.

**Как устроено.**

- *Меню* (`Infrastructure/ObjectActions.cs`) строится тем же, чем
  `MenuManager.CreatePopupMenu`: `ActionList` сущности (уже без `isHidden` и без
  вложенных), `IsActionHidden`/`IsActionEnabled` объекта, вложенные
  `ChildActions` (в метаданных их 29 у 7 родителей), схлопнутые разделители.
  Отличия от десктопа — только согласованные: «Свойства» наверху как «Открыть
  карточку», «Удалить» последним и красным.
- *Исполнение.* Десктопный `DoAction` живёт в UI-половине и почти всегда
  открывает форму. Вместо него — реестр веб-обработчиков: общие действия базовых
  классов (`Properties`, `DeleteItem`, `RefreshItem`, `AssignNew` у
  `ObjectContainer`, `AddItem` у `FakeContainer`) и псевдонимы — предметные
  действия, которые доменный класс сам сводит к общему (у `Massmedia` пять
  «Добавить …» → `AssignNew`).
- *Защита от тихого расхождения.* Если доменный класс в десктопе
  переопределяет общее действие (`Firm`/`Brand`/`AdvertType`/
  `ComboModuleContainer`/`PackageDiscountPriceList` — свой `AssignNew`;
  `ActionOnMassmedia` — «Свойства» открывают `ActionForm`; `MasterIssue`/
  `ModuleIssue`/`CampaignPart` — своё удаление; три класса спонсорских
  кампаний — своё обновление), общий веб-обработчик сделал бы не то. Такие пары
  перечислены в `ObjectActions.DesktopOverrides` и серые. Отражением этого не
  узнать: переопределения лежат в UI-половинах, которых в веб-сборке нет.
  Список составлен поиском по `override … AssignNew/ShowPassport/Delete` и
  веткам `DoAction` на эту дату — **новое переопределение в десктопе нужно
  дописывать туда руками**.
- *Меню на экране* — один хост на приложение (`ActionMenuHost` +
  `ActionMenuService`, по образцу `DialogHost`), поверх страницы: внутри строки
  его обрезал бы контейнер списка. Размещение — `wwwroot/js/actionMenu.js`
  (первый собственный JS в проекте, ~50 строк): от кнопки «⋯» или от точки
  щелчка, со сдвигом внутрь окна. Popper из `bootstrap.bundle.js` не взят: он
  спрятан внутри бандла, а `bootstrap.Dropdown` сам управляет DOM и спорит с
  Blazor. Значки — Bootstrap Icons 1.11.3 локально в `wwwroot/lib`.
- *Наведение* — только CSS: движение мыши не должно гонять сообщения по SignalR.
  Место под иконки занято всегда (`visibility`), строка не прыгает — на это
  полагается виртуализация.

**Разрез ядра.** `ObjectContainer.AssignNew` и ветка `AddNew` у
`FakeContainer` разрезаны по конвенции этапа 0: подготовка нового объекта
(`CreateNewChild` — ключи родителя и `ParentName`; `CreateNewObject`) и
завершение после сохранения (`CompleteNewChild`/`CompleteNewObject`) — в ядре,
показ карточки — в UI-половине. Десктоп ведёт себя как раньше.

**Дефект, найденный по пути: кнопка «Добавить» в дереве.** Её придумали в вебе
при переносе движка деревьев: она брала `childEntity.NewObject` и открывала
карточку — без ключей родителя. Проверено на «Рекламных тарифах»: в карточке

##### Общий механизм «класс + своё действие» в `ObjectActions`

Раньше реестр знал только общие действия базовых классов и псевдонимы
(`Aliases`). Добавлен `ClassActions`: ключ — имя класса, затем имя действия,
значение — обработчик. Поиск идёт у самого производного класса и выше, раньше
общих обработчиков и раньше `DesktopOverrides` — так же можно закрыть
переопределённое общее действие. Обработчик вызывает метод, вынесенный в ядро
из `DoAction`, и возвращает `ActionEffect.Changed`. **Тот же механизм нужен
журналу рекламных акций:** `ActionContainer` (`ShowFirms` / `ShowActions` /
`ShowHeadCompanies`) переключает `ChildEntity` корня так же, как
`AdvertTypeContainer` — обработчик добавляется записью в `ClassActions` и
разрезом `DoAction` в `ActionContainer`.

*Сборка:* `qd2.sln` собран (`Client`, `FogSoft.WinForm`), только штатные
предупреждения `Globals.cs` CS0649 и `MDIForm.cs` CS0162; сам десктоп не
запускался. Веб собран без ошибок.

#### Решение: движка `MasterDetail` не будет (2026-09-21)

**Волевое решение владельца продукта.** Отдельный движок «главная таблица —
подчинённая таблица» в веб не переносится. Четыре пункта, которые в десктопе

экранов: слева дерево, справа список детей выбранного узла.

Основание простое: это одна и та же форма отношения «родитель → дети», и у
веба она уже работает на восьми сценариях. Заводить второй движок ради той же
связи — лишний код и лишнее место для расхождений.

Какие это пункты (пара «мастер → деталь»):

| Пункт | Мастер | Деталь |
|---|---|---|
| `miAgencyTax` — Агентства и налоги | Agency (8) | AgencyTax (143) |
| `miHeadOrganizations` — Группа компаний | HeadCompany (1248) | Firm (16) |
| `miPaymentCommon`, `miPaymentFRS` — Журнал оплат | PaymentCommon (145) | PaymentCommonAction (146) |

**Что выяснилось при разборе (2026-09-21), до начала работ:**

1. **Сценария связи для этих пар в метаданных нет.** `iRelationScenario` знает
   19 сценариев, среди них ни одного с парами 8→143, 1248→16, 145→146
   (проверено на `ArtvisDev`). То есть «просто добавить маршрут в
   `MenuRoutes.Browser`» не выйдет — дереву нужен `RelationScenario`.
2. **Метаданные при этом трогать не придётся.** Конструктор
   `RelationScenario(XmlNode)` публичный и принимает XML, а не строку таблицы
   (`FogSoft.WinForm/Classes/RelationManager.cs:39`), так что веб может
   объявить пару у себя в коде — рядом с маршрутом — и не заводить строк в
   общей с десктопом базе. Это предпочтительный путь: иначе сценарий пришлось
   бы накатывать на все базы заказчиков ради экранов, которых в десктопе нет.
3. **Начальные значения отбора** (`ShowInactive=1` у групп компаний,
   `filterAgencies` у оплат) кладутся в `container.Filter` при создании — тем
   же приёмом, что уже делает `BalanceStatRow` перед `ShowBrowser`.

**Открытый вопрос — «Журнал оплат».** Для агентств и групп компаний мастер —
это справочник, и узел дерева с именем ничего не теряет. А у оплат мастер
(сущность 145) — финансовый грид: по метаданным его список это Фирма, Группа
компаний, **Сумма, Израсходовано, Остаток**, Агентство, Тип оплаты, Дата
платежа. В дереве узел показывает только имя объекта, то есть семь колонок из
восьми видно не будет, пока не открыть карточку. Для бухгалтерии это,
возможно, неприемлемо. Варианты, когда дойдёт очередь: (а) мириться,
(б) оплаты не через дерево, а двумя обычными журналами — 146 уже перенесён как
`miPaymentByManagerFromRSection`, (в) показывать мастер списком, а деталь —
под ним, то есть всё-таки две таблицы. Решать не сейчас, но и не молча.

## 7. Что обязательно учесть

1. **Права становятся серверным требованием.** Сейчас права гасят пункты меню,
   то есть защита реализована в UI. В вебе эндпоинт вызывается напрямую, минуя
   меню. Проверку прав нужно ставить на каждое действие. Это единственное
   место, где план требует принципиально нового кода, которого в десктопе нет.

   **Сделано и проверено 2026-09-10. Нового кода понадобилось меньше, чем
   считал этот пункт: модель прав уже есть в базе, её не было только на
   исполнении.** Что выяснилось при разборе:

   - права на действия хранятся в `GroupRight (groupID, entityActionID)` и
     `UserAdditionRight (userID, entityActionID, isGrant)` — устроено ровно как
     `GroupMenu`/`UserAdditionMenu` для меню, и считает их серверная функция
     `dbo.IsActionEnabled(@userID, @entityActionID)` (админ → всё;
     `isGrantingAllowed = 0` → действие вне контроля прав; иначе персональное
     разрешение, иначе группа);
   - `EntityInfoRetrieve` уже возвращает это значение по каждому действию, а C#
     кладёт его в `Entity.Action.IsEnabled`. То есть `Entity.IsActionEnabled` —
     это **не** «действие объявлено в метаданных», как читается по имени, а
     «этому пользователю оно разрешено». Десктоп этим значением только гасит
     кнопки (`JournalForm`, `SmartGrid`, `TreeView2`), на исполнении не
     проверяет никто;
   - права реальные: `DeleteItem` — 76 действий, из них 75 под контролем прав,
     `Properties` — 57/56, `AddItem` — 15/14, а `RefreshItem` — 86/3. То есть
     **пишущие операции защищены, чтение — нет**: читать даёт меню.

   Сделано три вещи, в этом порядке (первая — предусловие для остальных):

   1. **Кэш сущностей — на circuit** (см. поправку к разделу 3.1). Без этого
      проверка прав читала бы права первого вошедшего.
   2. **Проверка на исполнении — в `DataAccessor.DoAction`**, подключаемой
      политикой (`SetActionAuthorization`), тем же приёмом, что и хранилище
      пользователя: десктопу — пустая реализация, поведение не меняется; вебу —
      `WebActionAuthorization`. `DoAction` выбран потому, что это единственная
      точка, через которую проходят и чтение (`GetContent`), и сохранение
      (`Update`), и удаление (`Delete`) — ни один будущий экран этапов 2/3 не
      сможет забыть проверку.
   3. **Доступ к экрану — по меню** (`MenuAccess`): сущность доступна, если на
      неё ведёт хоть один разрешённый пункт меню (`UserMenuItems.enabled`),
      то есть ровно то же правило, что в десктопе, только проверяемое на
      сервере, а не тем, что пункта не видно.

   **Сопоставление имён.** Словари действий у слоя данных и у прав разные:
   `DoAction` оперирует `Load`/`AddItem`/`UpdateItem`/`DeleteItem`, а права
   висят на `RefreshItem`/`AddItem`/`Properties`/`DeleteItem`. Проверено
   запросом: `UpdateItem` и `Load` в `iEntityAction` не встречаются **ни разу**.
   Поэтому сохранение существующей записи (`UpdateItem`) проверяется по праву
   `Properties`, а чтение (`Load*`) не проверяется вовсе. Прямолинейное
   «имя действия = имя права» запретило бы редактирование всем, включая
   администратора.

   **Граница, которую надо помнить на этапах 2-3.** Если сущность действия не
   объявляет, оно считается разрешённым — это верный перенос десктопной
   семантики (нет строки в `iEntityAction` → в десктопе просто нет кнопки, а не
   запрет), но означает, что новое действие, которое должно быть под правами,
   обязано иметь свою строку в `iEntityAction`. Иначе оно пройдёт без проверки.
   Второе: `MenuAccess` сейчас пускает только на сущности, куда ведёт пункт
   меню; когда появятся дочерние журналы и селекторы (этап 2), правило нужно
   будет **дополнить** «доступно из родительского экрана», а не ослабить.

   **Как проверено** (dev, пользователи `sveta` — админ, и `fog` — id 133, не
   админ):

   | Проверка | Результат |
   |---|---|

   | `fog` открывает «Банк» (пункт меню разрешён) | журнал читается, 373 строки — чтение не перекрыто |
   | у него же «Добавить»/«Открыть» | погашены (`AddItem`=0, `Properties`=0) |

   Последняя строка — дефект, который нашла сама проверка: кэш «на circuit» не
   то же самое, что «на пользователя», и выход с повторным входом в той же
   вкладке оставлял метаданные (а значит, права) от предыдущего. Сброс сделан в
   `WebLoggedUserStorage` — единственной точке, где в вебе меняется текущий
   пользователь.
2. **Валидация имён сущностей и действий, приходящих с клиента.**
   `DataAccessor.DoAction` резолвит процедуру по ключу
   `EntityId_ActionName_InterfaceObject` из параметров. Клиент не должен иметь
   возможности запросить произвольную сущность или действие. Параметризация
   запросов сама по себе в порядке (`BuildExecScript` — только для
   диагностики).
3. **Долгие операции.** Пересчёт акции и отчёты за широкий период сейчас просто
   вешают UI-поток. В вебе появляются таймауты Kestrel и обратного прокси; нужен
   фоновый запуск с прогрессом хотя бы для отчётов. Кандидаты видны по логу
   `DbExecutionScope` (`StoredProcExecutionTimeThresholdMS`) и по вызовам с
   кастомным command timeout.
4. **Объёмы данных в сетках.** WinForms-сетки показывают тысячи строк без
   постраничности; тарифная сетка — матрица «даты × окна». В HTML нужна
   виртуализация или постраничность, иначе экран умрёт на реальных данных.
5. **Культура и форматы дат.** Культура сейчас ставится на клиенте (`Language`
   = `ru`), даты в интерфейсе — ДД.ММ.ГГГГ. В вебе культура ставится на запрос,
   а HTML-инпуты отдают ISO. Классический источник тихих багов при разборе.
6. **Файловая система.** `Templates\`, файлы роликов, импортируемые выписки —
   всё превращается в серверные пути плюс upload/download-эндпоинты.
7. **Отсутствие тестов.** Тестового проекта в репозитории нет. Переписывать UI
   поверх непокрытой логики рискованно. Минимум перед этапом 3: снять эталонные
   результаты ключевых вызовов процедур на тестовой базе, чтобы сравнивать
   «до и после».
8. **Развёртывание — решено (2026-08-24): Kestrel напрямую, без IIS.**
   На сервере, где сейчас крутится десктоп через RDP, IIS не установлен
   (служба `W3SVC` отсутствует) — заводить его ради обратного прокси
   означало бы новую зависимость сверх того, что нужно. `dotnet publish` +
   Kestrel как служба Windows закрывает автозапуск после перезагрузки без
   IIS. HTTPS и сертификат — если понадобятся при выходе за периметр
   (вопрос №6) — тоже настраиваются в самом Kestrel, IIS для этого не
   обязателен. Вместо раскладки клиента — публикация службой; конвейер
   выката и процедура отката ещё не определены. Текущая автоматизация
   (`AdvertAg.build`, NAnt, `pack.bat`, `PublishUrl`) не переиспользуется.
9. **Многопользовательность на уровне БД не меняется** — десктоп и сейчас
   работает многопользовательски против одной базы, конкурентность
   разруливается процедурами. Новых гонок веб сам по себе не вносит; вносит
   только п. 1.
10. **Память сервера.** Состояние открытых экранов переезжает с рабочих станций
    на сервер. Нужны таймаут простоя, ограничение числа открытых вкладок и
    оценка памяти на пользователя на этапе 2.

#### Что подтвердилось

- **Ядро переиспользуется целиком.** Своего SQL в вебе нет ни строки: журнал
  идёт через `Entity.GetContent`, сохранение — через `PresentationObject.Update()`,
  то есть те же IUD-процедуры. Мост этапа 0.4 окупился ровно здесь.
- **Довод 5.1 №2 про диалоги — верен буквально.**
  `if (form.ShowDialog(owner) == DialogResult.OK)` превратился в
  `if (await Dialogs.ShowAsync(...) == DialogOutcome.Ok)`. Механика —
  `TaskCompletionSource`; работает потому, что состояние компонента в Blazor
  Server живёт между действиями, как жил бы стек WinForms-формы. Это был самый
  весомый аргумент за выбранную технологию, и он выдержал проверку.
- **Шов `ILoggedUserStorage` из этапа 0.2 подошёл без правок ядра.**

#### Находки, видимые только на живом прогоне

Ни одна из них не видна в архитектуре — ради них срез и делался:

1. **`DataAccessor.procedureConfigs` не грузится лениво.** Все остальные
   словари ядра догружаются сами при промахе кэша, этот — нет: `DoAction`
   берёт `procedureConfigs[key]` напрямую и падает с `KeyNotFoundException`.
   В десктопе его грузит `SplashLogginForm` после входа; в вебе понадобился
   свой вызов (`CoreBootstrap`).
2. **Метаданные жёстко называют сборку десктопа.** `iEntity.assemblyName` для
   доменных сущностей — `Merlin`, то есть `Merlin.exe`. В вебе те же классы
   лежат в `FogSoft.Core.dll`, и `Entity.CreateObject` их не находил. Решено
   сопоставлением имён на стороне веба (`DomainAssemblyResolver`); менять
   метаданные нельзя — база общая с десктопом.
3. **Смешение статической и интерактивной отрисовки раздваивает
   scoped-сервисы.** Шаблон Blazor делает страницы статическими по умолчанию;
   макет оставался статическим и получал *другой экземпляр* scoped-сервиса,
   чем интерактивная страница. Симптом (диалог «уже открыт», но не виден)
   совершенно не похож на причину. Лечится объявлением интерактивности
   глобально — для замены десктопа статическая отрисовка не нужна нигде.
4. **Фильтр может быть мёртвыми метаданными.** У сущности 17 фильтр объявляет
   поле `isHidden`, которого процедура `AdvertTypes` не принимает вовсе;
   параметр молча отбрасывается при сверке с реальными параметрами процедуры.
   Так же ведёт себя и десктоп — это не дефект веба. Важно для этапа 2:
   «фильтр не работает» может означать заброшенную функцию, а опечатка в имени
   параметра фильтра никак себя не проявит.
