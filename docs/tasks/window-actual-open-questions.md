## 1. Контекст

**Две пары полей:**
- `TariffWindow.windowDateOriginal` / `dayOriginal` — время окна по расписанию тарифа. Пишется один раз при создании
  и служит ключом слота.
- `TariffWindow.windowDateActual` / `dayActual` — время после «Отредактировать время выхода» (`SP/TariffWindowMoveTime.sql`)
  или правки в паспорте окна.
- `Issue.originalWindowID` — окно, куда выпуск поставили.
- `Issue.actualWindowID` — окно, где выпуск реально выйдет. Развести эти два поля может только `SP/IssueTransfer.sql`
  (перенос трафиком).

**Правило Миши от 07.10.2026:** везде используется фактическое окно и фактическое время, исходное значение остаётся
только для истории переносов. Это правило отменяет В-10 от 06.10.

**Масштаб расхождений:**
- 1 207 выпусков, у которых исходное окно ≠ фактическому;

### 2.1 Вопросы из карты (Р-1…Р-8)

#### Р-1. Строки трафик-сетки и сетки генерации остаются «по расписанию»?
- **Суть.** Строку сетки и групповые операции по строке адресует время по расписанию:
  - «Отредактировать время выхода»;
  - «Изменить продолжительность»;
  - «Удалить...»;
  - «Изменить цену»;
  - «Изменить окна…».

  Если строить строки по фактическому времени, операции после первого переноса промахнутся.
- **Варианты.** (а) Оставить. Это узнавание слота, то есть законная история окна. (б) Перевести операции на windowId.
- **Рекомендация.** (а).
- **Уточнено.**
  - Строка — это пара (время по расписанию, цена), а не тариф (`SP/TariffWindowRetrieve.sql:148-154`,
    `Cls/TariffWindowWeek.cs:224,233`). У одного времени с двумя ценами две строки. Особое окно — отдельная строка
    с ценой 0.
  - При (б) операция по строке с фактическим временем 10:20 не «найдёт 0 окон», а изменит окна чужого слота 10:20,
    если такой есть.
  - Цена варианта (б) занижена. Процедур не 5, а минимум 6: забыта `SP/TariffWindowChangeDuration.sql:52`.
    `SP/TariffWindowRetrieveByDate.sql` общая с клоном (`Cls/ActionOnMassmedia.cs:573`). Ещё C#:
    `Cls/TrafficManagement.cs:102-104,201`, `Cls/TariffWindowWeek.cs:237`, `Ctl/TariffWindowGrid.cs:459`.
  - Колонка (день) тоже по исходной дате. Поэтому (а) без противоречий работает только вместе с Р-2 «запретить».
  - Довод «фактическое время показано в ячейке» верен только для трафик-сеток. В десктопной сетке генерации
    (`Ctl/TariffWindowGrid.cs:480-487`) и в тексте ячейки веб-генерации его нет.
  - Посылка «слот однозначно задан парой (станция, windowDateOriginal)» схемой не гарантирована: уникального
    индекса нет, `T/TariffWindow.sql:53-136`. Связано с Р-7 и Т-3.
- **Доп. вопрос.** Показывать ли фактическое время в десктопной сетке генерации (добавить в этап 7)?

#### Р-2. Запретить менять дату окна — только время?
- **Суть.** Сейчас dayOriginal = dayActual у всех 2 010 628 окон. Если дату запретить, это станет гарантией, и около
  15 мест «день окна» (модули, пакеты, сетки, §2.1 карты) останутся на dayOriginal без эффекта.
- **Варианты.** (а) Запретить. (б) Разрешить и перевести эти места на dayActual, добавить индекс (tariffId, dayActual)
  и защиту от двух окон одного тарифа в одном дне.
- **Рекомендация.** (а).
- **Уточнено.**
  - Развести дни может не только UpdateItem (`SP/TariffWindowIUD.sql:133`), но и AddItem (`:156-159`). Там дни
    считаются отдельно из двух дат, которые передал вызывающий. Запрет нужен в обоих режимах. Дополнительно
    можно добавить CHECK (dayActual = dayOriginal) на таблицу; без него гарантия держится только на дисциплине
    писателей, включая будущие Deploy-скрипты.
  - Запрет делать в SQL. UpdateItem вызывают паспорт в десктопе, паспорт в вебе (`Traffic.razor:731`,
    `TariffWindowsView.razor:219`) и объединение окон (`TariffWindowWithRollerIssues.WinForms.cs:51,78`).
    Нужен новый ключ iMessage с переводом на es (`docs/business-errors.md`).
  - Обход «окно после полуночи — особым окном следующего дня» создаёт окно без тарифа, с ценой 0 и вместимостью 0.
    Это пересекается с Р-3: при варианте (а) Р-3 «Сделать первым» обнулит цену выпуска.
  - При (а) индекс `UX_TariffWindow_dayActual_windowID` из этапа 0 становится необязательным. Читатели,
    переведённые на фактическое окно, могут фильтровать по его dayOriginal через существующий
    `UX_TariffWindow_dayOriginal_windowID`.
  - Ветки показа сдвига на другую дату (`Cls/TariffWindowWeek.cs:287-288,349-350`) после запрета перестанут
    срабатывать на новых данных.

#### Р-3. Цена выпуска (tariffPrice) после переноса трафиком
- **Сейчас.**
  - IssueTransfer цену не меняет.
  - Любая смена позиции, не только «Сделать первым» (в том числе массовая через ChangePositioningForm,
    `Cls/CampaignPart.cs:179`), пересчитывает цену от tw.price фактического окна (`SP/IssueIUD.sql:338,349,369-370`).
    Клиент уже передаёт фактическое окно (`Cls/Issue.cs:68-73`).
  - Замена ролика другой длины считает цену от исходного окна (`SP/RollerSubstitute.sql:113,117,207`).
  - Автоперенос при активации считает цену от нового окна.
- **Варианты.**
  - (а) Как в карте: перенос цену не меняет, последующие пересчёты идут от фактического окна. Для окна без тарифа —
    откат на прайс-лист исходного окна. Минусы: цена «догонит» окно при посторонней операции, например при смене
    позиции. Откат на исходное окно использует его не как историю.
  - (б) Новое: перенос цену не меняет, последующие пересчёты масштабируют хранимую цену. Замена ролика —
    ×(новая длина / старая), смена позиции — ×(1 + c_new/100) / (1 + c_old/100). `Fn/fn_GetIssuePrice.sql` линейна
    по длительности и по наценке, поэтому окно читать не нужно, и проблема окон без тарифа исчезает. Проверить
    округление decimal(18,2).
  - (в) Перенос трафиком пересчитывает цену по новому окну. Тогда трафик-менеджер меняет деньги клиента.
- **Рекомендация.** (б).
- **Уточнено.**
  - Наценки спонсора (`SP/ActionRecalculate.sql:147-152`, `SP/ActionActivate.sql:159-165`) — это не цена,
    а расход бонусного времени: `f_GetSponsorDuration` → `Campaign.issuesDuration`, проверка TimeBonusExceed.
    Их надо перевести в обычное «П», убрать из Р-3 и из зависимостей этапа 4.
  - Р-3 касается только линейных кампаний. У модульных и пакетных `Issue.tariffPrice` = 0, у спонсорских деньги
    идут по ProgramIssue.
  - «Сделать первым» в окне без тарифа обнуляет цену уже сейчас (`SP/IssueIUD.sql:75-84`).
  - Справочник (§5 №3) называет пересчёт от фактического окна дефектом. После решения согласовать.
  - Числа в документах расходятся: «138 из 158» (справочник:156), «158 из 518» (карта), «239» (справочник §5 №3).
    Пересчитать одним запросом.

#### Р-4. Автоперенос при активации считать переносом (писать только actualWindowID)?
- **Рекомендация.** Да, этап 8.
- **Уточнено.**
  - TransferLog при автопереносе уже пишется (`SP/ActionActivate.sql:570-572`). В Issue теряется только
    исходное окно.
  - Автоперенос внутридневной (`:265,279`), поэтому деньги и права не затрагивает. Зависимость этапа 8 — от этапов
    1, 2, 3, 5 и 6, а не «1–7»; от этапа 4 он не зависит.
  - Проверку «тестовая активация» сделать нельзя: при @isTestActivate = 1 автоперенос не запускается (`:223-226`).
    Нужна настоящая активация тестовой акции.
  - Нужно записать, почему при автопереносе цена пересчитывается, а при переносе трафиком нет. Причины: акция ещё
    макет; базовая цена по умолчанию совпадает (`:299`); разная допускается только с флагом
    allowDifferentWindowPrice. Если окно-кандидат без тарифа, наценка за позицию обнуляется (`:522-524`).
  - После «да» окно, где активация не прошла, остаётся ссылкой originalWindowID, и удалить его будет нельзя
    (`SP/TariffWindowIUD.sql:54`, `SP/TariffWindowMassDelete.sql:21`).
  - Журналы покажут разное «исходное время» одного переноса. «Переносы» кампании берут время по расписанию
    (`SP/CampaignIssuesTransfers.sql:16`), а таблица активации и TransferLog — фактическое время окна-источника
    (`SP/ActionActivate.sql:93`).

#### Р-5. «Перенос дня» для выпуска, ранее перенесённого трафиком
- **Варианты.** (а) Обе колонки = новое окно в слоте фактического окна; пометка о переносе трафиком стирается.
  (б) Перенести оба окна, каждое в свой слот.
- **Рекомендация.** (а) без TransferLog, но с поправками:
  - Прайс-лист для поиска слота брать из тарифа **фактического** окна. В карте сказано «исходного», а это то же
    смешение осей, что в `SP/RollerSubstitute.sql:152`. К тому же если тарифа нет у исходного окна, @priceListID =
    NULL, и слот не найдётся.
  - Запасной поиск по (станция, windowDateOriginal) неоднозначен: уникального индекса нет. Нужен ORDER BY с
    приоритетом тарифного окна.
- **Сказать Мише прямо.** (а) стирает историю переноса, а Р-4 её сохраняет. Строки TransferLog этого выпуска
  остаются: журнал переносов (сущность 141) продолжит показывать старый перенос, а «Переносы» кампании (206) — уже
  нет.
- **Уточнено.**
  - «Новая постановка, как перетаскивание или клон» — неточно. issueID, позиция, подтверждение и tariffPrice
    сохраняются. Про цену см. Р-9.
  - Отбор модульных «по дню модуля» сегодня ничего не меняет, кроме 446 пакетных с днём +1 (О-8).
  - После обнуления @windowId (§6 карты, п. 1) тихая постановка в чужое окно превратится в TransferError посреди
    цикла (Т-5).

#### Р-6. Срок хранения TransferLog
- **Уточнено.**
  - Числа 30 в коде нет. Срок задаёт общий параметр `DaysHistorySave` из `iInternalVariable`, по умолчанию 365
    (`Fn/f_SysParamsDateHistorySave.sql`). Он же задаёт срок журнала удалённых выпусков и объявлений
    (`SP/DeleteHistory.sql:15-23`).
  - Строка удаляется, только когда все три даты (переноса, старая и новая) старше срока.
  - Очистку запускает только `job_DeleteEmptyActions`, то есть Protector. Фактический срок зависит и от того, как
    часто её запускают.
  - История пропадает и каскадом при удалении выпуска (`T/TransferLog.sql:10`): перетаскивание — это удаление плюс
    добавление.
- **Варианты.** (а) Оставить общий параметр. (б) Поднять его в «Системных настройках» без правки кода: удлинятся
  все три журнала. (в) Отдельный параметр для TransferLog: правка функции, SysParams, SysParamsUpdate, метаданных
  и DeleteHistory.
- **Рекомендация.** (а). Если нужно дольше — (б).

#### Р-7. Что считать дублем окна
- **Суть.** «Создать новое окно…» (`Cls/SpecialTariffWindow.cs:52`, `SP/TariffWindowRetrieve.sql:48`) ищет
  совпадение обеих дат. Поэтому можно создать второе окно в ту же эфирную минуту или дубль слота.
  Слить с соседним вопросом: «Отредактировать время выхода» и паспорт окна могут свести два окна в одну эфирную
  минуту без предупреждения (390 таких совпадений уже было). DJin режет блоки по строке времени, поэтому такие окна,
  вероятно, сольются в один блок (вживую не проверено, Т-6).
- **Варианты.** (а) Одно правило дубля для всех путей — создание, шаблоны, MoveTime, паспорт: «у станции уже есть
  окно с windowDateActual = X или windowDateOriginal = X». MoveTime пропускает окно с причиной в журнале
  «не перенесено», паспорт отказывает. (б) Предупреждать, но разрешать. (в) Только «Создать новое окно…», как
  в карте.
- **Рекомендация.** (а) для новых действий; старые 390 совпадений не трогать.
- **Уточнено.**
  - Сейчас найденное окно не «молча обновляется», а пересохраняется со своими же значениями. Ввод пользователя
    (длительность, цена, вместимость) теряется без сообщения. Поиск не фильтрует по tariffId.
  - «Решить без Миши» не получится: правило «windowDateOriginal = X» запрещает особое окно в минуту, которая
    освободилась после переноса слота. Трафик-менеджерам это нужно объяснить; обход — минута рядом.
  - Особое окно, созданное раньше слота, молча блокирует генерацию тарифного окна. Тариф в этот день выпадает
    из продажи (`SP/sl_GenerateTariffWindowsDay.sql:65-75`), а у шаблонов строки в @errors нет.
  - Дубль слота ломает `SP/TariffWindowRetrieveByDate.sql` (без ORDER BY, вызывающие берут Rows[0]). Клон может
    поставить выпуск в особое окно, «Удалить...» — выбрать не то окно.
  - Довод «последнее окно без тарифа создано 15.06.2025» смешивает эту функцию с окнами по шаблону. Даты создания
    в TariffWindow нет.

#### Р-8. Склейки окон: что делать с чужим окном в эфирном промежутке цепочки
- **Уточнено.**
  - Генерация не «начнёт» удалять склейки — она удаляет их уже сейчас (`SP/CheckLinkedWindows.sql:24-33`), но по
    времени по расписанию. Меняются ось и критерий: сейчас достаточно любого windowPrevId, а не именно хвоста.
  - Новая проверка порвёт и связи, которые сейчас уцелели потому, что между звеньями стоит хвост другой цепочки.
    Цифра «0 из 416» это могла не учесть.
  - У `Fn/f_CheckLinkedTariffWindows.sql:13` есть второй вызывающий — `SP/GenerateTariffWindowByTemplate.sql:84`.
    Шаблонная генерация и «Продлить окно» начнут отказывать с InsideLinkedWindowError. Этого нет ни в уведомлении,
    ни в тексте для пользователей. Правка одной `SP/TariffWindowIUD.sql:144` эффекта не даёт.
  - Проверка стоит не там, где окна сдвигаются. MoveTime (`:66-119`) и паспорт (`SP/TariffWindowIUD.sql:75-101`)
    проверяют только собственные связи окна. Поэтому чужое окно в промежуток ставится свободно, а связь рвётся
    позже, при постороннем запуске генерации. «Объединить с предыдущим/следующим» в трафике
    (`Ctl/TrafficGrid.cs:226-265`) ищет соседа по строке расписания, а не по эфиру.
- **Варианты.** (а) Только уведомить трафик-менеджеров, как в карте. (б) Ещё и не пускать окно в эфирный промежуток
  чужой цепочки. MoveTime — пропуск с журналом «не перенесено», как LinkedWindowsWrongOrder; паспорт и
  «Объединить» — отказ. Одна функция проверки на все места. (в) Одно из направлений A–D из
  `docs/window-merging.md:273-286` — это большая переделка.
- **Рекомендация.** (б), этап 7. Это новый отказ трафик-менеджеру, поэтому нужно решение.
